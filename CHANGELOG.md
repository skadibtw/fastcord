# Changelog

## Unreleased

### Added
- macOS stream audio (M37, #37): "Share audio" on macOS 13 and later records an audio-only ScreenCaptureKit stream next to the picture: a shared window sends its application's sound (the owner found through the window server), a shared screen everything except fastcord (`excludesCurrentProcessAudio`), so the call is never sent back. Samples arrive as 48 kHz stereo `f32` and are interleaved on ScreenCaptureKit's queue into the existing Go Live audio path with no allocation; the picture stream and the audio stream end independently. Type-checked and linted for `aarch64-apple-darwin` from Windows only; the maintainer's run is pending (docs/TESTING.md).
- Linux stream audio (M36, #36): with "Share audio" on, the Linux share picker lists the PipeWire outputs ("Everything “…” plays", captured through the output's monitor) and inputs ("Input “…”"), outputs first and never fastcord's own nodes, and the chosen one is captured as 48 kHz stereo `f32` into the existing Go Live audio path. The screen portal is never assumed to carry audio. Choosing an output shows the warning that viewers may hear the call; the note explains routing one application to a separate output (for example with pavucontrol) to share only that. A node that disappears ends the audio instead of silently moving to another one (`node.dont-reconnect`); no choice means the picture only, with a notice. Checked against a real PipeWire daemon in WSL (a source and a null output's monitor, about one second of a 440 Hz tone each); the official viewer and A/V sync on a desktop remain a manual check.
- macOS screen sharing (M34, #34): `fastcord-platform::capture` gains a ScreenCaptureKit backend (`objc2-screen-capture-kit` and the objc2 CoreMedia/CoreVideo/CoreGraphics bindings, all from the objc2 0.6 family already in the tree). The picker lists the displays (in pixels, Retina-aware) and on-screen windows (never fastcord's own); ScreenCaptureKit scales the source to at most 1280x720 at 30 fps and delivers `420v` NV12 in BT.709, so no converter runs; window resizes are scaled into the picture. A missing Screen Recording permission reads "allow fastcord under System Settings, Privacy & Security, Screen Recording"; the window closing or the user stopping the share from the menu bar ends it as closed. Type-checked and linted for `aarch64-apple-darwin` from Windows only; the maintainer's run on a Mac is pending (docs/TESTING.md). Camera capture on macOS and macOS stream audio (M37) are not part of this.
- Linux screen sharing (M33, #33): `fastcord-platform::capture` gains a Linux backend over xdg-desktop-portal ScreenCast (`ashpd`, already in the tree) and PipeWire (`pipewire` 0.10, linking the system `libpipewire-0.3`). The share picker offers "A screen" and "A window", each opening the desktop's own dialog; the stream is negotiated as BGRx/BGRA shared memory (no DMA-BUF) at up to 30 fps and converted to NV12 by the existing CPU converter, paced like Windows. Cancelling the dialog ends with "No screen or window was chosen" before Discord is told anything; the desktop ending the session ends the share as closed. Linux builds now need `libpipewire-0.3-dev` and `clang` (CI and release workflows install them); docs/RELEASE.md lists the runtime requirements. Checked against a real PipeWire daemon in WSL; the portal and the official client on a Wayland desktop remain a manual check. Camera capture on Linux and Linux stream audio (M36) are not part of this.
- Voice channel bitrate (#118): the microphone is encoded at the joined guild voice or Stage channel's `bitrate` (clamped to 8-384 kbit/s) instead of a fixed 64 kbit/s; DM calls and channels without one keep 64 kbit/s. A `CHANNEL_UPDATE` of the joined channel or a move retargets the running encoder through the new `EngineControl::Bitrate` without reopening devices, and the audio dialog shows "Sending your voice at N kbps" during a call. Needs a manual check on a live call (docs/TESTING.md).
- Offline fake Discord for app testing (`feat(dev)`, no issue): the `fastcord-fake` crate serves a synthetic world (three servers, DMs, friends, about 200 messages) over loopback REST and a zlib-stream Gateway, logs every request to a redacted `fake-requests.jsonl`, and answers anything it does not implement with 404 `fake: not implemented`. `fastcord-app --features fake-discord -- --fake-discord <port>` (debug builds only; a release build with the feature fails to compile) signs in at once with a fixed token, memory-only, keeps its files under `fastcord-fake`, never opens the credential store, tray, autostart or single-instance hand-off, shows a `[FAKE]` title and a banner, and fetches no avatar, emoji or attachment from the network. Not covered: voice, video, QR and password login, real request shapes (live alt-account checks stay the only wire proof).

(Fixes #43).
- Release archives now carry the libopus BSD-3-Clause copyright, conditions and disclaimer (the exact `opus/COPYING` of `libopus_sys` 0.3.3 bundled by `opus2` 0.4.0, with source attribution) plus the davey 0.1.4 and OpenMLS MIT notices in `THIRD_PARTY_NOTICES.md`, and a generated `THIRD_PARTY_CRATES.md` with the license text of every Rust crate the Windows/Linux/macOS release targets can link (`scripts/gen_third_party_licenses.py`, `--check` for staleness after `Cargo.lock` changes). `scripts/package.sh` copies both files into every archive and refuses to package if the libopus notice is missing. (Fixes #44).
- Explicit attachment Download is no longer capped by the 64 MiB Open cache limit: it streams straight to the chosen file through a `.part` file that is renamed into place only when complete, and it never enters the cache. Open and previews keep the limit (Fixes #45).
