# Changelog

## Unreleased

### Added
- `fastcord-model`: typed Discord entities (`User`, `Role`, `Channel` with forward-compatible `ChannelKind`, `Message`, attachments, reactions, replies), serde wire decoding (decimal-string IDs/permissions), partial `MessageUpdate` merge that never clears omitted fields, and Discord's channel permission algorithm (owner/admin, `@everyone`/role/member overwrites, implicit view/send rules, timeouts).
- `fastcord-discord`: fixed-origin `/api/v10` REST over reqwest/rustls with sensitive raw-token authorization, zeroizing/redacted user credentials, bounded JSON bodies, typed permission/resource/authentication/retryable errors, and account-wide 401 cancellation. Its monotonic-clock scheduler learns shared buckets while retaining major IDs, reserves concurrent capacity, serializes unknown routes, honors fractional resets and route/global 429 deadlines, and prioritizes user writes over speculative reads.
- Token login: masked, bounded token entry with an alt-account/ToS acknowledgement; off-thread `GET /users/@me` validation; correct account identity; explicit memory-only sessions; saved-login restoration; and logout that stops authenticated work, purges account state, and reports native deletion failures without claiming success.
- `fastcord-platform`: `keyring-core` with exactly one target-selected native backend (Windows Credential Manager, macOS Keychain, Linux Secret Service), credentials under service `fastcord` and account ID, native account discovery without a plaintext index, serialized off-thread access, zeroizing/redacted loaded tokens, and categorical secret-safe errors.
- QR login (ADR 0006): `fastcord-discord::remote_auth` implements Discord's remote-auth protocol v2 over a rustls/ring WebSocket with a per-attempt RSA-2048/OAEP key pair, nonce proof, fingerprint verification, heartbeats, the server's session timeout, pending-user display, and the ticket-for-token exchange. The login screen shows the QR code (primary method) with explicit start, cancel, regenerate, expiry and phone-cancel handling; the resulting token follows the same `GET /users/@me` validation and native-store path as token paste. A CAPTCHA demand stops with a clear message pointing to token login or the official client. Keys, tickets, QR links, and tokens are memory-only, redacted in `Debug`, and dropped when an attempt ends.
- Main Gateway lifecycle (ADR 0005): `fastcord-discord::gateway` connects to API v10 with `compress=zlib-stream` (one persistent zlib context per connection, fragmentation-safe, 16 MiB event ceiling with incremental decompression), Identifies with the web-client profile (Chrome properties, build number fetched from discord.com with a bundled fallback, capabilities 16435 from named flags), heartbeats with jitter and ACK enforcement, Resumes with sequence replay and duplicate dropping, and reconnects with bounded jittered backoff. Explicit state machine with terminal `AuthenticationRequired` (close 4004 or any 401 of the account) and `Stopped` (rejected payloads, too many sessions, an account action Discord requires, repeated Invalid Session, oversized or undecodable READY): no challenge is ever completed or bypassed. READY and READY_SUPPLEMENTAL are decoded without an untyped JSON tree and normalized (users stored once, members and DM recipients by ID, `merged_members` aligned with guilds); `PASSIVE_UPDATE_V2` and the live message/guild/channel events are typed. Delivery is a byte-bounded queue (2 MiB) with backpressure that never stops heartbeats and never drops or reorders events; a 120-frames-per-60-seconds send ceiling is enforced. `fastcord-model` gains `Guild`, `GuildMember`, `VoiceState` and `Channel::recipient_ids`; `fastcord-platform` reports the system locale. The account screen shows the live connection state (connected with server/DM counts, reconnecting, rejected token returns to login, stopped with reason). The Identify profile and its evidence are documented in `docs/PROTOCOL.md`.
- Bounded Discord state and lazy guild subscriptions: opcode 37 follows only the selected and active voice guilds, coalesces navigation, limits member ranges and individual interests, releases obsolete subscriptions explicitly, and retains its transmitted ledger across Resume. The single-writer reducer normalizes users/members, applies sparse member-list SYNC/INSERT/UPDATE/DELETE/INVALIDATE and passive/voice/member updates, releases ranges on navigation, and evicts unreferenced detail under a capacity-accounted 12 MiB metadata ceiling. Required identity/permission state that cannot fit stops the connection with a visible safety error rather than silently truncating it. No opcode-14 fallback, activities, threads, or typing UI.
- Guild/channel navigation: reducer-validated server and text/announcement/voice selection, deterministic category ordering, owner/admin/overwrite-aware access, disabled inaccessible voice/outage rows, stable remembered selections, and immediate closure when permissions or metadata change. Fixed-height lists instantiate only viewport/overscan rows; compact latest-slot UI windows and coalesced controls remain bounded, with no history prefetch or voice auto-join. Role lifecycle events and incomplete member-role metadata are handled for permission correctness.
- Renderer backend is pinned through safe iced/wgpu compositor configuration to DX12 on Windows, Metal on macOS, and Vulkan on Linux, independent of `WGPU_BACKEND`; tiny-skia remains the no-adapter fallback. Reference working-set/private-memory measurements and remaining authenticated/platform checks are recorded in `docs/PERFORMANCE.md` and `docs/TESTING.md`.
- Message history and virtualized timeline: a typed `GET /channels/{id}/messages?limit=50` reader (latest/before/after cursors, hard record limit, wrong-channel and wrong-side pages rejected), a single-writer `MessageStore` (16 MiB capacity-accounted budget, at most 500 messages per channel and 2,000 globally, retention nearest the reader's anchor rather than the newest rows, bodies over 512 KiB rejected instead of truncated, a bounded request journal so a stale REST page never resurrects a message the Gateway deleted or edited meanwhile), `MESSAGE_DELETE_BULK` decoding, per-message layout revisions, and redacted `Debug` for messages and attachments. The UI has a reusable variable-height virtual list (Fenwick prefix sums keyed by message ID and width bucket, measured heights, at most two buckets per row, message-ID plus in-row-offset anchoring that survives prepends, deletions above the viewport, resizes and image-height changes, follow-new-messages only at the bottom, jump-to-latest) that builds widgets only for the viewport plus one viewport of overscan with exact spacers, and a timeline pane that shows author, time, wrapped text, and attachment metadata for the selected readable channel. Paging happens only on explicit action or when scrolling near the retained edge; the worker publishes at most 512 KiB of bodies per snapshot through the same coalescing latest slot as navigation.
- Sending messages: a multi-line composer under the timeline (Enter sends, Shift+Enter breaks the line, per-channel drafts for the 16 most recent channels, an 8,000-character editor cap, a length note near Discord's limit) shown only where the account has `SEND_MESSAGES`. `POST /channels/{id}/messages` carries a snowflake-shaped string nonce with `enforce_nonce` and an always-explicit `allowed_mentions` (users and roles; `@everyone`/`@here` only when ticked for that message). Each send is one outbox operation, posted once, one per channel at a time in written order, confirmed by whichever of the REST answer or the author's own nonce-matching `MESSAGE_CREATE` arrives first, so it is never shown twice. Failures are classified as "Not sent" (refusals, never connected: Retry, Edit, Discard) or "Not confirmed" (timeouts, broken responses, 5xx: Retry send with the same nonce, Discard, or resolved by the Gateway); nothing is re-posted automatically. The outbox is limited to 16 operations through slots the UI reserves before queueing, and message text never reaches `Debug` output. `fastcord-model` decodes message nonces leniently.
- Editing and deleting own messages: only the account's own `DEFAULT`/`REPLY` messages show Edit and Delete (on hover); someone else's messages and system messages show neither, and the worker re-checks ownership against its store before any request. Edit moves the text into the composer (the draft is set aside and returns on Save or Escape) and sends `PATCH /channels/{id}/messages/{id}` with `content` only, so attachments and other fields are never removed by a text edit; an empty edit is allowed only while attachments remain. Delete asks for confirmation in the row, then sends `DELETE` (a 404 counts as deleted). The REST answer and the Gateway's `MESSAGE_UPDATE`/`MESSAGE_DELETE` reconcile through one store path in either order: an edit's answer never rolls back a later edit from another client (RFC 3339 `edited_timestamp` ordering), partial updates keep omitted attachments, and nothing is ever recreated. Changes being saved show their new text marked "Saving your edit…"/"Deleting…"; failures stay on the row with a fixed reason, Retry (once, explicitly), and Dismiss, and resolve by themselves when the Gateway reports the same outcome. At most one change per message and 16 overall; edit text is redacted from `Debug`.
- `fastcord-audio` engine and native devices: cpal device enumeration (off the UI thread) with stable backend IDs, explicit `System default` versus a specific device that fails rather than silently falling back, and stream-format selection preferring 48 kHz. One owner thread per call opens and closes the streams; callbacks only convert any cpal sample format to/from f32 through preallocated lock-free SPSC rings (100 ms cap, oldest capture discarded on overrun, counted silence on underrun) and never allocate, lock, or do I/O, which a counting allocator verifies in tests and on real devices. The engine downmixes the microphone to mono, resamples device rates to 48 kHz (rubato sinc), encodes 20 ms Opus frames at 64 kbit/s with in-band FEC (bundled, statically linked libopus via `opus2`), and decodes, resamples, and maps Opus packets to the output's channel layout at a 40 ms playback target; decoders also provide FEC recovery and concealment. Encoded frames and playback packets cross bounded Tokio channels; device failures are reported as events. Dropping the engine stops the streams, joining their callback threads. Fatal device errors close only the failed direction's endpoint (discarding queued playback packets), malformed playback attempts are bounded per service pass, integer output saturates, and a 256-tap sinc retains the 20 kHz passband between 44.1 and 48 kHz.
- Replies across the timeline and composer: `POST /channels/{id}/messages` carries a genuine type-0 `message_reference` with `fail_if_not_exists`, and always states the per-reply `allowed_mentions.replied_user` choice (off by default). Reply previews resolve only visible, uncached targets; bounded cached/deleted/unavailable states and `limit=49` around history loading support exact-target jumps without landing on neighbors or replacing the existing viewport for deleted targets. REST- and Gateway-confirmed deletions invalidate reply previews immediately. Editing a failed send restores its original reply target and mention choice rather than silently converting it into a plain message. Deleted targets cannot silently degrade to plain sends. Live official-client acceptance is pending the authorized alt session.
- Voice session and encrypted RTP transport (new crate `fastcord-media`, depending on `fastcord-model` only): main Gateway opcode 4 through `Gateway::voice_state()` (sent only while Ready, coalesced, Resume-aware, never starving heartbeats) and decoded VOICE_SERVER_UPDATE; join correlation of VOICE_STATE_UPDATE/VOICE_SERVER_UPDATE in either order with a fresh generation per join, move, reallocation, or credential change; a voice Gateway v8 task (Identify with `max_dave_protocol_version: 1`, `t`/`seq_ack` heartbeats over JSON and binary sequences, Resume keeping UDP, transport keys, and DAVE state, typed close reasons including 4017 "E2EE required"), UDP IP discovery with retries and a visible "UDP blocked" outcome, UDP ping latency, and `aead_aes256_gcm_rtpsize` (preferred with hardware AES) / `aead_xchacha20_poly1305_rtpsize` transport encryption with a never-wrapping nonce. Local media remains queued until an authenticated DAVE group transition enables it; outgoing audio is DAVE frame-encrypted before transport AEAD. RTP (CSRCs, RFC 8285 extensions, padding, wrap-aware sequences) and RTCP (sender/receiver reports, compound packets, NACK/PLI) parsers reject malformed input; received audio is attributed only through Speaking/Video SSRC mappings and DAVE-authenticated, with a 100 ms/32 KiB hold for unannounced SSRCs. Offline crypto/runtime regressions pass; official live voice interoperability remains pending.
- Mandatory DAVE v1 E2EE in `fastcord-media`, using `davey` pinned at 0.1.4 behind a session adapter; Voice Gateway JSON/binary opcodes 21–31, authenticated external Add/Remove proposal handling, cached-reference-only public commit validation before engine mutation, Welcome/commit recovery, epoch-aware transitions, and encrypted-only media transforms. Session channel moves issue fresh credentials carrying the destination channel so the DAVE MLS group ID stays aligned. Media stays fail-closed until authenticated keys and transition execution. Real MLS proposal/commit/welcome membership-churn, rekey, recovery, and driver RTP crypto tests pass; official Discord-client transition, membership, and bidirectional audio interoperability remains pending because no live account/session is available.
- Voice playback and app media bridge: authenticated per-SSRC packets feed a four-speaker bounded reorder/jitter stage (40 ms initial, 20–120 ms adaptive target), using Opus FEC for a proven one-frame gap and PLC otherwise, then float mixing and a final limiter. The app correlates explicit main-Gateway join requests with voice credentials, pumps microphone Opus frames into encrypted media, routes received DAVE-decoded packets into the engine, and tears down both sides on leave/reallocation/panel shutdown. A fake-device engine smoke test encrypts/decrypts four RTP SSRCs with AES-GCM, reorders and drops packets, verifies audible mixed output, and measures zero callback heap operations.
- M21 voice controls: the joined call panel exposes local mute/deafen, participant speaking state, and per-user 0–200% playback volume. Mute disables capture processing and sends the existing silence tail/speaking-off sequence; deafen disables playback and capture while preserving prior self-mute. Server mute/deafen are displayed as separate restrictions. User-keyed volume preferences are bounded, account-scoped, non-secret settings. Remote gains ramp independently per SSRC; speaking ownership updates replace the participant's old SSRC and speaking indicators release on a short event-driven delay.

Atomic controls updates preserve concurrent UI, server-restriction, and participant changes; received audio refreshes speaking release. - Private conversations (M13): virtualized DM/group-DM list is reconciled from each READY generation, READY_SUPPLEMENTAL, channel Gateway updates, and one account-scoped `GET /users/@me/channels`; list/open REST work stays worker-owned and nonblocking, and a newer READY cancels pending work and rejects stale generation-tagged completions while Gateway, voice, and user commands continue. Failed list fetches are retried on the next READY. Manually entered decimal recipient IDs issue a single `POST /users/@me/channels` (1–9 unique other-user IDs, 256 UTF-8-byte editor bound), never bulk discovery/creation. Recipient add/remove events decode their distinct payloads (remove carries a nested partial user), maintain the metadata byte ledger across recipient-vector growth, and removing the current user drops the private conversation. Reducer-validated private selection reuses bounded history, send, edit, delete, and reply behavior; private-message access remains server-authoritative and REST refusals stay visible.
- Attachment viewing and bounded CDN cache (M14): image attachments load a thumbnail on request ("Load preview"), and clicking the thumbnail opens a larger in-app view drawn over the account screen (Download, Open, Close); every attachment shows name, size, type, and dimensions with explicit Download (native save dialog, then a copy of the cached file) and Open (OS default application). Programs and scripts (`.exe`, `.bat`, `.ps1`, `.lnk`, `.sh`, …) can be saved but are never launched from the client. A separate credential-free HTTPS client fetches the CDN: signed query strings are sent exactly as Discord wrote them, redirects are followed by hand with every hop re-validated (HTTPS, no embedded credentials, at most five), and nothing but a plain `GET` leaves the client. A 403/404 asks the authenticated `POST /attachments/refresh-urls` for a new signed URL once and retries once. Cache identity is account/channel/message/attachment, never a URL. Compressed bytes stream to an account-scoped disk LRU shared at 256 MiB (atomic temp-file renames; partial downloads are neither evicted nor served, and crash leftovers are removed); previews are limited to 32 MiB, 16 Mpx, and 8192 px per side (checked from the header before any pixel allocation, scaled to the display box, first frame only) and other files to 64 MiB; decoded pixels live in a 12 MiB LRU shared with the iced texture handle; at most four fetches and two decodes run at once, all off the UI thread. Leaving the channel or scrolling the message out of the built rows cancels its work, and logout purges the account's files.
  Concurrent transfers reserve their full on-disk byte charge atomically before streaming, aborted transfers clean their partial files, and cancelled decode callers cannot free slots until their blocking decoder finishes. Windows native fixture acceptance exercised thumbnails, the larger view, an actual native-dialog save with matching file hash, OS-handler dispatch, and logout cache purge; official alt-account acceptance remains pending.
- Unicode/custom emoji and picker (M15): attributed Twemoji 17.0.3 assets with a versioned Unicode 16.0 index; grapheme-aware skin-tone, variation-selector, ZWJ and flag runs preserve their original text, while custom `<:name:id>` / `<a:name:id>` tokens use credential-free Discord PNG/GIF CDN assets with a text fallback for missing or unsupported data. Only actually visible emoji load, decoded pixels/animation frames are capped at 2 MiB, and the shared attachment decoder pool caps simultaneous decoding at two workers. Animation reuses immutable frame handles, ticks only while visible and active, and stops behind image/audio views, on focus loss and after scrolling out. Opening the picker keeps still-visible timeline emoji and budgets the picker's cells (2 MiB) in addition to the timeline's; GIF delays of 10 ms or less play at 100 ms like browsers.
  The virtualized picker searches names/aliases, groups categories, offers Unicode variants and the 32 most recent choices, and pages role/availability/external-permission-filtered guild emoji from the reducer. Choosing an emoji pastes exact source text at the composer's current cursor/selection; drafts, sends and the timeline's Copy text action keep it intact. No Nitro entitlement is invented: restrictions are explained and Discord rejections remain visible in the unsent-message strip. Live official-client rendering/send interoperability remains a manual acceptance item.
- Reactions (M16): messages keep an aggregate per emoji (Discord's count and whether the account reacted, never the reacting users, at most 32 distinct emoji per message) charged to the existing 16 MiB message budget. `MESSAGE_REACTION_ADD`/`REMOVE`/`REMOVE_ALL`/`REMOVE_EMOJI` apply to retained messages only: an echo of the account's own reaction is a no-op in either order with the REST answer, super (burst) reactions keep counts right without a paid-reaction UI, and an event for an uncached message allocates nothing (a history page in flight merely learns of it and is retried instead of trusted; a message created meanwhile takes it on its journaled copy). Chips under each message add the account's reaction or take it back on click (`PUT .../reactions/{emoji}/@me` and the user client's typed `DELETE .../reactions/{emoji}/0/@me`, both percent-encoded and pinned by `fixtures/rest/reaction-routes.json`); the worker checks the stored message and `ADD_REACTIONS`, keeps one request per reaction in flight (at most 16), draws it disabled until Discord answers, and reports a failure once as a fixed sentence without ever retrying. The hover React button opens the emoji picker for that message, and a right-click on a chip loads who reacted (first 25, only on request). Official-client interoperability in both directions and the real typed-delete response remain live checks.
- Microphone noise suppression Off/Light (M23, ADR 0004): `fastcord-audio::denoise` has one `Denoiser` trait with a bit-exact Off and Light = nnnoiseless 0.5.2 (RNNoise) on 480-sample blocks, scaled to its i16 range, with its documented artifact-laden first output replaced by silence and its one-block delay reported. The capture pipeline denoises mono 48 kHz blocks before the 20 ms Opus frames; Off, a muted microphone and a call that starts muted run no inference (a counter proves it), and mute or device replacement clears delayed audio so none leaks into the next talkspurt. Light is the default; the choice persists in `audio-devices.json` (older files stay Light), applies to a running call without reopening devices, and never touches stream/system audio. The settings dialog names the running engine only while a call has one (reset when the engine stops) and otherwise the saved choice, and scrolls instead of hiding its buttons. A synthesized, license-clean noisy-speech fixture (`fixtures/audio/`, regenerable, hash-checked) shows Light improving SI-SDR by +8.8 dB without clipping, also at +9 dB level; in release on the reference PC Light costs 0.31 % of one core (p95 0.04 ms per 10 ms block) and adds 10 ms. Releases ship `THIRD_PARTY_NOTICES.md` with the nnnoiseless/RNNoise license. Official-client call acceptance remains pending.
- High quality noise suppression (M23a, ADR 0004): DeepFilterNet 3 (`deep_filter` pinned to a git revision, tract runtime, bundled ~8 MB model) behind the same trait. Its non-`Send` runtime is built, run and dropped by one dedicated denoise thread that exchanges 480-sample blocks with the audio owner over bounded queues (80 ms cap, never waited on), so selecting it never stalls playback or capture: the previous engine keeps running until the model is built and has consumed its 30 ms lookahead (about 0.15 s after selection in release), and switching modes mid-call leaves no gap (frames stay contiguous; a slower engine repeats at most its extra delay, a faster one resumes exactly where the slower stopped, joined by a 2 ms continuity ramp). A worker that fails, panics or cannot keep real time hands the stream back to Light with a visible error (reselect to retry); at most one runtime exists at a time and switching away or ending the call drops it on its own thread. On the synthesized keyboard-clicks plus distant-voice fixture High quality beats Light by +6.6 dB SI-SDR and 20.8 dB more attenuation of speech-absent windows. In release on the reference PC: p95 0.35 ms per 10 ms block, 4.5-4.8 % of one core at real time, about +13 MB private memory (32-35 MB peak while building) that returns to within about 3 MB of the Light baseline without growing over twenty cycles, 30 ms algorithmic delay plus about 1 ms worker round trip. Releases also ship the DeepFilterNet and tract notices. Official-client call acceptance remains pending.
- H.264 RTP video transport (M25, `fastcord-media::video` and the voice driver): independent video-capable sessions advertise negotiated H.264 media/RTX directions and layer state, viewer opcode 12 and Media Sink Wants (opcode 15). Receiving supports byte-bounded per-SSRC reordering, single-NAL/STAP-A/FU-A depacketization, whole-frame DAVE authentication, keyframe gating, 10 ms NACK grace/RTT-paced retries, RTX, PLIs, receiver reports and 200 ms incomplete-frame expiry; unannounced SSRCs are held at most 100 ms/64 KiB. Sending seals complete frames before fragmentation into at most 1,200-byte datagrams, paces at most 100 ms, retains retransmissions at most 500 ms/2 MiB, and uses a fresh transport nonce for every retransmission. Reception reports, REMB and sink wants drive bounded bitrate changes, keyframe requests and pause/resume `VoiceEvent`s. The media crate never decodes/renders; M28 connects the app's watch decoder and renderer, while capture/send remains M29. Independent RFC 6184/4588 + AEAD vectors and real MLS/DAVE loss/reorder/RTX driver tests cover transport; official-client interoperability remains pending.
- AV1 receive (M26: `fastcord-media::video::av1`, the voice driver, `fastcord-video::av1`, and app stream workers): AV1 is advertised decode-only with payload type 101/RTX 102; the bounded AOM RTP depacketizer handles aggregation, fragmented OBU headers/lengths, strict malformed input, N-keyframe gating, RTX/loss repair, and per-SSRC codec changes. DAVE seals complete temporal units before fragmentation, preserving authenticated OBU headers and non-final lengths; sizes are restored only after decryption. dav1d 1.5.4 is statically built from a pinned, hash-verified source archive with the target C compiler (portable C, no assembler, network, DLL, or FFmpeg); decoding is lazy, input capped at 2 MiB, native pictures at 4096 per side/4096x2304 pixels and 256 MiB retained allocation. Borrowed 8-bit luma avoids a copy; other supported YUV layouts/depths convert to NV12, RGB/identity streams are refused, and failed native contexts are discarded. Independent RTP/AEAD vectors, genuine libaom streams checked against its reference decoder, malformed/damage sweeps, real MLS/DAVE driver tests, and bounded threaded-decoder tests cover the path. Official-client AV1 interoperability remains pending (U4).
- Video playback in iced (M28): explicit Watch/Show/Stop controls for Go Live offers in the parent voice channel; a latest-frame lease slot and coalesced, visibility-only subscription, with no fixed redraw timer or video pixels in UI messages. The dedicated worker now decodes H.264 through Media Foundation/VideoToolbox as well as AV1 through dav1d; hiding the pane, focus loss/minimize, or an occluding view suspends decode and releases references, and resume requests a fresh keyframe. Three recyclable decoded buffers are capped at 48 MiB of owned capacities; wgpu reuses one Y/UV texture pair and converts NV12 with preserved color matrix/range and sample aspect ratio. The no-adapter tiny-skia path converts directly to leased BGRA off the UI thread and blends borrowed pixmaps without per-frame image encoding/handles. Stop watching, logout, stream end, and parent-voice changes release playback state without replacing the parent voice connection. Deterministic logic/metadata tests and real native fixture-window checks are documented in `docs/TESTING.md`; live official-stream acceptance remains pending.
- One web-client identity for the whole run (ADR 0005): the profile is built once at login — `client_build_number` fetched from discord.com web assets there rather than at every Gateway start, plus the per-launch identity (`client_launch_id` and `launch_signature` are two fresh UUIDv4s, `client_app_state` is `"focused"`) — and is reused unchanged by every Identify and every reconnect. The same profile now identifies the REST client: `x-super-properties` carries the identical properties JSON base64-encoded, alongside its user agent, `x-discord-locale`, and the client fingerprint constant, so the Gateway and API halves of a session never disagree about who the client is. The credential-free CDN client is untouched and still sends none of these. The launch identity is generated once per launch, never per Identify; the desktop-only `native_build_number` is still not sent.
- Windows screen share (M29): the Go Live row offers **Share screen** while joined to a guild voice channel. A picker lists the machine's screens and the shareable top-level windows (visible, titled, not minimized or suspended, never fastcord's own); choosing one starts Windows.Graphics.Capture on a dedicated owner thread first, and only when the OS accepted it is the stream created (opcode 18), so a refused permission or a vanished window never creates a stream. Pictures are scaled to fit 1280×720 (never upscaled, even edges) and converted to BT.709 NV12 by a D3D11 video processor (CPU converter fallback), paced to 30 fps on capture timestamps, and encoded by Media Foundation (hardware first, Microsoft's software transform as the fallback, falling back to software if a hardware encoder fails while running). The stream's own voice connection offers one H.264 screen layer; nothing is encoded until the server selected H.264 for us, keyframes follow PLI/FIR (answered immediately even for a static screen, which is also resent about once a second), the encoder bitrate follows the transport's congestion feedback and the server's sink wants (a paused layer slows capture to one picture a second), and a refused unit restarts the stream at a throttled keyframe. Resizing a shared window reopens the encoder only after the new size held for 300 ms; closing the source, a permission refusal, an encoder failure, a stream failure, STREAM_DELETE (with Discord's reason), Stop sharing, and leaving or moving the voice channel all stop the capture thread (joined, bounded) and delete the stream when it exists, without touching the parent voice connection. The capture border and cursor stay at the OS defaults. Other platforms report that capture is not implemented yet. Hardware tests on Windows (AMD Radeon RX 9070 XT, Microsoft software encoder) captured a real window and display, round-tripped the encoded units through the decoder and compared the painted colors; official-client viewing at 720p30 and microphone continuity during a share remain live acceptance (Refs #29).

### Fixed
- REST identity headers now derive the user-agent and locale from the same `ClientProperties` used by Gateway Identify and `x-super-properties`, instead of hardcoding Windows/en-US. The stable-per-build fingerprint has one definition in the versioned profile module; headers remain prebuilt once per REST client. Offline fixtures cover Windows, macOS, Linux, and a non-en-US locale, and malformed identity headers fail with secret-safe configuration errors (Fixes #50).
- The bundled dav1d build enables `_DARWIN_C_SOURCE` on macOS so Darwin's BSD typedefs remain visible with strict C11/POSIX settings, fixing Apple Silicon and Intel codec compilation (Fixes #41).
- Linux release builds install `libasound2-dev` before compiling, matching CI's minimal ALSA-header setup for cpal and preserving SHA-pinned actions (Fixes #42).
