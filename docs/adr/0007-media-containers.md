# ADR 0007: MP4 and WebM demuxing for inline attachment playback

Status: accepted (2026-10-20)

## Context
Issue #74 shipped an inline Ogg Opus player; video and other audio stayed Download/Open-only because ADR 0001 rules out FFmpeg and the build had no container demuxer. Issue #116 adds MP4 (ISO BMFF, QuickTime) and WebM/Matroska so that the attachments people actually post (phone and screen-recorder clips, browser recordings) can play, using only codecs the client already ships or the OS provides: H.264 (Media Foundation, VideoToolbox, VA-API/OpenH264), AV1 (bundled dav1d) and Opus (libopus).

Candidates for the container layer:

- **`mp4` / `re_mp4` crates:** read the whole sample table into per-sample structs with their own allocation policy, expose no sample budget, and parse boxes we do not need; `mp4` also pulls extra dependencies. Bounds would have to be added around them.
- **`matroska-demuxer`:** reasonable, but its block iteration reads through its own buffering and it does not give a pre-built, budgeted sample index, which seeking needs.
- **`symphonia`:** a large decoder family; only its container parts would be used and its codec features are what ADR 0001 keeps out.
- **A minimal hand-written, bounded parser:** the boxes and elements needed are few and well specified.

## Decision
Write the demuxers in `fastcord-video` (`container`: `mp4.rs`, `matroska.rs`), with no new dependency. The module indexes a file once without touching media data and then reads single samples on demand:

- Index entry per sample: file offset, size, presentation time in ms, keyframe flag (24 bytes). At most 400 000 samples per file (9.6 MB worst case; typically a few hundred kB), each sample at most 8 MiB, metadata (`moov`, `Info`, `Tracks`) at most 16 MiB; everything is checked against the file length and the enclosing box before use, counts are checked against the bytes actually present before allocating, and a hostile or truncated file yields an error rather than a panic (tests flip bytes and truncate at every offset).
- MP4: `ftyp`/`moov` found by walking top-level boxes with seeks (so `moov` may follow `mdat`); `tkhd`, `mdhd`, `hdlr`, `stsd` (`avc1`/`avc3`+`avcC`, `av01`+`av1C`, `Opus`+`dOps`, `mp4a` recognised only to be skipped), `stts`, `ctts` (v0 and v1), `stss`, `stsz`, `stsc`, `stco`/`co64`, and the first non-empty edit of `elst` (the start offset that cancels a composition delay). Fragmented MP4 (`mvex`/`moof`) is refused.
- Matroska/WebM: EBML header (DocType `webm`/`matroska`), `Segment` of known or unknown size, `Info`, `Tracks`, `Cluster` (known or unknown size), `SimpleBlock`, `BlockGroup`/`Block` with `ReferenceBlock` for delta frames. Blocks are indexed by reading their first bytes only. Lacing and `ContentEncodings` are refused (a laced audio track is dropped, leaving the video silent).
- Supported tracks: H.264 (`avcC`, converted to Annex B with SPS/PPS before keyframes), AV1 (`av1C` sequence header placed before keyframes; samples are already sized low-overhead OBUs), Opus in 20 ms packets, mono or stereo. The first video track decides: any other video codec (HEVC, VP8, VP9, MPEG-4) is refused with a clear message and stays Download/Open. An unsupported audio track (AAC, MP3, FLAC, multi-frame Opus) leaves the video playing silently with a visible note.
- Decoding stays in the existing codec traits; the audio goes through the same `FilePlayer` as Ogg Opus (now over a `PacketSource` trait), which is the master clock; video is decoded on its own worker and presented through the latest-frame lease (`playback::Session`).

## Consequences
- No new crate, license notice or `THIRD_PARTY_CRATES.md` change. The parsers are ours to maintain; the fixtures are generated by `fixtures/video/gen_container_fixture.py` from the committed elementary streams and checked against the libaom-derived AV1 pixel oracle.
- **AAC is not decoded in this change.** The OS decoders (Media Foundation AAC, AudioToolbox) need new `unsafe` bridges plus an audio test fixture that cannot be produced without an AAC encoder in the repository's toolchain; the most common phone clip (H.264 + AAC) therefore plays without sound and says so. This is a follow-up, not a decision against AAC; Linux has no OS AAC decoder and will stay silent for AAC regardless.
- Seeking goes to the keyframe at or before the target, decodes forward and shows the last picture at or before the target; audio seeks to the packet. Audio is the clock; the estimate is accurate to about 100 ms.
- RAM budget while playing: index + 2 x 8 MiB working buffers + at most 2 pending pictures + the 3-buffer / 48 MiB frame pool + the audio engine's bounded rings. Paused and finished players block with no timers.

## Rejected
- **FFmpeg or any GPL/LGPL codec bundle:** ADR 0001.
- **Playing while downloading (progressive/fragmented MP4, live WebM):** the file must be in the attachment cache first (64 MiB ceiling), as for Ogg.
