# Protocol notes

Wire-level behavior fastcord implements or depends on, with its evidence status. Design decisions live in `docs/SPEC.md` and `docs/adr/`; this file records what the code actually sends and expects. Community-documented behavior (userdoccers, `discord.py-self`) is a compatibility dependency, not a guarantee.

## Main Gateway (milestone 6)

Implemented in `fastcord-discord::gateway`. One `Gateway` handle is one account's connection lifecycle; a Tokio task owns the socket and hands ordered `GatewayEvent`s to the single consumer (the reducer of milestone 7).

### Connection and compression
- URL from `GET /gateway` (cached; asked again only after a failed connect), then `?v=10&encoding=json&compress=zlib-stream`. Only `wss://` hosts on `discord.gg` are ever connected to or sent the token; anything else (including a hostile `resume_gateway_url`) is refused, a hostile resume URL falling back to the discovered one.
- One persistent zlib context per connection (`flate2`, pure Rust). WebSocket message payloads accumulate until the `00 00 ff ff` sync-flush suffix, which is looked for at the end of the accumulation, so a message boundary may fall anywhere (even inside the suffix). The dictionary is never reset on a live connection; a new connection starts a new one. Identify's `compress` stays `false`.
- Safety ceiling: 16 MiB per decompressed event, and 16 MiB of compressed bytes accumulated toward one. Exceeding it ends in `Stopped(EventTooLarge)` (a diagnosable startup error, never silent truncation). Decompression is incremental, so a bomb is stopped before it is allocated. Scratch above 256 KiB is released as soon as the event has been handled.
- zstd-stream is intentionally not implemented (SPEC §4.1).
- Outbound frames are capped at 15 KiB locally, and a sliding window counts the 120-frames-per-60-seconds send ceiling; Identify, Resume, and heartbeats are always sent but counted, and server heartbeat requests beyond the ceiling are ignored.

### State machine
`Connecting -> AwaitHello -> Identifying | Resuming -> Ready -> Reconnecting -> Connecting …`, plus two terminal states: `AuthenticationRequired` (back to login) and `Stopped(reason)` (conditions reconnecting cannot fix).

- HELLO's interval is clamped to 1 s–5 min; the first heartbeat is offset by `jitter * interval`; every heartbeat carries the last delivered dispatch sequence (or `null`); server heartbeat requests (op 1) are answered immediately. A heartbeat interval that passes without an ACK ends the connection (`Reconnecting(HeartbeatTimeout)`); it is never left displayed as connected. While events are waiting for a slow consumer the task is not reading, so missing ACKs are not held against the server.
- Resume (op 6) uses the READY `session_id`, the last delivered sequence, and the READY `resume_gateway_url`. A Resume is never followed by an Identify on the same connection. Replayed dispatches with a sequence at or below the last delivered one are dropped before they reach the consumer, so replay cannot duplicate a message, a reaction, or a deletion.
- Reconnect delay, never zero: a connection that stayed Ready for 30 s waits a random 1–5 s before reconnecting; otherwise `min(60 s, 1 s·2^(n-1))` with jitter between half and all of it. Non-resumable Invalid Session waits a random 1–5 s. Connect failures keep the session (a network outage says nothing about it); only the server ends it.
- Reconnect limits (in memory, per Gateway task): Identifies (not Resumes) are counted in a rolling 24 h window and a 21st is not sent; 10 consecutive failed connection attempts (discovery, connect, or a connection that dropped before staying Ready for 30 s) also stop. Both end in `Stopped(IdentifyBudget)` / `Stopped(ReconnectFailures)`, and so do two consecutive `403` answers to `GET /gateway` (`Stopped(DiscoveryForbidden)`; Cloudflare or a ban: asking again does not help; a single 403 is retried with the normal backoff). The app shows "Disconnected" with the reason and a Reconnect button; Reconnect starts a new Gateway task, which resets every counter. `401` still ends in `AuthenticationRequired`.
- Clean close: Quit sends close code 1000 and waits up to 2 s for the connection task before the process exits (`GatewayCloser`); dropping the handle (logout, account switch) closes with 1000 too. A forced kill closes nothing.
- Op 7: reconnect and Resume. Op 9: `d = true` Resumes; `d = false` drops the session and Identifies after 1–5 s. Five consecutive Invalid Session answers to Identify end in `Stopped(IdentifyRejected)`: the profile or account is being refused without a close code and fastcord does not loop on it.

| Close code | Meaning here |
|---|---|
| 4004 | `AuthenticationRequired`: stops all attempts and all authenticated work of the account |
| 4003, 4007, 4009, 1000, 1001 | session is gone: reconnect and Identify |
| 4001, 4002, 4010–4014, 4016 | `Stopped(Rejected(code))` (our payload or configuration is refused; retrying cannot help) |
| 4015 | `Stopped(TooManySessions)` |
| anything else (4000, 4005, 4008, abnormal closure, no code) | reconnect and Resume |

A 401 on `GET /gateway`, or on any other request of the account (`RestClient::authentication_required`), also ends in `AuthenticationRequired`. READY with a non-empty `required_action` is delivered, then ends in `Stopped(ActionRequired(code))`. No challenge is ever completed or bypassed.

Dropping the `Gateway` handle closes the socket with code 1000, which ends the session on Discord's side.

### Capabilities
Identify's `capabilities` is derived from named flags, never a magic number: `LAZY_USER_NOTES` (1<<0), `NO_AFFINE_USER_IDS` (1<<1), `DEDUPE_USER_OBJECTS` (1<<4), `PRIORITIZED_READY_PAYLOAD` (1<<5, requires dedupe), `PASSIVE_GUILD_UPDATE_V2` (1<<14) = **16435**. No intents. Not enabled because their payloads have no handler: protobuf user settings, reaction debouncing, client-state v2, versioned read states and guild settings, token refresh, auto call/lobby connect, channel obfuscation. The empty `client_state.guild_versions` is sent on a cold login; the 2026-10-25 target adds a bounded persisted map for warm logins (see below).

### Identify profile (ADR 0005, target revision 2026-10-25)

The code sends the official desktop (Electron) profile. It is built once at
login and reused by every Identify and REST request, except the 30-minute
heartbeat and the installation id learned after READY (both still open).

#### Version chain

`client_version` and `native_build_number` come from the update manifest
(`https://updates.discord.com/distributions/app/manifests/latest` with
`channel=stable`, the host `platform`, `arch` and a client-generated
`install_id`: `full.host_version`, `metadata_version`); `client_build_number`
comes from `https://discord.com/app`; the Electron and Chromium versions are
not in the manifest and are a pinned pair reviewed when the host version
changes. A CI or scheduled check fetches the manifest and `/app`, asserts the
user-agent/native/build consistency, and fails when the pin is stale; it does
not download Discord.

Implemented by `gateway::resolve_versions`, once per process (fake mode: the
bundled values): `GET` the manifest with `channel=stable`,
`platform=win|osx|linux`, the build's `arch` and a fresh `install_id` per
process, in parallel with `/app`; at most 256 KiB, no redirects, 10 s.
`full.host_version` `[a, b, c]` becomes `a.b.c`; `metadata_version` must be in
1000–9999999. The host version and native build come from the same manifest or
are both bundled (Windows x64 1.0.9265, Windows arm64 1.0.57, macOS 0.0.419,
Linux 1.0.166; native 96160; web build 649389, all observed 2026-10-25). The
pinned pair is Electron 42.11.15 / Chromium 148.0.7778.280, read from the
installed stable Windows host 1.0.9265 (`PIN_HOST_VERSION`). The check is
`live_version_chain_matches_the_pin`, daily in
`.github/workflows/identity-pin.yml`; it fails when the stable Windows x64
host differs from `PIN_HOST_VERSION`, and an offline test keeps the bundled
Windows host equal to the pin.

### READY normalization
Decoded straight from the borrowed event text into typed structs that name only the fields used, so unknown fields are skipped as they are read and no untyped JSON tree is built; READY's arrays stream element by element.

- `users` (deduplicated, each once, current user included) plus ID references: guild members carry `user_id`; DMs and group DMs carry `recipient_ids`. A payload that still embeds user objects (no dedupe) normalizes to the same shape.
- `merged_members` is parallel to `guilds` (an unavailable guild's slot is empty). A length mismatch is `Stopped(MalformedReady)`: attaching members by position would silently be wrong.
- Guild fields come from the guild object or from `properties` (client-state-v2 shape). Channels learn their `guild_id`. Unknown channel types are preserved. Null arrays mean empty. Partial user objects (missing `username`) are accepted.
- Unavailable (outage or geo-restricted) guilds are listed by ID only.
- READY_SUPPLEMENTAL: per guild `voice_states` and the remaining members (from its own `merged_members`, parallel to its own `guilds`), plus `lazy_private_channels`. Malformed ones stop like malformed READY.
- PASSIVE_UPDATE_V2 is decoded and applied by the bounded reducer (milestone 7): channel unread markers, voice state changes/removals, and normalized members.
- Live dispatch events keep their wire shape (`MESSAGE_CREATE/UPDATE/DELETE`, `GUILD_CREATE/DELETE`, `CHANNEL_CREATE/UPDATE/DELETE`); a payload that does not decode is skipped (its sequence still counts), unknown event names are consumed. `Debug` of events names the event only, never content or URLs.

### Consumer queue
Events pass through a byte-bounded queue (2 MiB budget, 256 events): each reserves about twice its frame size and returns it when taken. A slow consumer stops the task from reading the socket instead of growing memory; nothing is dropped, ordering is kept, and heartbeats continue. An event larger than the whole budget (a big READY) is queued alone. Events already decoded are always delivered before a reconnect, so the Resume sequence equals what was delivered.

### Voice state (milestone 17)
Opcode 4 (Update Voice State) is sent through `Gateway::voice_state()` (`VoiceStateControl`): `{"op": 4, "d": {"guild_id": "<id>"|null, "channel_id": "<id>"|null, "self_mute": bool, "self_deaf": bool, "self_video": false}}`, where `channel_id: null` leaves voice and `guild_id: null` addresses a private call. The consumer sets one wanted state; the connection task sends it only while Ready (after READY or RESUMED, never while Identifying or Resuming) and only when it differs from what this session last sent. Rapid requests coalesce and the newest wins. What was sent survives reconnects: after RESUMED only a state changed while disconnected goes out; a fresh READY starts with nothing sent, so a wanted join is sent again and a wanted leave is not sent at all. Opcode 4 counts against the 120-per-60 s ceiling and may use the control reserve but never the slots kept for a full window of heartbeats; when only those are left it is deferred until the window frees a slot. The current shape has no `self_stream`; the 2026-10-25 target adds it and sets it while a Go Live stream is live (B2 in `docs/IDENTITY_AUDIT.md`).

VOICE_SERVER_UPDATE (`{token, guild_id, channel_id?, endpoint}`) is decoded for the voice layer and ignored by the reducer. A null `endpoint` means the voice server is being reallocated: the voice connection disconnects and waits for the next update. The token is redacted from `Debug`, zeroed on drop, and never logged.

## REST client identity (ADR 0005)

`RestClient` carries the same `ClientProperties` the Gateway Identifies with, so both halves present one consistent official-client identity (ADR 0005 revision 2026-10-25). The identity headers are encoded and validated once at REST client construction, then installed as default headers for every authenticated request. The current build uses `/api/v10` and only the headers below; the target uses `/api/v9` and the desktop (Electron) surface listed after the bullets.

- `Authorization: <raw user token>` (no `Bot `/`Bearer ` prefix, marked sensitive).
- `x-super-properties`: the `ClientProperties` JSON, standard-base64 encoded — the exact same object Identify sends under `properties`, with the current `client_heartbeat_session_id`.
- `user-agent`: the profile's `browser_user_agent` (the Electron UA).
- `x-discord-locale`: the profile's `system_locale` until the account locale is known, then the account's client locale.
- `x-fingerprint`: the current build omits it. The target generates one through `GET /experiments` for the unauthenticated login flow; a captured value is never reused across installations/accounts.
- **Target additions:** `X-Installation-ID` (the persisted installation id), `x-discord-timezone`, `sec-ch-ua`/`sec-ch-ua-mobile`/`sec-ch-ua-platform` as Electron sends them, `sec-fetch-site`/`mode`/`dest`, `accept-language`, `accept-encoding`, `origin`/`referer` on writes, and a bounded cookie jar for `discord.com` sent on REST and WebSocket handshakes.

Offline consistency tests use `fixtures/rest/client-identity-profiles.json` for Windows, macOS, Linux, and a non-en-US locale, comparing REST user-agent/locale and decoded `x-super-properties` against the actual Gateway Identify properties.

The credential-free CDN client (`fixtures/`, `assets/`, signed attachment URLs) is a separate `RestClient`-independent HTTP client with no default headers and no `Authorization`, and never receives these headers.

## Lazy subscriptions and member lists (milestone 7)

Implemented in `fastcord-discord::gateway::subscription` (what is sent) and `fastcord-discord::state` (what is kept). Evidence: the field set and operation semantics below come from community documentation (`discord.py-self`'s `GuildSubscriptions`/`types/gateway.py`, Userdoccers' opcode table) and have **not** been captured from a live session; risk **U2** stays open until the checks in `docs/TESTING.md` have run. `fixtures/gateway/subscriptions_navigation.json` records exactly what fastcord sends for a two-guild navigation; the `member_list_update_*.json`, `voice_state_update.json`, and `guild_member_update.json` fixtures are shaped after the documented payloads with fabricated IDs.

### Opcode 37
`{"op": 37, "d": {"subscriptions": {"<guild_id>": {...}}}}`. Opcode 14, the deprecated predecessor, is never sent and there is no fallback to it; a payload that cannot fit stops with `SubscriptionTooLarge` rather than being silently dropped. Each guild entry always carries every field:

| Field | Sent | Meaning |
|---|---|---|
| `typing` | `true` for a wanted guild, `false` to release it | In the community documentation this flag is what subscribes the connection to the guild (it is how the guild's other fields start to take effect); fastcord sets it for that reason only. TYPING_START is never decoded or shown. |
| `threads`, `activities`, `member_updates` | always `false` | Not MVP features. |
| `members` | user IDs, at most 200 per guild | Individually requested members (visible authors, reply targets, voice participants, permission computation). |
| `channels` | `{channel_id: [[start, end], ...]}` | Member-list ranges of the visible member sidebar only. Empty for voice-only subscriptions and milestone 8 navigation (no member sidebar is displayed). |
| `thread_member_lists` | always `[]` | Not MVP. |

Because it is not established whether an omitted field means "unchanged" or "cleared", every field of every changed guild is sent explicitly: the result is the same under either reading. A guild is released by sending it with `typing: false` and everything else empty, never by leaving it out.

What is subscribed: the selected guild and the guild of the active voice channel, nothing else. When a member sidebar is visible, ranges are the 100-row blocks touched by its viewport, at most three in total; `select_channel` initially requests `[0, 99]`, and scrolling releases obsolete blocks. Milestone 8 clears the member viewport and only requests the current user's member when needed for permissions. Navigating changes only what differs, in one frame, and releases the old guild explicitly. Rapid changes are coalesced: the first change opens a 250 ms window and everything changed within it is sent as one frame; setting what is already sent sends nothing.

Desired state (`SubscriptionTarget`, set through `Gateway::subscriptions()`) is kept apart from the last transmitted session state. A new READY clears that ledger; a RESUMED retains it, explicitly releases guilds removed while disconnected, and resends complete wanted entries because server-side retention is not established. Nothing is sent before READY/RESUMED. Subscription frames count against the 120-per-60 s ceiling; scheduled heartbeats have priority and optional traffic reserves enough slots for HELLO's heartbeat interval plus 20 other control frames. When only the reserve is left, sending is deferred (retried every 5 s) and the latest target wins. Frames are split before the 15 KiB outbound limit; one guild at its caps is about 5 KiB.

### GUILD_MEMBER_LIST_UPDATE
`{id, guild_id, member_count, online_count, groups: [{id: "online"|"offline"|role_id, count}], ops: [...]}`. `id` is `everyone` or a hash of the channel's permission overwrites; the event does not name a channel, so lists are keyed by `id`. Operations address positions in the **whole flattened list** (section headers count as rows):

- `SYNC {range: [s, e], items}`: the rows of `s..=e` (fewer items than the span means the list ends there).
- `INSERT {index, item}` / `DELETE {index}`: insert or remove one row; every later row, known or not, shifts by one.
- `UPDATE {index, item}`: replace one row.
- `INVALIDATE {range}`: the server no longer maintains `s..=e`; those rows are forgotten, nothing shifts.

An item is `{group: {...}}` or `{member: {user, roles, nick, ...}}` (presence is ignored). Since only subscribed ranges are described, rows are held sparsely as segments of known rows; an INSERT or DELETE moves later segments, touching segments join, and nothing outside what the server told us is invented. A row that cannot be read keeps its index (`Unreadable`); an operation name this client does not know empties the list's rows (counts kept) because it can no longer be trusted. Positions past `u32::MAX` are dropped, and a list never holds more than 1,000 known rows.

Member lists are accepted only for the selected guild and the selected channel's expected list ID; navigation releases old rows and late updates for another permission list are ignored. The expected ID follows [discord.py-self's `GuildChannel.member_list_id`](https://github.com/dolfies/discord.py-self/blob/master/discord/abc.py): `everyone` if the guild's default role grants VIEW_CHANNEL and no overwrite denies it, otherwise the unsigned MurmurHash3 x86-32 (seed zero) of lexically sorted `allow:<id>`/`deny:<id>` view overwrites joined by commas. An incremental event cannot introduce a list before its first SYNC. Rows outside the current subscription ranges are released on viewport changes.

### Events the reducer consumes
READY and READY_SUPPLEMENTAL (replace/extend state; a READY drops everything the session derived), GUILD_CREATE (a guild already held keeps its members, voice, and unread markers), GUILD_DELETE (outage keeps only the ID), CHANNEL_CREATE/UPDATE/DELETE (DM recipients move to the user table), MESSAGE_CREATE (only the channel's last-message marker, never backwards), PASSIVE_UPDATE_V2 (unread markers, voice states, members of guilds not subscribed; ignored for guilds not held), GUILD_MEMBER_ADD/UPDATE/REMOVE, VOICE_STATE_UPDATE (guild voice only), GUILD_MEMBER_LIST_UPDATE. Missing member/user fields in GUILD_MEMBER_UPDATE preserve old values; explicit null/empty fields clear them. READY's deduplicated users remain available until supplemental members acquire their references. Gateway sequence filtering discards replayed duplicates before the reducer.

### Retention (SPEC §4.5)
One `Store` is the only writer. Sizes conservatively account for owned String/Vec capacities, hash-table allocation slack, and auxiliary identity/focus tables against a 12 MiB budget. Channel metadata uses compact sorted vectors rather than large hash-table capacity overhead. Above the budget the store sheds toward 80%: nonvisible lists, unreferenced users, then unreferenced members (oldest write first, a user goes with its last member); optional maps are compacted so eviction releases backing memory. Identity and permission data, the current user's own member, voice/requested members, and visible rows are not selectively shed. If required data alone cannot fit, the reducer releases the account store and latches `limit_exceeded()`; the app drops the Gateway and displays terminal `StateTooLarge`. It never displays a silently truncated account as connected.

### Not established (verify live, see docs/TESTING.md)
Whether `typing: true` is really the subscription flag and whether it is needed for `channels` to take effect; whether omitted fields clear anything (irrelevant to correctness, since none are omitted); which subscriptions the server applies implicitly before any opcode 37; whether subscriptions survive a Resume; whether a voice-guild-only subscription keeps voice states fresh while another guild is selected (the reducer handles VOICE_STATE_UPDATE for it and PASSIVE_UPDATE_V2 for the rest); the real member-list ids for channels with overwrites.

## Guild/channel navigation (milestone 8)

Navigation is a reducer-owned ID selection, not a new REST discovery path. READY and the existing guild/channel/member events provide the metadata; GUILD_ROLE_CREATE/UPDATE/DELETE also update the retained role table and effective permissions. Guild outages remain visible but disabled. Text, announcement, and voice channels with VIEW_CHANNEL appear in deterministic category/position/ID order; categories are labels, not openable channels. Voice rows without CONNECT are visible but disabled. Opening a voice row selects it without sending a voice join.

Permission checks use the model's owner/admin and everyone/role/member overwrite algorithm. Incomplete owner/member/role metadata fails closed (a positively identified guild owner can bypass); an omitted or null member `roles` field is not proof of an empty role set. Active communication timeouts remove voice/send permissions. Changes reconcile the selected IDs and remembered channel per joined guild; hidden, removed, or newly forbidden channels cannot remain open. Selection is revalidated on the reducer even if a click originated in an older UI window.

The UI receives only two bounded row windows (at most 128 rows each, names capped to 256 UTF-8 bytes) and the selected channel's permission summary. Navigation controls are watch-coalesced; replaceable snapshots occupy one shared latest slot and at most one unconsumed notification. Fixed 32-pixel rows use exact top/bottom spacers and one viewport of overscan on each side, never one widget per cached channel. No full Store clone reaches the UI, no periodic redraw is subscribed, and no navigation action fetches message history (history paging is milestone 9).

## Message history (milestone 9)

Implemented in `fastcord-discord::history` (the request) and `fastcord-discord::message_store` (what is kept). Evidence: route and field shapes come from Discord's public API documentation and community user-client documentation; `fixtures/rest/channel-messages.json` and `fixtures/gateway/message_delete_bulk.json` are sanitized, fabricated-ID payloads in those shapes. No live capture exists yet (see `docs/TESTING.md`).

### Request
`GET /channels/{channel}/messages?limit=50[&before={id}|&after={id}]`, `Priority::UserRead`, through the shared scheduler (major parameter = channel). Exactly one cursor at most; `around` is a reply-jump feature (milestone 12). The response is decoded with a hard limit of 50 records while streaming, newest first as sent. A message of another channel or on the wrong side of the cursor makes the whole page `InvalidJson`; nothing is partly trusted. 403 and 404 map to the scheduler's `PermissionDenied`/`ResourceGone` and are shown as fixed, secret-free text with a Retry action; nothing is retried automatically.

### When a page is requested
Only for an explicit reason, for the channel the reducer validated as selected, readable (`READ_MESSAGE_HISTORY`) and text/announcement: opening it (`Latest`), scrolling within one viewport of the retained start (`Before(oldest retained)`), scrolling to the retained end while newer messages were evicted (`After(newest retained)`), "Load older", "Jump to latest" when the newest end is not retained, and Retry. A full page cannot prove the start of history, so one more empty page is requested before "older" ends. Navigation alone never fetches history; a failed page stops paging until Retry. Closing or losing the channel cancels the request and drops its bodies.

### Gateway events
`MESSAGE_CREATE`, `MESSAGE_UPDATE`, `MESSAGE_DELETE`, and `MESSAGE_DELETE_BULK` (`{ids, channel_id, guild_id}`) apply to retained messages only. A create outside the retained live edge is dropped (the cache refetches on demand); a partial update merges field by field (absent means unchanged, an explicit `null` edited timestamp clears it); a delete removes the row and an unretained one is a no-op. While a page request is in flight a bounded journal (at most four requests, 512 IDs) records what the Gateway changed: deleted messages are removed from the REST page, edited ones win over the older REST copy, creates the response predates are replayed, and an update to an uncached message, or journal overflow, makes the response stale (nothing changes, the same request may be repeated). A READY drops every body.

### Retention
The store holds one contiguous run per channel with a coverage ID range. Over 500 messages the end farthest from the reader's anchor goes (the live end is kept while the reader is at the bottom). Over 2,000 messages or 16 MiB the least recently used channel sheds first. Sizes are capacity-based and include the Arc header. A body larger than 512 KiB is rejected and reported, never truncated. UI snapshots hold at most 512 KiB of bodies (window spacers are recomputed when trimmed), and the layout index holds only numbers: at most 500 rows, two width buckets each.

## Sending messages (milestone 10)

Implemented in `fastcord-discord::send` (the request and failure classification), `fastcord-app::outbox` (operations and reconciliation), and `fastcord-app::composer` (the editor). Evidence: field semantics come from Discord's public "Create Message" documentation (`nonce` is an integer or a string of up to 25 characters; with `enforce_nonce` Discord checks the nonce for uniqueness among the author's messages of the past few minutes and returns the existing message instead of creating another) and community user-client documentation; `fixtures/rest/message-create-request.json` and `fixtures/rest/message-create-response.json` are sanitized, fabricated-ID payloads in those shapes. No live capture exists yet (see `docs/TESTING.md`).

### Request
`POST /channels/{channel}/messages`, `Priority::UserWrite`, through the shared scheduler (major parameter = channel), with exactly this body:

```json
{"content": "…", "nonce": "1290000000000000001", "enforce_nonce": true, "tts": false, "flags": 0,
 "allowed_mentions": {"parse": ["users", "roles"]}}
```

- `content`: the draft with surrounding whitespace trimmed, interior text as written. Empty text or more than 4,000 characters is refused locally; whether 2,000 (no Nitro) applies is left to Discord, whose 400 is shown as a failed send.
- `nonce`: a snowflake-shaped `u64` sent as a decimal string (at most 19 characters): milliseconds since the Discord epoch in the high 42 bits, 22 bits of operating-system entropy below, strictly increasing within the process. It is chosen once per operation and reused by every explicit retry.
- `allowed_mentions` is always sent, never left to Discord's default: `users` and `roles` parse, `everyone` (which covers `@here`) only when the user ticked "Allow @everyone and @here to notify" for this message. The choice resets after every send and on every channel switch. Replies add `replied_user` in milestone 12.
- No attachments, embeds, stickers, components, or TTS.

### Outcomes
The transport never re-posts. A `429` proves nothing was created, so the scheduler waits as told and posts again. Every other outcome is classified once:

| Outcome | Meaning | Shown as |
|---|---|---|
| 2xx with a decodable message of the channel | created | message in the timeline |
| connect failure, local validation, stopped account, 4xx (400, 401, 403, 404, 413, …) | definitely not created | "Not sent" with Retry, Edit, Discard |
| timeout after connecting, broken or unreadable response, oversized or undecodable 2xx body, 5xx | may have been created | "Not confirmed" with Retry send, Discard |

A 401 also stops the account and returns to login, as everywhere else.

### Error bodies
Discord answers a refused request with JSON like `{"code": 40002, "message": "You need to verify your account"}`. For message creation (`RestRequest::with_error_detail`) a 403 or other 4xx reads at most 4 KiB of that body and keeps only the numeric `code` and a `message` made safe (control characters become spaces, words containing `@` or longer than 32 characters are dropped, 96 bytes at most) as `RestError::Refused`. An unparsable, oversized or code-less body keeps just the status and the old fixed sentences. Mapped codes: 50013 and 50001 (permission/access), 50007 (user cannot receive messages), 40002 (verify the account), 40003 (opening DMs too fast), 40004 (sending temporarily disabled), 20016 (slowmode); 50035 keeps the 400 wording. The login (`POST /auth/login`) 400 body also nests `errors.login._errors[] = {code, message}` (for example `ACCOUNT_LOGIN_VERIFICATION_EMAIL`, `ACCOUNT_DISABLED`, `INVALID_LOGIN`); up to four enum-shaped codes are kept. Request bodies, headers and URLs are never part of an error.

### Stop and slow-down codes, 429 caps
- Stop (all authenticated work, reads included): 40002, 40012, 50178 and any `captcha_key`/`captcha_sitekey` field, as before.
- Slow down (writes only; reads and the Gateway carry on): **40003** (opening DMs too fast) and **40062** (service resource rate limited), on a 4xx or a 429 body. Both pause every non-GET request for the body's `retry_after` (at most 1 h) or, when it names none, 60 s; the refused request and each blocked one fail with `RestError::WritesPaused(reason)` and the UI says why. 40003 also blocks `POST /users/@me/channels` (opening DMs) for the `retry_after` or 10 minutes. Choice for 40062: it names a service-wide resource, not a route, so the pause covers all writes; kept short (60 s) because it is a guess that it is not route specific. Both codes are community-documented, unverified live.
- 429: the wait is the largest of the body `retry_after` and the headers, and 1 s when that is 0; no usable value at all still returns `InvalidRateLimit` (Cloudflare-style bodies). After 5 consecutive 429s of one request it is not rescheduled and returns `RestError::RateLimited`.

### Reconciliation
An operation is confirmed by whichever comes first: its REST answer, or a Gateway `MESSAGE_CREATE` in the same channel whose author is the READY user and whose `nonce` is the operation's decimal text. The second arrival is a no-op: a REST answer for an operation the Gateway already confirmed is dropped, and the message store ignores an ID it already holds, so the message is shown once in either order. Messages by other authors carrying the same nonce text are never taken as ours. Nonces are decoded leniently (a string of at most 25 characters or an integer; anything else counts as no nonce) and never make a message undecodable. An unconfirmed operation stays until the Gateway confirms it or the user retries or discards it; a retry within Discord's nonce window returns the message Discord already has.

### Ordering and bounds
One `POST` per channel is in flight; later messages of that channel wait until the earlier one is answered, so they arrive in the order written. Sends are checked against `SEND_MESSAGES` of the reducer-validated open channel when queued and when retried; the server stays authoritative. At most 16 operations exist across channels: the UI reserves a slot atomically before it queues a send (a full outbox refuses and keeps the draft), and the slot is freed when the operation leaves. The command queue holds 32 entries, the editor at most 8,000 characters, and drafts are remembered for the 16 most recent channels. Message text never appears in `Debug` output or logs.

## Editing and deleting own messages (milestone 11)

Implemented in `fastcord-discord::edit` (requests, ownership, answer ordering), `fastcord-app::changes` (operations), `fastcord-app::history` (validation and reconciliation), and the timeline/composer views. Evidence: Discord's public "Edit Message" and "Delete Message" documentation (an edit changes only the fields it sends; an `attachments` list in an edit replaces the message's attachments with that list) and community user-client documentation; `fixtures/rest/message-edit-request.json` and `fixtures/rest/message-edit-response.json` are sanitized, fabricated-ID payloads in those shapes. No live capture exists yet (see `docs/TESTING.md`).

### Which messages
Only messages whose author is the READY user and whose type is `DEFAULT` (0) or `REPLY` (19). System messages that name the user as author (joins, pins, boosts, calls, thread starters) and everyone else's messages are never offered or requested; deleting others' messages is moderation and out of MVP scope. The worker checks ownership against its own store copy of the message in the open channel, never against what the UI displayed; the server stays authoritative (a timed-out account's edit is refused by Discord and shown as such).

### Requests
- Edit: `PATCH /channels/{channel}/messages/{message}`, `Priority::UserWrite`, body exactly `{"content": "…"}`: the text with surrounding whitespace trimmed, at most 4,000 characters, empty only when the message has attachments (removing all text and attachments is a delete). Nothing else is sent, so fields the body omits (attachments, flags such as suppressed embeds) stay as they are. No `allowed_mentions` is sent; whether a mention added by an edit notifies anyone is Discord's behavior and is recorded as a live check. Unchanged text sends nothing.
- Delete: `DELETE /channels/{channel}/messages/{message}`, `Priority::UserWrite`, no body; 204 expected. A 404 means the message is already gone and counts as deleted.
- Both share the channel major parameter and route key `/channels/{channel_id}/messages/{id}` (per method) in the scheduler. Deletion is asked for in the row and queued only after the user confirms that same message.

### Outcomes and reconciliation
Both requests are idempotent, but the transport still never repeats one: every failure stays visible on the message's row (a fixed, secret-free sentence naming the action and whether it may have taken effect, with Retry and Dismiss, plus Edit for a failed edit) until the user retries it once or dismisses it. Timeouts, broken answers, and 5xx say the change may have taken effect and that retrying is safe; 403 and 400 say Discord refused; a 401 stops the account. At most one change per message is in flight and at most 16 exist across channels.

An edit's REST answer (the full message) is applied through the same store path as a Gateway `MESSAGE_UPDATE`, as an update carrying every modeled field, unless the cached copy already has a later `edited_timestamp` (compared as RFC 3339 instants), so an answer that arrives after another client's newer edit does not roll it back. The Gateway's echo of an applied edit changes nothing; a partial `MESSAGE_UPDATE` without `attachments` keeps them. A failed edit whose exact text the Gateway later reports, and any change of a message the Gateway reports deleted, ends by itself. A deletion's answer and the Gateway's `MESSAGE_DELETE` are each a no-op after the other; neither path can recreate a message. While an edit is being saved the row shows its new text marked "Saving your edit…"; on failure it shows Discord's copy again.

### Bounds
At most 16 changes, each holding at most 4,000 characters of new text; failed changes of messages no longer held (channel closed, message evicted) are dropped with their row, and a failure that arrives for such a message while its channel is still open is reported in the composer area. Edit and delete commands travel through the same 32-entry command queue as sends; a full queue refuses the action and keeps the editor's text. Once the queue has accepted an edit the composer leaves editing mode, so an edit the worker then refuses (the message was deleted or evicted meanwhile, or 16 changes are already unfinished) is reported in the composer area and its text is not kept. Edit text never appears in `Debug` output or logs.

## Replies (milestone 12)

Implemented by `fastcord-model::Message` (reply references and bounded nested previews), `fastcord-discord::send` (the create body), `fastcord-discord::history` (target reads), `fastcord-app::history` (visible-reference loading and jumps), and the timeline/composer. Wire shapes are captured with fabricated IDs in `fixtures/rest/message-reply-request.json` and `fixtures/rest/message-reply-response.json`; they follow Discord's Create Message schema and documented user-client behavior. No live capture is available yet.

### Send and mention policy

A reply uses the ordinary `POST /channels/{channel}/messages` `Priority::UserWrite` route with:

```json
{"content":"…","nonce":"1290000000000000002","enforce_nonce":true,"tts":false,"flags":0,
 "allowed_mentions":{"parse":["users","roles"],"replied_user":false},
 "message_reference":{"type":0,"message_id":"1289999999999999999","fail_if_not_exists":true}}
```

`type: 0` is a normal message reference, not a forward. `channel_id` is omitted because the reference must be to the message's own channel. `fail_if_not_exists` prevents a deleted target from silently becoming an ordinary message. A reply always supplies `allowed_mentions.replied_user`, including `false`; the checkbox defaults off and records the user's per-reply choice. A plain send has neither `message_reference` nor `replied_user`.

If Discord refuses a reply because its target was deleted after composition, the 400 is a definite not-sent result and remains visible in the outbox; the UI never retries it automatically or drops the reference. A target already known deleted disables Send until the user cancels or chooses another reply.

### Preview and jump

Only `type: 19` messages whose `message_reference.message_id` names the same channel are presented as replies. A missing `referenced_message` is unknown; `null` is deleted; an object is reduced to its display name (at most 128 Unicode scalar values), ID, and at most 200 characters of content. Unknown previews are fetched only for reply rows in the visible timeline, at most one speculative request at a time and with no more than 128 bounded resolution/deletion records.

The preview fetch uses `GET /channels/{channel}/messages?limit=1&around={message_id}` at speculative-read priority. It accepts only the exact requested ID; an adjacent message is never used as the preview. `Ok(None)` means the target is deleted. Clicking a non-deleted preview jumps locally if the target is retained; otherwise a user-priority `limit=49` `around` history page loads it (an odd limit avoids Discord's possible extra record for even limits while keeping responses within the hard 50-message decoder cap). If the target is absent from that page, the viewport is not moved to a neighbor and the target is shown as deleted; if it cannot be retained, it is shown as unavailable. Deleted targets do not offer a jump.

References and previews are memory-only. Reply text and preview text are omitted from `Debug`; the message store charges nested previews to its existing byte budget. Live official-client interoperability remains outstanding (docs/TESTING.md).
## Private conversations (milestone 13)

The sidebar receives a reducer-owned, virtualized window of DM/group-DM rows. Initial private-channel metadata comes from READY/READY_SUPPLEMENTAL and is reconciled with live `CHANNEL_CREATE`, `CHANNEL_UPDATE`, and `CHANNEL_DELETE`; after READY, the worker makes one `GET /users/@me/channels` request to fill the account's channel list. User objects are normalized once and conversation rows keep only bounded (256 UTF-8-byte) labels and IDs. No user/account search, relationship crawl, recipient discovery, or automatic create loop is performed.

The user explicitly enters one or more decimal recipient IDs (maximum 256 input bytes, 1–9 unique IDs excluding the current account; the API caps the whole group at ten members including the account) and presses Open. That action sends `POST /users/@me/channels` with exactly `{"recipients":["<id>", ...]}` through the authenticated scheduler. One ID opens/creates a DM; multiple IDs open/create a group DM. The result is accepted only when it is a non-guild DM or group DM. Confirmed 429s follow the shared scheduler; other errors are surfaced without a blind retry. Fixture coverage pins the body shape and recipient bounds.

Opening a private channel is allowed only when that DM/group-DM exists in the reducer, and closing/deleting it invalidates the selection and its history. Private conversations do not have guild role/overwrite permissions: the user-client API and Gateway remain authoritative, so a denied read/send/edit/delete is shown rather than inferred from fabricated guild permissions. Once selected, the channel uses the same bounded history, send/outbox nonce reconciliation, ownership-gated edit/delete, reply preview/jump, and composer as guild text channels.

## Attachments and the CDN (milestone 14)

Evidence: docs.discord.food "Cloud Uploads" (S7) for `POST /attachments/refresh-urls`; no live capture exists yet (docs/TESTING.md lists the pending checks).

- Message attachments already carry a signed `url` (`ex`/`is`/`hm` query). fastcord fetches it with a separate client that has no default headers, no cookies, no proxy credentials, and no `Authorization`; the authenticated REST client is never used for the CDN and the CDN client is never used for the API. The query string is sent byte for byte as Discord wrote it. `Redirect::none()`: a 3xx is followed by hand (at most five hops), each target resolved against the previous URL and required to be HTTPS without embedded credentials, so nothing but a plain `GET` crosses origins.
- On a CDN 403 or 404, one authenticated `POST /attachments/refresh-urls` with `{"attachment_urls": ["<the URL that failed>"]}` (user-read priority, the shared rate limiter) answers `{"refreshed_urls": [{"original": "<sent>", "refreshed": "<new>"}]}`. The new URL replaces only the URL used for the one retry; it is never stored, logged, or part of a cache key. The pair is matched by `original` (a single-element answer is accepted too). A second 403/404, a refresh error, or an unmatched answer ends the attempt; a 5xx or a network error never triggers a refresh.
- Cache identity is `account/channel/message/attachment` (SHA-256 of the four IDs plus a format version), independent of any URL. Files live under the OS cache directory in `fastcord/attachments/<account id>/`, named `<hash>.<safe extension>`; downloads stream into `<name>-<pid>-<n>.tmp` and are renamed into place under one process-wide lock. Eviction is least-recently-used by file modification time (touched on every hit) across all account directories, 256 MiB in total with each file charged at least 4 KiB, never evicting partial downloads or the file just stored. Before streaming, the declared length (or the limit, when undeclared) is reserved atomically by sizing the partial file under that lock; partial files account for their full reservation during concurrent transfers and shrink to the actual received length on completion. Failed or aborted workers remove their partial file. Logout removes the account's directory and stops every in-flight fetch and write of that cache.
- Limits: previews are fetched only up to 32 MiB (an attachment declaring more, or more than 16 Mpx or 8,192 px on a side, is refused with no request); Open fetches into the cache up to 64 MiB (a quarter of the disk cache, so four concurrent cache fetches always fit); larger files are refused with a message, not truncated. Download has no size ceiling: it streams straight to the chosen destination through the same credential-free, redirect-validated client (with the same single refresh on 403/404), into `.fastcord-download-<pid>-<seq>.part` beside the destination, created with `create_new`. The part file is renamed over the destination only after flush and `sync_all`; it is removed on error, on cancel, or when a logout purge stops the download. The disk cache is not charged. Header dimensions, pixel count, and the decoder's allocation (160 MiB) are checked before any pixel buffer exists; only PNG, JPEG, GIF, WebP, and BMP are decoded, animated formats show their first frame, and EXIF orientation is applied.
- Four fetch slots and two decode slots bound worker concurrency. A decode permit belongs to the blocking decoder itself: aborting its async caller cannot release the slot while pixel decoding is still running. The 12 MiB decoded LRU shares immutable thumbnail pixels with the UI; dimensions distinguish inline and larger-view entries.
- Open is offered only for passive types (`png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`, `mp3`, `ogg`, `wav`, `m4a`, `mp4`, `webm`, `pdf`, `txt`), judged on the final extension of the sanitized filename, which the cache entry keeps; every other type is Download-only. Open uses the OS default handler (`explorer.exe`, `open`, `xdg-open`) with the cached file, never through a shell. On Windows a `Zone.Identifier` stream with `ZoneId=3` is written before opening, and the file is not opened if that fails. Download asks for a destination in the native save dialog (off the UI thread) and streams the file there as described under Limits; a saved download is then marked the same way on a best-effort basis, and a volume without alternate streams (FAT, exFAT, network shares) still keeps the file.

## Message formatting, embeds and mentions (milestone 39)

Evidence: Discord's documented message object (`mentions`, `mention_roles`, `mention_everyone`, `embeds`) and its documented Markdown subset; no live capture exists yet (docs/TESTING.md lists the pending checks).

- Received fields kept per message and per `MESSAGE_UPDATE`: `mentions` (user objects, which resolve `<@id>`/`<@!id>`), `mention_roles`, `mention_everyone`, `embeds`. A partial update replaces only the fields it carries; an embed-only unfurl that shows nothing changes nothing.
- Embeds keep title, description, url, color, author/provider name, footer text, fields (at most 25), image and thumbnail URLs (and the media-proxy `proxy_url`) with sizes; at most 10 per message, a malformed or empty embed is dropped rather than failing the message. Their text is part of the message's byte cost in the store. Image and thumbnail URLs may be signed: they are never logged (`Debug` prints counts only) and fall back to an `Image: host` link. A picture is fetched only from its `proxy_url` on a `*.discordapp.net`/`*.discordapp.com` https host, never from the original third-party URL.
- Markdown is parsed on the client from the unchanged source text (`fastcord-model::markup`, borrowed spans): `**bold**`, `*italic*`/`_italic_`, `__underline__`, `~~strike~~`, `` `code` ``/` ``code`` `, fenced blocks with a language word, `> quote`/`>>> quote`, `#`/`##`/`###` headings, `-#` subtext, `- ` lists, `||spoiler||`, `\` escapes, bare and `<angle>` URLs, `[label](https://…)` masked links, `<@id>`, `<@!id>`, `<@&id>`, `<#id>`, `@everyone`, `@here`. Emphasis never crosses a line; `<t:…>` timestamps stay literal text. Limits: 200 blocks per message, lines over 4,096 bytes are plain, nesting depth 6.
- Mention names: users come from the message's `mentions`; role and channel names are looked up only for the ids the visible rows reference, in the selected server (an unknown id shows `@unknown-role`, `#unknown-channel`, `@unknown-user`). `@everyone`/`@here` are highlighted only when `mention_everyone` is true.
- Links open only when `http`/`https` with a host and no whitespace or control characters, through the OS default browser as a single process argument (never a shell). A masked link shows its host after the label.
- Sending is unchanged (`allowed_mentions` is always sent, see Replies). Composer completion replaces an `@`/`#` word at the cursor (after whitespace or at line start) with `<@id>`, `<@&id>` or `<#id>` from the shown authors, the server's roles and its text/announcement channels (at most 8 offered); nothing is sent until the user sends.

## Attachment uploads (milestone 40)

Evidence: Discord's documented cloud-upload flow as the web client uses it (`POST /channels/{id}/attachments`, a `PUT` to the returned storage URL, then `POST /channels/{id}/messages` with `attachments`); no live capture exists yet (docs/TESTING.md lists the pending checks).

- Slots: one authenticated `POST /channels/{channel}/attachments` (user-write priority, the shared rate limiter) with `{"files": [{"filename", "file_size", "id": "<index>"}]}`. The answer's `attachments[]` (`id`, `upload_url`, `upload_filename`) must match the request one to one by index; any other count, a duplicate or an out-of-range id is refused. `upload_url` is signed and never logged.
- Bytes: a `PUT` of the file with `Content-Length` and `Content-Type: application/octet-stream` from a separate client with no default headers, cookies or credentials, `https` only, no redirects, 60 s read timeout, and a host allowlist (`*.storage.googleapis.com`, `*.discordapp.com`, `*.discordapp.net`, `*.discord.com`, `*.discord.media`; no user info). The user token cannot reach it. The file is read in 64 KiB chunks and counted into the progress shown to the user; reading to the end must give exactly the size announced, and size and modification time are checked when chosen, before the slot request and before the `PUT`, so a changed file fails with "changed after you chose it" instead of sending other bytes.
- Message: `POST /channels/{channel}/messages` as in Sending messages, plus `attachments: [{"id": "<index>", "filename", "uploaded_filename"}]`; the text may be empty. Same nonce, `enforce_nonce` and `allowed_mentions` rules.
- Outcomes: a failure before the message `POST` (a file problem, the slot request, the `PUT`, a cancel) created no message, so the send is plainly Failed and an explicit retry uploads again; the message `POST` keeps the Sending rules (a lost answer is Uncertain, a retry reuses the nonce so Discord returns the message it already made). A cancel aborts only the upload phase; once the message `POST` has started it cannot be cancelled. Retrying always re-uploads (new slots); uploaded-but-unreferenced files expire on Discord's side. 413 and 4xx slot refusals are shown as size/permission limits; the real limits depend on the account and server and Discord stays authoritative (fastcord only refuses more than 10 files, empty files, non-files and files over 512 MiB).
- Ordering: one send per channel is in flight, with or without files, so messages keep the order they were written in.
- Choosing files: the system dialog, files dropped on the window (one event per file) and an explicit "Paste image" (clipboard `CF_DIB`, Windows only, read only when asked, re-encoded as PNG without alpha into a private temporary directory; the file is deleted when its last reference goes and stale ones at the next start).

## Read state, unread markers and mentions (milestone 41)

Evidence: Userdoccers/docs.discord.food descriptions of READY `read_state`, `user_guild_settings`, `MESSAGE_ACK` and `POST /channels/{id}/messages/{id}/ack`; no live capture exists yet and the fixtures here are synthetic (docs/TESTING.md lists the pending checks).

- READY: `read_state` (an object with `entries`, or a bare array) gives per channel `id`, `last_acked_id` (older payloads: `last_message_id`) and `mention_count`; `user_guild_settings` (same two shapes) gives `guild_id` (null for DMs), `muted`, `mute_config.end_time` and `channel_overrides[]` with `channel_id`, `muted`, `mute_config`. Both are read leniently from a transient JSON value: an entry whose ids do not parse is skipped, an unexpected shape yields no markers, and neither can fail the session. A mute whose `end_time` has passed is ignored. A new READY replaces the whole table.
- Events: `MESSAGE_ACK` (`channel_id`, `message_id`, `mention_count`) sets that channel's cursor and count, as sent by any client of the account; `USER_GUILD_SETTINGS_UPDATE` updates the guild/channel mutes; `CHANNEL_DELETE` forgets the channel.
- The cursor is the account's, never the channel's `last_message_id`: a channel is unread when it has a cursor, its newest message is newer than the cursor, and neither it nor its guild is muted. A channel without a cursor shows nothing (a fresh account does not light up). A message that mentions the account (`mentions` contains it, `mention_everyone`, or a role it holds, or any message in a DM) adds one mention, once, when newer than the cursor, even in muted places; the account's own message acknowledges the channel. A guild shows a dot if any channel is unread and the sum of mention counts.
- Table bounds: 16,384 cursors and 4,096 muted guilds and channels, charged to the 12 MiB metadata ledger and shed first (before members) under pressure; READY brings them back.
- Acknowledging: `POST /channels/{channel}/messages/{message}/ack`, user-write priority. Automatic (the newest message is on screen): `{"token": null}`. Explicit "Mark as read": `{"manual": true, "mention_count": 0}`. At most one acknowledgement is in flight; while it is, only the newest wish is kept (`ack_wanted`), so a burst of messages costs one request. An automatic one is sent only when the window is active and drawn, the open channel follows the live edge and sits at the bottom, and the newest retained message is newer than the cursor; reading older history never acknowledges. A failure is silent and not repeated for the same message; a success updates the store at once (forward only, so a stale answer cannot mark newer messages read) and the echo from the Gateway changes nothing further. Not established: whether the first automatic acknowledgement may omit `last_viewed`/a token, and whether the sending session receives its own `MESSAGE_ACK`.
- First unread: `GET /channels/{id}/messages?around=<cursor>`; the oldest message newer than the cursor is scrolled to and highlighted (the cursor's own message may be gone). If the retained run already covers the cursor no request is made.

## Custom emoji (milestone 15)

Evidence: Discord's public Guild and Gateway documentation (guild `emojis`, `GUILD_EMOJIS_UPDATE`) and the public emoji CDN; fabricated-ID payloads only, no live capture yet (docs/TESTING.md).

- Guild `emojis` arrive inside GUILD_CREATE (and the same normalized field from READY guilds). Each entry keeps `id`, `name`, `animated` (default `false`), `roles` (default empty), and `available` (default `true`); every other field is skipped as read. The reducer stores them per guild sorted by ID and deduplicated, charged to the existing store budget, and a GUILD_UPDATE keeps the held list.
- `GUILD_EMOJIS_UPDATE` (`{guild_id, emojis: [...]}`) replaces the whole emoji list of a guild the store already holds and marks that guild changed; an update for an unknown guild is ignored. There is no request to refresh emoji: the Gateway is the only source of the list, and **no REST emoji fallback** (`GET /guilds/{id}/emojis`) exists.
- Usability is computed locally and never assumes entitlements: an emoji is offered only when `available` is true and its `roles` are empty, include the `@everyone` role (the guild ID), the user is the guild owner, or the member's known roles intersect them. Animated and external emoji may be rejected by Discord for lack of Nitro; the rejection appears beside the unsent message as for any other send failure.
- Message text is sent unchanged: custom emoji are the ordinary `<:name:id>` / `<a:name:id>` tokens, Unicode emoji the original sequence. Parsing never rewrites the source.
- Images are fetched with the credential-free CDN client of milestone 14 from `https://cdn.discordapp.com/emojis/{id}.{png|gif}?size=32&quality=lossless` (`gif` only for `animated` emoji): no `Authorization`, cookies, or default headers. The URL is public and unsigned, so a 403/404 is never answered with `POST /attachments/refresh-urls`; the emoji keeps its text token. Files are limited to 2 MiB, 120 frames, and 512 KiB of decoded RGBA, are cached with the attachment disk cache under a reserved zero-channel identity, and are decoded off the UI thread only while visible. GIF frame delays of 10 ms or less are shown as 100 ms (browser behavior).
- Unicode emoji use the bundled, attributed Twemoji 17.0.3 PNGs (`assets/emoji/`); nothing is requested for them.

## Reactions (milestone 16)

Implemented by `fastcord-model::Message` (the aggregate and its changes), `fastcord-discord::gateway` (the four reaction events), `fastcord-discord::message_store` (where they apply), `fastcord-discord::reaction` (the requests), `fastcord-app::reactions`/`history` (the user's requests and the who-reacted list), and the timeline chips. Evidence: Discord Userdoccers (S5: the Reaction object, Create Reaction, Delete Own Reaction, List Reactions, and the Gateway "Message Reaction ..." events). `fixtures/gateway/message_reaction_*.json` and `fixtures/rest/reaction-routes.json` / `reaction-users.json` are shaped after those pages with fabricated IDs. No live capture exists yet (docs/TESTING.md).

### What is kept
A message holds one aggregate per emoji, `{count, me, emoji}`, and never the reacting users. `count` is Discord's total (normal and burst reactions together); `me` is only the account's own **normal** reaction, so a super reaction made elsewhere counts but never highlights a chip. A custom emoji is identified by its ID alone (a rename, or the null name of a deleted emoji, does not split a reaction), a Unicode emoji by its exact name. At most 32 distinct emoji are kept per message (Discord allows 20 normal and 5 burst), names are at most 64 bytes, and the aggregate is charged to the existing 16 MiB message budget by capacity like every other body field. Reactions in a REST page or `MESSAGE_CREATE` arrive as the message's `reactions`; a `MESSAGE_UPDATE` carries none and never changes them.

### Gateway events
`MESSAGE_REACTION_ADD` and `MESSAGE_REACTION_REMOVE`: `{user_id, channel_id, message_id, guild_id?, emoji: {id?, name?, animated?}, type?, burst?}`, everything else (`member`, `message_author_id`, `burst_colors`, ...) skipped as it is read. A reaction is a burst reaction when `type` is present and not `0`, or `burst` is true. `MESSAGE_REACTION_REMOVE_ALL`: `{channel_id, message_id, guild_id?}`. `MESSAGE_REACTION_REMOVE_EMOJI`: the same plus `emoji`. An emoji is accepted only when it has a nonzero `id` or a non-empty `name` of at most 64 bytes; otherwise the event is undecodable and skipped (its sequence still counts). `MESSAGE_REACTION_ADD_MANY` needs the `DEBOUNCE_MESSAGE_REACTIONS` capability, which is deliberately not enabled (§Capabilities), so it never arrives; it would be consumed as an unknown event. The navigation reducer ignores all four.

| Event | Effect on a held message |
|---|---|
| add, own normal | `me = true`, `count + 1`; **a repeat changes nothing** (the REST answer and this echo each become a no-op after the other) |
| add, burst or another user | `count + 1`; a new emoji gets an entry unless 32 are held |
| remove, own normal | needs `me` (otherwise nothing), clears it, `count - 1` |
| remove, burst or another user | `count - 1` |
| remove, count reaches 0 | the entry is dropped (order of the rest kept) |
| remove emoji / remove all | the entry / every entry is dropped |

"Own" means `user_id` equals the READY user, which the history coordinator hands to the store at every READY (`MessageStore::set_user`; until then every event counts as another user's).

### Where an event applies
Retained messages only, copy-on-write and only when the event changes what is shown: an event that repeats the held state keeps the revision and the shared handle, so no row re-measures. A body that would exceed 512 KiB after the change is removed like an oversized update. A message that is **not** held allocates nothing: no entry, no run for its channel, no tombstone. The only thing a request in flight can need is not to be wrong: with a history page pending for that channel, a message created meanwhile (the live-edge journal) takes the change on its journaled copy, and any other message is noted exactly like an update to an uncached one, so a page that lists it is `Stale` and asked for again rather than trusted (the journal holds at most 512 such IDs; one more makes every page stale instead of growing). Without a pending page the event does nothing at all. Tests flood 100,000 events across 10,000 uncached messages, and against held messages with 2,000 distinct emoji, and require the byte ledger to equal a recount and to stay within budget.

### Requests
Each request is made once (only a 429 is rescheduled by the shared scheduler), on the channel's major parameter. The emoji is one percent-encoded path segment: every byte except ASCII letters, digits, and `-._~` becomes uppercase `%XX`; a Unicode emoji is its UTF-8 bytes, a custom emoji `name:id` (`wave%3A777`). The animated flag is not part of the path.

| Action | Request |
|---|---|
| Add the account's reaction | `PUT /channels/{channel}/messages/{message}/reactions/{emoji}/@me`, no query, no body, user-write priority |
| Take it back | `DELETE /channels/{channel}/messages/{message}/reactions/{emoji}/0/@me`: the **user client's typed route** (`0` is a normal reaction), no body, user-write priority; no fallback to the untyped bot route |
| Who reacted (only when the user asks) | `GET /channels/{channel}/messages/{message}/reactions/{emoji}?limit=26&type=0`, user-read priority; the first 25 names are shown and a 26th means "and others" |

`fixtures/rest/reaction-routes.json` is the compatibility pin: the exact method and path for each action with a Unicode emoji (👍), a variation-selector emoji (❤️), a ZWJ/skin-tone sequence (👩🏽‍💻) and a custom emoji, asserted against the routes the code builds (the list is pinned with `limit=25`; the app asks for 26). Rate-limit keys: `PUT` is `/channels/{channel_id}/messages/{id}/reactions/{emoji}/@me`; the typed delete's `0` normalizes to `{id}`, giving `.../reactions/{emoji}/{id}/@me`; the list is `.../reactions/{emoji}`. A user object in the list is reduced to its ID and display name (global name, else username, at most 64 characters).

### The user's request and its answer
Clicking a chip asks for the opposite of the *stored* state (take the reaction back when `me`, add it otherwise); picking an emoji in the picker only adds, and does nothing when the reaction already is the user's. The worker checks the request against its store, never against what a stale UI showed: the channel must be the open one, the message retained, and the emoji nameable in a path. Adding a reaction nobody made yet needs `ADD_REACTIONS` (`PermissionSummary.add_reactions`, which a timeout removes); joining a reaction others made and taking one's own back are not gated locally. The server stays authoritative either way.

At most one request per (message, emoji) is in flight and at most 16 exist (a click on a busy reaction, or a full ledger, says so and asks nothing), so an add and a remove of one reaction can never race to Discord. An unanswered request is only an overlay: its chip is drawn as if Discord had accepted it and is disabled; the store changes when Discord answers. A 2xx answer goes into the store through the same path as the Gateway's report of the account's own reaction, so whichever arrives second is a no-op in either order. A 404 for a removal means the reaction is already gone and counts as removed. Every other failure changes nothing, is shown once as a fixed secret-free sentence above the message box (permission refused, message or emoji gone, rejected, "could not reach Discord", "did not confirm; it may have been applied"), and is never retried by the program; a 401 stops the account as everywhere else. Requests in flight survive a channel change; their answers meet an empty store.

### Live observation (2026-10-16)
The alt-account Windows app added a Unicode heart reaction to a DM through the bare `PUT`, listed both reacting accounts through the `type=0` route, and removed its own reaction through the typed `DELETE`. The official client's count changed 1 → 2 → 1. This establishes those three normal-reaction requests for the tested client profile; no raw authenticated traffic or sanitized live packet fixture was committed. See `docs/TESTING.md` for the executable and scope.

### Not established (verify live, see docs/TESTING.md)
The real answer for removing a reaction that is already gone (404 is assumed); custom-reaction interoperability and the error codes Discord uses for a blocked reactor, the 20-emoji limit, and an unavailable custom emoji; the burst/normal count arithmetic against the official client's chips; moderators' remove-emoji/remove-all events.

## Voice session and transport (milestone 17)

Implemented in `fastcord-media` (depends on `fastcord-model` only). Evidence: payload shapes and codes follow Discord's voice documentation and the community voice-connection/opcode tables (docs.discord.food); nothing below was captured from a live session yet (see the pending checks in `docs/TESTING.md`). Transport vectors in `fixtures/voice/transport-vectors.json` were generated with pycryptodome, independently of the RustCrypto crates under test.

### Join correlation
`session::JoinCorrelator` pairs the account's own VOICE_STATE_UPDATE (`session_id`) with VOICE_SERVER_UPDATE (`token`, `endpoint`) in either order. `join(guild, channel)` starts an attempt (call it right before opcode 4); every attempt and every credential change gets a new `Generation`, and the consumer drops any older connection. Until the first connection, states for another channel are stale and ignored; afterwards a different channel is a server-side move, and the new token (from VOICE_SERVER_UPDATE, before or after the state) reconnects. A token is used for one generation only; moving channel always waits for a new one. A null endpoint means reallocation (drop the connection, wait); a channel-null state ends the attempt. Private calls match on the channel, and the channel ID is the `server_id`.

### Voice Gateway v8
- URL `wss://<endpoint>/?v=8`; the endpoint must be a plain `host[:port]` (no scheme, path, or credentials), otherwise nothing is contacted. Origin `https://discord.com`, rustls/ring with webpki roots, 1 MiB message cap.
- Identify (op 0): `server_id`, `user_id`, `session_id`, `token`, `max_dave_protocol_version: 1` (DAVE v1, milestone 18; a channel that requires E2EE and receives no DAVE version closes with 4017, `CloseReason::E2eeRequired`). A connection that offers video adds `video: true` and, for an owner, its screen layer (see the H.264 section below); audio-only connections send exactly the fields above.
- Heartbeat (op 3) every HELLO interval (clamped to 1–60 s) as `{"t": nonce, "seq_ack": last}`; `seq_ack` is the last `seq` of a numbered JSON message or the two-byte prefix of a binary message, `-1` before any. An unacknowledged heartbeat when the next is due, or a missing HELLO/READY/RESUMED/Session Description (10/15 s), reconnects. A server op 3 is answered at once.
- READY (op 2) → UDP socket to `ip:port`, IP discovery, then Select Protocol (op 1): `{"protocol": "udp", "data": {"address", "port", "mode"}, "codecs": [{"name": "opus", "type": "audio", "priority": 1000, "payload_type": 120}]}`, plus one `video` entry per video offer when the connection offers video (below). Mode: `aead_aes256_gcm_rtpsize` when offered and the CPU has AES+CLMUL (PMULL on ARM), otherwise `aead_xchacha20_poly1305_rtpsize`; deprecated modes are never chosen, and READY without either stops (`NoSupportedMode`).
- Session Description (op 4) must name the selected mode, `opus`, DAVE version 1, and a 32-byte `secret_key` (decoded straight into a zeroizing array); its `video_codec`, when present, names the codec this connection should send. Local media then waits for DAVE keys (milestone 18), so nothing leaves before the MLS transition executes.
- Resume (op 7) `{server_id, session_id, token, seq_ack}` once media is established; RESUMED (op 9) keeps the UDP socket, SSRC, key, and nonce counter. A socket lost before Session Description identifies again with a fresh UDP socket. Five consecutive failed attempts (backoff 1–16 s) end with `Network`.
- Close codes: 4006/4009 `SessionInvalid`, 4004 `AuthenticationFailed`, 4011 `ServerNotFound`, 4014/4022 `Disconnected`, 4017 `E2eeRequired`, 4021 `RateLimited` — none reconnect; 4013/4015 resume; other 4xxx are protocol errors.
- Received: Speaking (op 5) and Video (op 12) map SSRCs to users, Clients Connect (op 11) and Client Disconnect (op 13, forgets the user's SSRCs) are surfaced; Session Update (op 14) and Media Sink Wants (op 15) are used by connections that offer video (below); client flags/platform are ignored.
- Leaving: `VoiceSession::leave` sends close 1000 and drops UDP, key, and task; dropping the session aborts at once. The main Gateway's channel-null opcode 4 (above) is sent by the caller.

### UDP, RTP, RTCP
- IP discovery: 74-byte request `0x0001`, length 70, SSRC, zero address/port; the response must be type `0x0002`, length 70, our SSRC, a NUL-terminated textual IP, and a nonzero port, from the server's address. Up to five requests one second apart; no answer ends with `UdpUnreachable` (no relay fallback). UDP ping `0x1337CAFE`+sequence every 5 s; a matching `0x1337F00D` answer reports the round trip.
- Demultiplexing uses clear bytes only: ping and discovery answers by length and magic (RTP version field 0), RTCP by packet type 192–223, everything else of version 2 as RTP. Datagrams from any other source address are dropped.
- rtpsize AEAD: authenticated clear part = RTP fixed header + CSRCs + 4-byte extension preamble (extension elements are encrypted with the payload), or the 8-byte RTCP header + sender SSRC. The packet ends with the 16-byte tag and the 4-byte big-endian nonce counter, which forms the first four bytes of the 12-byte (AES-GCM) or 24-byte (XChaCha20) nonce; the suffix is stripped before verification. The send counter starts at 0, is shared by RTP and RTCP, and never wraps: after nonce `0xFFFFFFFF` the connection ends with `KeyExhausted`. RTP sequence (16-bit) and timestamp (32-bit) wrap independently and are unrelated to the nonce.
- Sending: queued Opus frames (at most 5) are read only after Session Description; a Speaking (op 5, `speaking: 1`) is sent before the first audible packet after silence; `end_speech` sends five `F8 FF FE` silence frames 20 ms apart, then `speaking: 0`. Payload type 120, 960 ticks per frame, random initial sequence/timestamp. A Sender Report (no blocks) follows every 5 s while media was sent.
- Microphone bitrate (#118): the Opus encoder targets the `bitrate` field of the guild voice or Stage channel the account's voice state is in (the requested channel until Discord's `VOICE_STATE_UPDATE` names one), clamped to 8000-384000 because it is network input. A DM or group-DM call and a channel without the field use 64 kbit/s; the official client's DM-call rate is not yet compared. A `CHANNEL_UPDATE` of that channel or a move retargets the running encoder in place (`EngineControl::Bitrate`), with no device reopen. Nothing extra is sent on the wire. Stream audio (128 kbit/s), soundboard and voice messages are unaffected.
- Receiving: payload type 120 (Opus) and, on connections that offered video, the negotiated video payload types (below); payload type 96, which Discord reserves for probe packets, is ignored on those connections and counted as malformed on audio-only ones, as is any other. Packets are authenticated, padding and extension elements removed, and the sequence extended across wraps per SSRC. Audio from an unannounced SSRC is held at most 100 ms and 32 KiB, then dropped, never attributed to someone else. Receiver/Sender Report blocks about our SSRC are surfaced as reception reports; the RTCP compound is parsed with its own header/length rules (padding only on the last packet). Received audio waits in a 64-packet queue; newer packets are dropped (and counted) when the consumer lags.

## Go Live signaling and independent stream session (milestone 24)

The main Gateway exposes explicit create, watch, unwatch, pause/resume, and ping intents (opcodes 18–22). `StreamKey` parses the documented owner-qualified forms `guild:{guild_id}:{channel_id}:{owner_id}` and `call:{channel_id}:{owner_id}` without losing the owner identity. `StreamCorrelator` pairs `STREAM_CREATE` (which carries `rtc_server_id` and `rtc_channel_id`) with `STREAM_SERVER_UPDATE` (which carries the stream token and endpoint) by key, in either arrival order. A new RTC identity, credential change, server reallocation, or delete advances an independent generation; a repeated CREATE with identical RTC IDs preserves the running transport, credentials and DAVE group. The sender is paused before its old transport is retired during a real reallocation. Malformed keys and unusable identities fail closed.

Each stream opens its own voice-v8 session using `rtc_server_id` as its voice Identify `server_id`; `rtc_channel_id` remains the independent RTC channel identity. Each stream owns its own token, WebSocket/UDP/SSRC/transport nonce state. DAVE's MLS group identity is `rtc_server_id - 1`, checked before opening the session and supplied independently of the parent voice channel. Watchers do not open an audio engine or microphone. Stream end, reallocation, protocol failure, and connection failure tear down only the matching stream task; parent voice remains independent. Local unwatch retires the stream generation immediately so late events cannot restart it, and bounded outbound signal backpressure retains a command until the Gateway accepts it.

The app accepts explicit stream intents through `NavigationBridge`; watching starts no capture, and creating a stream is the owner flow of milestone 29 (below). M28 provides Watch/Show/Stop controls for Go Live offers in the joined parent voice channel. Every stream has independent RTC/DAVE state; the transport requests, repairs, reassembles and DAVE-opens complete frames, and a dedicated worker decodes H.264 (Windows/macOS native paths) or AV1 (dav1d) only while its pane is visible and the window is active. Linux watch sessions offer AV1 only until M30 supplies an H.264 decoder.

## H.264 video transport (milestone 25)

Implemented in `fastcord-media::video` (packetization, reassembly, pacing, retransmission ring, rate control) and the voice driver (`gateway::driver::video`: negotiation, feedback, the DAVE boundary). Evidence: the Userdoccers voice documentation (S9: native RTP extension IDs, RTX, RTCP duties, Select Protocol codec fields, Media Sink Wants), RFC 6184 (H.264 RTP), RFC 4588 (RTX), RFC 4585/5104 (NACK, PLI, FIR), draft-alvestrand-rmcat-remb, and RFC 8285. **Nothing below was captured from a live session**: the unverified assumptions are listed at the end and in `docs/TESTING.md`. Wire vectors in `fixtures/voice/h264-rtp-vectors.json` come from `fixtures/voice/gen_h264_rtp_vectors.py`, an independent RFC 6184/4588 and pycryptodome implementation.

### Negotiation
- A connection offers video only when created with `connect_with_video` (`VideoOptions::watch()` for a stream viewer, `share(..)` for an owner); `connect` stays audio-only. Offers are validated first: payload and RTX payload types 97–127 other than 120 (96 is reserved), unique per codec, and a layer only with an encoder.
- Identify: `video: true`; an owner adds `streams: [{"type": "screen", "rid": "100", "quality": 100, "max_bitrate", "max_framerate", "max_resolution": {"type": "fixed", "width", "height"}}]` (one layer, 1280×720 at 30 fps and 2.5 Mbit/s by default).
- Select Protocol: `{"name": "H264", "type": "video", "priority": 1000, "payload_type": 103, "rtx_payload_type": 104, "encode": bool, "decode": bool}`. A viewer offers decode only, an owner both; fastcord sends only a codec the server selected *and* it offered `encode` for. The codec's profile is not conveyed (the native codec structure has no such field).
- READY's `streams` stay untyped until a video offer reads them: the first stream with a nonzero `ssrc` is the layer (`rtx_ssrc` defaults to `ssrc + 1`, `rid` to `100`; a RID the one-byte RTP extension cannot carry is refused). Session Description `video_codec` selects the codec to send; anything but `H264`, or no layer, means nothing is sent (`VoiceEvent::VideoNegotiated { codec: None }`). Session Update (op 14) with a `video_codec` re-evaluates that.
- Opcode 12 from us: an owner announces its layer (`{"audio_ssrc", "video_ssrc", "rtx_ssrc", "streams": [{"type": "video", "rid", "ssrc", "active", "quality": 100, "rtx_ssrc", "max_bitrate", "max_framerate", "max_resolution"}]}`) before the first RTP packet and again with `active: false`/`true` when the server pauses and resumes it. A viewer sends one with `video_ssrc: 0`, `rtx_ssrc: 0`, `streams: []` after Session Description (the documentation requires "at least one Video payload before sending or receiving video data"; whether a viewer needs it is unverified). Opcode 12 from others maps their audio, primary, and RTX SSRCs (an RTX SSRC knows its primary); the best *active* stream by `quality` is the one a viewer wants.
- Media Sink Wants (op 15), viewer: `{"<primary ssrc>": 100, "any": 0}` for the best active stream of each announced user, sent when it changes (never an empty first message), re-sent after RESUMED, and `{"any": 0}` while the viewer turned video off with `MediaSender::set_video_wanted(false)` (a watch connection starts wanting). Turning it back on asks for a keyframe. From the server to an owner: `{"<our ssrc>" or "any": quality}`; 0 pauses the layer (opcode 12 `active: false`, frames refused, `VoiceEvent::VideoActive(false)`), above 0 resumes it (keyframe requested) and caps the bitrate at `quality`% of the configured one.

### RTP
- 90 kHz clock; the offered payload types (103/104); the marker bit on the last packet of a frame; random initial sequence numbers and timestamp; frame timestamps follow the source clock and are strictly increasing. Datagrams are at most 1,200 bytes with RTP header, extensions, tag, and nonce suffix, so a payload is at most 1,138 bytes.
- One-byte header extensions (profile `0xBEDE`) with Discord's fixed native IDs, inside the AEAD body behind the clear 4-byte preamble: primary packets carry abs-send-time (3), playout-delay (6, minimum and maximum 0), video-content-type (7, `1` = screenshare), and RTP stream ID (11, the layer's RID); RTX packets carry abs-send-time (3) and repaired RTP stream ID (12). Received extension blocks are only validated, never interpreted.
- H.264 (RFC 6184 packetization mode 1): fastcord sends single NAL unit packets and FU-A; it receives those and STAP-A, and rejects STAP-B, MTAP, FU-B and decoding-order numbers. A frame is one Annex B access unit. **DAVE seals the whole frame first** (the transform keeps every NAL header readable, rewrites start codes to `00 00 00 01`, and leaves no start code in its ciphertext), so start codes alone delimit the NAL units of the sealed frame, and the receiver rebuilds exactly those bytes before DAVE opens the frame. Keyframes are recognized from the unencrypted NAL headers (IDR, type 5).
- Receiving: one bounded buffer per primary SSRC (4 MiB, 2,048 packets) over the wrap-extended sequence, at most four streams per connection. A frame is the contiguous run ending at a marker packet (or before a timestamp change) and is delivered in order only when complete. A gap older than 10 ms is a loss; a frame still incomplete after 200 ms is abandoned together with its packets, and a jump of more than 512 packets (or the same far back) is a sender restart that drops what was buffered. After any abandoned, undecryptable, refused, or untaken frame the stream drops delta frames until a keyframe and asks for one. A frame that fails DAVE is never delivered. Packets of an SSRC the server has not announced are held 100 ms and 64 KiB. Complete frames wait in a three-frame queue (each at most 2 MiB); a full queue drops the frame and restarts at a keyframe.
- RTX (RFC 4588): payload = the original sequence number (2 bytes) + the original payload, on the RTX SSRC and payload type with its own sequence numbers; the timestamp and marker bit are the original's. Received RTX is unwrapped onto its primary stream; sent RTX copies the shared payload from the retransmission ring, so nothing is re-encrypted at the DAVE level.

### RTCP
- Receiver side, as one compound datagram led by a Receiver Report (sender SSRC = our audio SSRC): a report block per stream every second (fraction and cumulative loss counting RTX-recovered packets as received, highest sequence, interarrival jitter, last-sender-report and delay-since-last-report from the sender's reports); Generic NACK for gaps (first request after the 10 ms reorder grace, repeated every round trip + 10 ms clamped to 30–100 ms, at most six times per packet and 64 numbers per round); and a PLI when a stream is damaged (at least 500 ms apart per stream; a new stream gets 250 ms to produce its keyframe first, and a delivered keyframe cancels a request still waiting).
- Sender side: a Sender Report for the layer, and for the RTX stream once it repaired something, every 5 s while sending (NTP time, the RTP timestamp extrapolated from the last frame, packet and octet counts). Received: report blocks about the layer (loss and round trip steer the bitrate), Generic NACK (at most 256 numbers per packet), PLI and FIR (surfaced as `VoiceEvent::KeyframeRequested`, coalesced to one per 300 ms), and REMB (honored when it names our SSRC or none).
- Every RTCP datagram is sealed under the same transport key with the 8-byte header + sender SSRC in the clear, and **every datagram, retransmissions included, takes a fresh transport nonce** from the connection's single counter.

### Pacing, retransmission ring, and rate control
- The pacer normally queues at most 100 ms at 2.5× the target bitrate (78,125 bytes at 2.5 Mbit/s), with 20 ms of burst credit for late wake-ups. An empty queue may admit one keyframe with up to 180 ms of data at the same pacing rate and burst limit; the ordinary bound returns as soon as it drains. It cannot extend an occupied queue or admit more than the existing packet/frame byte caps. A frame that does not fit is refused whole, with no gap in the RTP sequence. A frame too large for an empty queue does not trigger a congestion bitrate cut. The retransmission ring holds sent primary packets for 500 ms and 2 MiB and evicts whole frames.
- Rate control follows SPEC §8.3: cut 20% on more than 5% loss, a pacer over its cap, or a round trip over 100 ms above the running minimum (cuts at least one second apart); raise at most 5% per interval after five seconds at or below 2% loss; a REMB or server limit applies at once and caps the return. Changes reach the encoder as `VoiceEvent::VideoBitrate`. A refused or discarded frame restarts the stream at a keyframe (`VideoFrame`s after a gap are refused until one arrives), requested with `VoiceEvent::KeyframeRequested`. Frames offered while DAVE keys are not ready wait in a three-frame queue and are discarded when keys arrive.
- Counters (`TransportStats`): packets, complete frames, drops, refusals, retransmissions, NACKed sequence numbers, and PLIs sent.

### Not established (verify live, see docs/TESTING.md)
Whether the server selects and forwards H.264 to fastcord without a profile in Select Protocol (U4); whether a viewer needs the empty opcode 12 and the exact opcode 15 shape (`any: 0` beside the SSRC); the extension IDs and the playout-delay and content-type values of native UDP (taken from the community table, not captured); whether the server honors REMB and receiver reports without transport-wide congestion control (neither the transport-wide sequence extension nor transport-cc feedback is implemented); whether bare Receiver Report + NACK/PLI compounds without SDES are accepted; the RID value and RTX SSRC derivation; the real packetization official clients emit (STAP-A aggregation is handled, interleaved modes are not) and that DAVE-sealed frames from them reassemble to the exact bytes DAVE sealed; stream-group DAVE interoperability (U3).

Wire vectors in `fixtures/voice/av1-rtp-vectors.json` come from `fixtures/voice/gen_av1_rtp_vectors.py`, an independent implementation of the AV1 RTP aggregation/fragmentation layout, RFC 4588 RTX, and rtpsize sealing (pycryptodome), written without reference to the Rust code under test.

### Negotiation
- Select Protocol lists AV1 after H.264: `{"name": "AV1", "type": "video", "priority": 2000, "payload_type": 101, "rtx_payload_type": 102, "encode": false, "decode": true}` (the priority is the entry's position times 1,000). A viewer and an owner both offer it, decode only: `VideoOptions::validate` refuses an AV1 encode offer, and a Session Description or Session Update that names `AV1` as the codec to send leaves nothing sent (`VoiceEvent::VideoNegotiated { codec: None }`). The payload types are the community-documented numbers (S9); the server's selection is U4.
- A packet's payload type decides its codec: 103 and 104 are H.264 media and RTX, 101 and 102 AV1 media and RTX. An RTX payload type on a primary SSRC, or a media payload type on an RTX SSRC, is counted malformed and changes nothing. A stream's receiver is created for the codec of its first packet; a packet of another codec on the same SSRC replaces the receiver (its buffer, statistics and keyframe state), so each switch restarts at a keyframe of the new codec.

### RTP payload
- The payload is an aggregation header and OBU elements. Header bits: `Z` (0x80) the first element continues the previous packet's last one, `Y` (0x40) the last element continues in the next packet, `W` (0x30) the element count (0: every element is prefixed with a LEB128 length; 1–3: exactly that many elements, the last without a length), `N` (0x08) the first packet of a new coded video sequence, and three reserved bits that must be zero (a strict-zero policy; the specification does not say how receivers treat them). `N` with `Z`, or `N` anywhere but a frame's first packet, is malformed. An element is an OBU header, its optional extension byte, and its payload, normally with `obu_has_size_field` cleared; a size-bearing OBU is accepted (the specification only says it SHOULD NOT be sent) when its size matches its element exactly. LEB128 values are at most eight bytes, at most 2^32 − 1, and elements are never empty.
- OBUs are validated as they are joined: forbidden and reserved bits zero, an extension byte present when flagged with its reserved bits zero, types 1–8 and 15 only, and one temporal/spatial layer per packet. Fragments are joined however a header, extension, or length is split across packets. Temporal delimiters (type 2) and tile lists (type 8) are discarded as the format requires; padding (type 15) is kept. A frame, its packets, and its elements are bounded (2 MiB, 2,048 packets, 4,096 elements), and a depacketizing error leaves no output.
- **DAVE seals the whole temporal unit first.** davey's AV1 transform drops temporal delimiters, tile lists, and padding, leaves each kept OBU's header, extension byte, and (for every OBU but the last) canonical minimal LEB128 size readable and authenticated, encrypts the payloads, and clears `obu_has_size_field` on the final OBU, which then has no size and runs into the DAVE trailer. The receiver rebuilds exactly those bytes (`Framing::Dave`: the same OBUs with only the last unsized), DAVE opens them, and `av1::normalize` restores the final size afterwards, so nothing is rewritten inside DAVE's authenticated range. What reaches the consumer is `ReceivedVideo { codec: Av1, data }` with the frame as minimal low-overhead OBUs (every OBU sized, no temporal delimiter), which is what the decoder takes.
- **Keyframes.** A frame header is encrypted, so nothing inside the sealed frame can be inspected: the first packet's `N` bit is the keyframe signal (`ReceivedVideo::keyframe`, a coded video sequence start). Until a keyframe arrives, or after any abandoned, undecryptable, refused, malformed, or untaken frame, frames are dropped without being opened and a PLI is requested (at least 500 ms apart per stream). A keyframe whose first packet lacks `N` does not restart the stream, and a repaired first packet keeps its `N` bit.
- Loss repair is the H.264 section's: Generic NACK after a 10 ms reorder grace, RTX on payload type 102 and the stream's RTX SSRC (the original sequence number, then the original payload), a 200 ms frame deadline, receiver reports. A lost marker packet shows as a hole only once a later packet arrives; a lost first packet of a stream's first frame is never known to exist, and the partial frame is refused by the depacketizer.
- A decoder that loses a frame, or cannot keep up, asks for a keyframe through `MediaSender::request_video_keyframe(ssrc)`: the stream's receiver waits for a keyframe exactly as after a lost frame and a PLI follows. A request for SSRC 0 is an error; one for an SSRC that has no receiver changes nothing.

### Decoding
- `fastcord-video::av1::Decoder` is dav1d 1.5.4, compiled statically from the unmodified source in `crates/fastcord-video/native/` (commit `54706fc6bc0cdecab7e9593974a4039cc038fca7`, SHA-256 `9edb11a2108b375cc58370354e705feebc93430bb780130363815c1e1ac0c250`, verified by `build.rs` before unpacking into the build's output directory; the portable C implementation, `HAVE_ASM=0`, so no assembler is needed). It runs in-process, single-threaded and synchronous, with fastcord's own picture allocator (reusable slots, at most 256 MiB retained) and a 2 MiB input buffer. Its native context is opened by the first valid temporal unit and closed by `reset`, by drop, and by any decode failure (dav1d keeps a frame it gave up on, and a reference to the input buffer it was given, until it sees another frame header, so a failed context is never reused; the next keyframe opens a new one).
- A temporal unit is one RTP frame. Input must be sized low-overhead OBUs (a temporal delimiter is optional); malformed OBU framing is refused before native state is touched. Pictures are limited to 4096 per side and 4096 × 2304 pixels. Output is the borrowed NV12 contract: 8-bit 4:2:0 luma is borrowed from the native picture without a copy; 10/12-bit samples are shifted down by 2/4 (no tone mapping or dithering), 4:2:2 and 4:4:4 chroma is box-averaged to 4:2:0, monochrome gets neutral chroma, and an identity-matrix (RGB) stream is refused. In-loop filters and film grain are applied. The input timestamp (the 90 kHz RTP timestamp as nanoseconds) comes back with its picture.
- The app starts one codec-owning decoding thread per visible watched stream at its first H.264/AV1 keyframe, with an encoded queue bounded to 4 frames and 6 MiB. Queue overflow or decode failure drops the dependent chain, requests a keyframe, and restarts there; failed keyframes receive at most three consecutive requests. Codec/SSRC changes discard old references. Hiding/minimizing suspends decoding and releases native references on the owner thread; resume requests one keyframe. The renderer consumes bounded frame leases through the latest-frame slot below.

### Not established (verify live, see docs/TESTING.md)

## Video playback handoff (milestone 28)

- Watching is an explicit opcode-20 action; Stop watching queues opcode 19 and closes its generation's latest-frame slot immediately. There is one watch at a time. Available offers are bounded keys from `self_stream` voice states in the parent voice channel, excluding this account. The pane can be hidden without unwatching so text navigation remains usable. Parent voice is not replaced; leaving/moving the parent voice channel ends the old watch.
- Pixels never enter iced's ordered message channel. A decoder callback copies visible NV12 rows once into a reusable lease; padding is skipped without changing the visible crop. A pool retains at most three Arc-backed buffers and 48 MiB of owned allocation capacities, with newest pictures dropped visibly when all leases are in use. One latest-frame slot replaces stale pictures; at most one outstanding readiness notification enters iced until consumed. A stale worker can update only its own watch generation.
- Windows/macOS H.264 decoders and dav1d preserve color matrix (BT.601, BT.709, BT.2020 nonconstant-luminance), full/limited range and sample aspect ratio. H.264 SPS VUI provides a fallback where native output attributes omit them; explicit unsupported matrix values are refused. AV1's sequence metadata and display render dimensions are preserved. Unspecified metadata uses documented defaults; HDR tone mapping and constant-luminance BT.2020 are not implemented.
- iced's `shader::Program` and exact re-exported wgpu version prepare/render integration reuse a single `R8Unorm` Y / `Rg8Unorm` UV texture pair. Upload is the one render-thread transfer allowed by SPEC §8.6; codec work and repacking remain on the worker. A shader applies the color rows and avoids a second sRGB transfer on sRGB targets. Display/sample aspect ratio is letterboxed across resize. Texture replacement happens only for a resolution change; an unused/closed watch is trimmed, not cached indefinitely.
- Only the no-native-adapter fallback uses tiny-skia. Its worker converts directly from borrowed NV12 into one leased opaque BGRA buffer using the same color coefficients; the app compositor blends that borrowed pixmap. Neither path encodes PNG/JPEG or creates an image handle per video frame.
- Readiness subscriptions exist only while the watch pane is visible, the window is active/nonzero-sized and no attachment/settings/emoji view covers it. There is no playback animation timer. Visibility wakes the stream task immediately even if no media arrives, clears encoded work, and frees native decoder references on its owner thread; resume starts at a fresh keyframe. Unwatch/logout closes the generation before cancelling the RTC task, allowing all CPU leases and reusable GPU planes to be released.
- This handoff changes no RTP/DAVE framing or payload-type assumptions. Actual official-client watch interoperability (U3/U4), resize/minimize/reopen under a real stream, and repeated-cycle process/GPU memory acceptance remain live gates; native decoded fixture-window checks are not a substitute.

## Windows screen-share send (milestone 29)

Implemented by `fastcord-platform::capture` (sources, Windows.Graphics.Capture, conversion), `fastcord-video::share` (the encode pipeline) and the app's `gateway::stream_share` (the Go Live lifecycle and the stream RTC task). The Go Live signaling and the stream session are those of milestones 24 and 25; this section is what the owner adds. **Nothing here was captured from a live session**; the unverified assumptions are at the end and in `docs/TESTING.md`.

### Lifecycle
- The user picks a screen or window. The capture starts first; only when the OS accepted it (`StartCapture` succeeded) does the worker send opcode 18 `{"type": "guild", "guild_id", "channel_id"}` (`"call"` without a guild for a private call) for the joined parent voice channel. A refused permission, a stale handle or an unsupported OS therefore never creates a stream.
- STREAM_CREATE (admitted only for the key this account's create produced) and STREAM_SERVER_UPDATE open the stream's own voice-v8 session with `connect_with_video(.., VideoOptions::share(SendOptions::SCREEN_720P30))`: Identify `video: true` with one `screen` layer, Select Protocol with H.264 encode and decode and AV1 decode, DAVE group `rtc_server_id - 1`. The parent voice session, its microphone engine and its DAVE group are not touched.
- Nothing is encoded until the connection attached its frame sink **and** Session Description selected H.264 for us (`VoiceEvent::VideoNegotiated`). Any other codec, or no layer, fails the share with a visible message. Opcode 12 (the layer announcement), pacing, retransmission and RTCP are the driver's (milestone 25).
- Feedback: `KeyframeRequested` (PLI/FIR, coalesced to one per 300 ms by the driver) makes the next picture an IDR, delivered at once even for a static screen (the capture thread is woken and redelivers its newest picture); `VideoBitrate` reaches the encoder in place (`CODECAPI_AVEncCommonMeanBitRate`; an encoder that cannot is reopened at an IDR), clamped to 64 kbit/s and the 2.5 Mbit/s layer bitrate; `VideoActive(false)` (Media Sink Wants 0) stops encoding and slows capture to one picture a second, and resuming asks for a keyframe. A unit the transport refuses (full queue, over 2 MiB) restarts the stream at a keyframe, self-requested at most every 300 ms. A static screen is resent about once a second.
- The share ends on Stop sharing, the source closing, a capture permission refusal, an encoder failure, a stream session failure, STREAM_DELETE for the owner's key (Discord's reason is shown: `unauthorized`, `stream_full`, `safety_guild_rate_limited`, …), leaving or moving the parent voice channel, or a new READY. The capture thread is stopped and joined (at most 3 s, off the async worker), the stream task is aborted, and opcode 19 `{"stream_key"}` is sent when the stream had been created and the Gateway session is still the one it belonged to (not on leave or READY, where the server already ended it).

### Capture and conversion
- Sources: displays (`EnumDisplayMonitors`, primary first, labelled `Screen N - WxH`) and top-level windows (`EnumWindows`: visible, not minimized, not DWM-cloaked, titled, not a tool window unless it asks for a taskbar button, not a desktop shell class, at least 48×48, never this process), at most 128, titles at most 120 characters. Titles are never logged.
- One MTA owner thread per session (the process keeps its MTA alive with `CoIncrementMTAUsage`); a free-threaded WGC frame pool of three BGRA buffers (the OS's two plus the newest picture kept for redelivery), at most 4096×2304 pixels and 8192 per side (larger sources fail with a size error rather than being cropped); the OS capture border and cursor stay at their defaults. `GraphicsCaptureItem.Closed` and a per-iteration liveness check end the session as `SourceClosed`; `E_ACCESSDENIED` is "permission denied".
- The output is the source scaled down to fit 1280×720 with its aspect ratio (never upscaled, even edges, at least 16), converted to NV12 in BT.709 limited range by a D3D11 video processor (a CPU box-filter converter is the fallback when the processor cannot be built or refuses a frame, reported as `Converting(Cpu)`; a software-only D3D device uses it directly). Pictures are paced to at most 30 per second on their capture timestamps, with the newest picture delivered at its slot rather than lost. A new source size takes effect after it has held for 300 ms (pictures in between are stretched to the old size), then the encoder is reopened at the new size and the stream continues at an IDR.
- Timestamps are relative to the first picture and at least 1 ms apart; the transport maps them onto the 90 kHz RTP clock (milestone 25).

### Not established (verify live, see docs/TESTING.md)
Whether the official client accepts the H.264 stream without a profile in Select Protocol, and renders its colors correctly when the encoder's SPS carries no VUI color description (fastcord's own decoder assumes BT.709 limited range; the capture converts to exactly that, but nothing signals it); whether Discord answers a Go Live from this client profile (U1b) and what STREAM_DELETE reasons occur in practice; whether `Media Sink Wants` 0 arrives when nobody watches (the pause path is tested against fakes only); the encoder bitrate honored by the hardware transform within the layer's ceiling over a real network; resource figures for SPEC §12.

Implemented in `gateway/decode.rs` (`presence_of`), `state/presences.rs` and `fastcord-discord::presence` (REST). Shapes come from community user-client documentation and are **unverified** against a live account.

- Incoming: READY `presences` (`[{ "user": {"id"}, "status", "activities" }]`), READY_SUPPLEMENTAL `merged_presences.friends` (`[{ "user_id", "status", "activities" }]`) and `PRESENCE_UPDATE` (`user.id` or `user_id`, `status`, `activities`, optional `guild_id`/`client_status`, both ignored). Each entry is read on its own; non-objects and entries without a non-zero user ID are skipped. `status` is one of `online`, `idle`, `dnd`, `invisible`, `offline`; any other string counts as omitted. Only an activity of type 4 (custom status) is kept, as its `state` text (128 characters). An omitted `status` or `activities` leaves what is held as it is; an `activities` array without a custom status clears the text.
- Honesty: only presences that are sent are shown. A user with no entry has an unknown presence and gets no dot (never drawn as offline); `offline` is drawn grey. `invisible` is shown for the account itself only when its own settings say so; nothing is inferred from activity.
- Subscriptions: user accounts receive friend presences on their own, so fastcord sends no presence subscription (opcode 37 stays guild-only). Instead the store admits a presence only for a referenced user (relationship, direct-conversation recipient, member of a retained member list or guild member, the account) and prunes entries on RELATIONSHIP_REMOVE, CHANNEL_DELETE, recipient/guild-member removal and guild removal. At most 2000 are held; READY replaces the table.
- Own status: `PATCH /users/@me/settings` with `{"status": "online"|"idle"|"dnd"|"invisible"}` or `{"custom_status": {"text": "..."}}` (`{"custom_status": null}` clears). This is the web client's legacy settings call; Discord stores it and echoes PRESENCE_UPDATE to every session, so Gateway opcode 3 is not used (it would not persist across reconnects). One request per click, never retried by the program. The confirmed choice is shown until the table's own entry changes.
- Not established: whether modern accounts accept the legacy settings PATCH or require `user_settings_proto` (a base64 protobuf), whether the echo for `invisible` reaches the same session, and what the account's own initial status in READY looks like.

## Typing indicators (#69)

Evidence: community documentation of `TYPING_START` and `POST /channels/{id}/typing`; no live capture exists and the fixtures are synthetic.

- Incoming: `TYPING_START` (`channel_id`, `user_id`; `timestamp`, `guild_id`, `member` are ignored). A `TypingTable` in `fastcord-discord::typing` keeps at most 4 people per channel and 32 overall, each lapsing 10 s after the event on a local monotonic clock (the server timestamp is not trusted). The account's own events are ignored; a `MESSAGE_CREATE` by that author, `CHANNEL_DELETE`, READY and RESUMED clear entries. Names come from the store's users ("Someone" if unknown); one name reads "X is typing…", two "X and Y are typing…", more "Several people are typing…".
- No periodic work: the worker arms one sleep until the next entry lapses only while the table is non-empty.
- Outgoing: `POST /channels/{id}/typing` with no body, user-write priority, never retried. Sent only for text edits of a new message (not cursor moves, not while editing a sent message, not on an empty draft), while the window is active, in the open channel where sending is allowed, at most once per 8 s per channel (`TypingSend`). Failures (401/403/404/429) are dropped silently; the only cost is a missing indicator for others.
- Not established: whether threads and group DMs accept the same route for the user client, and whether the sending session receives its own `TYPING_START`.

## GIF picker (#70)

`GET /gifs/trending` and `GET /gifs/search?q=...` (both with `provider=tenor&locale=en-US&media_format=gif`) answer a bare array or `{"gifs":[...]}` of `{title,url,preview,gif_src,src}`; unverified against a live account. `url` (https only) is what a message carries; previews are fetched without `Authorization` through the credential-free fetcher and are the only traffic to the GIF provider. ## Stickers (#71)

- Received: `sticker_items` on a message (`{id,name,format_type}`, at most 3 kept, names cut to 64 characters). `format_type` 1 PNG and 2 APNG are fetched as `https://cdn.discordapp.com/stickers/{id}.png?size=160`, 4 GIF as `https://media.discordapp.net/stickers/{id}.gif?size=160`, both without `Authorization` through the credential-free cache and shown as a static first frame. 3 (Lottie) and unknown formats are shown by name. Unverified against a live account.
- Listing: `GET /guilds/{id}/stickers` for the viewed server only, as an array of `{id,name,format_type,available}`; stickers with `available:false` are shown but cannot be picked. Standard packs and other servers' stickers are not offered (Nitro); in DMs the picker explains this.
- Sending: `POST /channels/{id}/messages` with `content:""`, `sticker_ids:["<id>"]`, a fresh nonce and `enforce_nonce:true`, once, never retried. It does not go through the text outbox: success is recognized when the message arrives over the Gateway; a 4xx is reported as not sent and an ambiguous failure as possibly delivered.

## Message forwarding (#72)

- Received: a forward is an ordinary type-0 message whose `message_reference` has `type: 1` (plus the source `message_id`/`channel_id`/`guild_id`) and a `message_snapshots` array of `{message:{content,timestamp,edited_timestamp,type,flags,attachments,embeds,sticker_items,mentions,mention_roles}}`. At most one snapshot is kept (a malformed entry is skipped, not fatal); it is shown only when the reference type is 1. The snapshot is rendered, never the original: the source ID is not looked up, jumped to or used for a reply line (`replied_to` already requires message type 19), so edits or deletion of the original, and its access restrictions, change nothing. Snapshot attachments are keyed by the forwarding message's ID, so previews, downloads and signed-URL refresh work like ordinary attachments. Unverified against a live account.
- Sending: `POST /channels/{dest}/messages` with `content:""`, `message_reference:{type:1,message_id,channel_id,guild_id?,fail_if_not_exists:true}`, a fresh nonce and `enforce_nonce:true`, once per destination, never retried. It does not use the text outbox (a forward has no draft to restore): the result is shown per destination, an ambiguous failure is reported as possibly delivered and that destination is never sent to again, a 4xx may be retried by the user. Several destinations are separate concurrent requests under the shared rate limiter.
- Optional note: sent as a separate ordinary message to the same destination only after its forward was confirmed, once, with its own nonce (the forward body itself carries no text). Whether the official client sends it this way is not established.
- Boundaries: re-forwarding a forward is not offered; destinations are limited to the sendable channels of the open server and the sidebar conversations; at most five per action.

## Inline audio playback (#74)

- No new routes. The attachment is fetched exactly as for Open: the credential-free CDN client, redirects revalidated hop by hop, one refresh through `POST /attachments/refresh-urls` after a 403/404, the 64 MiB (`MAX_FILE_BYTES`) ceiling, the account-scoped disk LRU. The signed URL and the token never reach the player; it only receives a local file path. 401/403/404/429 are therefore the attachment cache's existing handling and are shown with fixed texts.
- Container and codec: Ogg (RFC 3533) pages, CRC-32 checked, first logical stream only; `OpusHead` (RFC 7845) version 0, channel mapping family 0, 1 or 2 channels; every packet at most 1500 bytes and exactly 20 ms by its TOC (RFC 6716 section 3.1). Pre-skip is not trimmed from the start, the final granule is not used to trim the end, the output gain field is ignored. Voice messages from official clients (`audio/ogg`, `voice-message.ogg`) are expected to satisfy this; that is unverified against live attachments.
- `waveform`/`duration_secs` do not affect decoding; the player's duration comes from the last page's granule position. They are used only to draw the voice-message row (see Voice messages, #75).

## Voice messages (#75)

- Received: a voice message is an ordinary message whose `flags` has `1 << 13` (`IS_VOICE_MESSAGE`) and one `audio/ogg` attachment (`voice-message.ogg`) carrying `duration_secs` (a number of seconds, kept only when finite and 0..=86400) and `waveform` (base64 of up to 256 loudness bytes, 0-255; kept only up to 512 characters, otherwise dropped). The same fields on an attachment without the message flag are also treated as a voice message. The row shows a Play button, up to 64 bars (the loudest sample of each group) coloured by playback progress, and the sender's length; playback is the inline Ogg Opus player (#74) on the selected output device, started only by a click. Playback speed is not offered. Unverified against live attachments.
- Recording is a **compatibility-gated extension**: Discord's help article documents recording and sending for the mobile apps only, so nothing here is an existing desktop feature. It is off until "Voice message recording (experimental)" is turned on in the audio settings, and the panel says it is unverified. The wire shape is taken from the public bot documentation and has not been confirmed for a user account.
- Upload: the existing cloud-upload path unchanged: `POST /channels/{id}/attachments` with `{files:[{filename:"voice-message.ogg", file_size, id:"0"}]}`, then a `PUT` of the bytes to the returned storage URL by the credential-free uploader.
- Message: `POST /channels/{id}/messages` with `content:""`, `flags:8192`, a fresh nonce and `enforce_nonce:true`, and `attachments:[{id:"0", filename:"voice-message.ogg", uploaded_filename, duration_secs, waveform}]`, once, never retried by the program (the ordinary outbox rules apply: a definite refusal can be retried by the user, an ambiguous result is shown as possibly delivered). A voice file must be the only file and the message has no text (refused locally otherwise, never sent as an ordinary file). No header, property or client identity is changed for it.
- Audio: mono Opus at 32 kbit/s, 20 ms frames, from the selected input device and noise suppression (echo cancellation off), written as an Ogg Opus file (`OpusHead` pre-skip 312, CRC-checked pages, last page marked end of stream). At most 5 minutes (15 000 frames, about 1.2 MB), at least 0.5 s. The waveform is 256 loudness bytes (fourth root of the frame RMS, the loudest frame per span).
- Denial (401/403/404/429, a refused flag or attachment) surfaces as the outbox's fixed failure text with Retry and Discard; nothing is spoofed or retried automatically.

## Inline video playback (#116)

- No new routes: the same cached local file as for audio. The container is chosen by content (`ftyp`/`moov`/`mdat` after four size bytes for MP4, the EBML magic for WebM/Matroska, `OggS` for Ogg), never by file name or content type.
- MP4 (ISO 14496-12, QuickTime): `moov` is read whole (at most 16 MiB, before or after `mdat`); sample tables `stts`, `ctts` (version 0 and 1), `stss`, `stsz`, `stsc`, `stco`/`co64` and the first non-empty `elst` entry give each sample's offset, size and presentation time (milliseconds, rounded down). Video: `avc1`/`avc3` with `avcC` (length-prefixed NAL units are rewritten to Annex B, SPS/PPS placed before keyframes) or `av01` with `av1C` (sized OBUs as stored, the configuration's sequence header placed before keyframes). Audio: `Opus` with `dOps` (version 0, 1 or 2 channels, mapping family 0). `mp4a` with `esds` (object type 0x40) is played when its AudioSpecificConfig is AAC-LC with 1024-sample frames and one or two channels (ADR 0008), otherwise skipped. Fragmented MP4 (`mvex`, `moof`) is refused.
- WebM/Matroska (RFC 9559): EBML header `DocType` `webm` or `matroska`; `Segment` and `Cluster` of known or unknown size; `SimpleBlock` and `BlockGroup` (`Block` plus `ReferenceBlock`) in decoding order; `V_MPEG4/ISO/AVC` (`avcC` as `CodecPrivate`), `V_AV1` (`av1C` as `CodecPrivate`), `A_OPUS` (`OpusHead` mapping family 0), `A_AAC` (AAC-LC `CodecPrivate`). Lacing and `ContentEncodings` are not supported.
- Limits: 400 000 samples per file, 8 MiB per sample, 16 MiB of metadata, a sample range past the end of the file is `Malformed`. Opus packets must be 20 ms by their TOC byte, like Ogg. Offered by `.mp4`/`.m4v`/`.mov`/`.webm`/`.mkv` or `video/mp4`, `video/webm`, `video/quicktime`, `video/x-matroska`; whether a given file plays is decided after fetching it. Unverified against live attachments from the official clients.

## Polls (#73)

- Received: a message may carry `poll:{question:{text}, answers:[{answer_id, poll_media:{text, emoji?}}], expiry, allow_multiselect, layout_type, results:{is_finalized, answer_counts:[{id, count, me_voted}]}}`. At most 10 answers are kept (a malformed one is skipped), the question is cut at 300 and each answer at 55 characters, counts at 10 entries. Poll text is never logged. Unverified against a live account.
- Create: `poll:{question:{text}, answers:[{poll_media:{text}}], duration:<hours 1..768>, allow_multiselect, layout_type:1}` in `POST /channels/{id}/messages` with `content:""`, a fresh nonce and `enforce_nonce:true`, once. Permission to create polls is not modelled locally; Discord's refusal is shown.
- Vote: `PUT /channels/{id}/polls/{message}/answers/@me` with `{answer_ids:["1","3"]}`, the complete selection (empty withdraws), once per click and at most one request per poll in flight. Setting a selection is idempotent, so an explicit retry after an ambiguous failure cannot double a vote. The local result is applied as the same per-answer changes the Gateway reports, so whichever of REST answer and event arrives second is a no-op.
- End: `POST /channels/{id}/polls/{message}/expire` (the author's own poll), answered with the message; the poll is marked finalized locally even if the copy lags.
- Voters: `GET /channels/{id}/polls/{message}/answers/{answer}?limit=26` answered with `{users:[...]}`, only on request; at most 25 are shown.
- Gateway: `MESSAGE_POLL_VOTE_ADD` / `MESSAGE_POLL_VOTE_REMOVE` `{user_id, channel_id, message_id, guild_id?, answer_id}` change the counts of a held message only when that alters it (the account's own vote sets `me_voted` and counts once; a removal with nothing to remove, an unknown answer and a repeat change nothing). A vote for an uncached message makes a history page in flight stale. `MESSAGE_UPDATE` carrying `poll` replaces the held poll except that a finalized poll is never replaced by an unfinalized one. After a reconnect the poll is whatever the next history page or update reports; counts are not reconstructed from missed events.
- Unverified: all routes and bodies above come from public/community documentation, not a captured user-client session; whether the account receives the vote events for every channel it can read is also unverified.

## Message actions (#76)

- Link: `https://discord.com/channels/{guild|@me}/{channel}/{message}`, built locally from IDs the account holds (guild is the selected server, `@me` in conversations). A clicked link is parsed only if it is `https` on `discord.com`, `ptb.`/`canary.discord.com` or `discordapp.com` with exactly four numeric/`@me` segments; nothing is fetched to resolve it.
- Embeds: `PATCH /channels/{channel}/messages/{message}` with `{"flags":4}` to hide link previews and `{"flags":0}` to restore them (`SUPPRESS_EMBEDS = 1 << 2`), sending only that bit because Discord documents it as the only editable flag. The answer is the full message; it is applied with the edit path's partial update (skipped when a later `edited_timestamp` is already held). Allowed by the client for the account's own messages, and for others' only where the selected server channel grants Manage Messages; Discord stays authoritative (403 is reported). Sent once; the same state applied twice changes nothing, so the user may repeat it after an ambiguous failure. Unverified against a live account.
- Silent: a draft whose first word is `@silent` (any case, followed by whitespace or end) is sent with `flags: 4096` (`SUPPRESS_NOTIFICATIONS`, OR-ed with the voice flag when applicable) and the prefix removed, as the official clients do. The send is otherwise the ordinary nonce-enforced one.
- Uploads: a spoiler is a `SPOILER_` prefix on the filename in both the `POST /channels/{id}/attachments` slot request and the message's `attachments[]`; alt text is `description` (at most 1024 characters, omitted when empty) in the message's `attachments[]`.
- Removing attachments in an edit: `PATCH` with `attachments:[{"id":"…"}]` listing exactly the attachments that stay (Discord replaces the message's list with it); omitted entirely when none is removed, so a text-only edit still preserves attachments. Whether Discord keeps a kept attachment's description/spoiler when only its `id` is listed is not established.

## Unified inbox (#77)

- **Unread** is not a request: the reducer's read table (`READY.read_state`, `MESSAGE_ACK`, `MESSAGE_CREATE` effects, `USER_GUILD_SETTINGS_UPDATE` mutes) is queried by `Navigation::inbox`, the same `Store::unread` that draws the channel badges. A conversation is listed when it has an unread flag (newer than the cursor and not muted) or mentions; categories, voice channels and channels the account cannot open are left out; at most 64 rows with names capped at 256 bytes are copied, with the full count and mention total. Mentions first, then newest message first.
- **Mentions list:** `GET /users/@me/mentions?limit=25&roles={bool}&everyone={bool}[&before={message_id}]`, `UserRead` priority, sent once per user action (open the tab, Refresh, Load more, filter toggle). The answer is a bare array of at most 25 messages, newest first; a longer or malformed body is refused. A full page offers "Load more" with `before` set to the last ID held. Messages carry the channel (and, when sent, the guild); the app opens them by channel ID alone (a held DM, or an openable channel of a held guild, selecting the guild first). Items are previews (author 64 characters, text 200) capped at 100 items and 64 KiB; duplicates are dropped by message ID. The list is never written to disk, never feeds `notify`, and is dropped on close, logout or account change.
- **Mark read:** `POST /channels/{id}/messages/{id}/ack` with `{"manual":true,"mention_count":0}` for the newest message the store holds, through the existing acknowledgement path. Requests are serialized (one in flight), at most one waiting per conversation (128 waiting), never retried; a 401 stops the account. The local cursor moves only after Discord accepted it; the echo (`MESSAGE_ACK`) also converges it. This one is immediate.
- **Automatic acks** (the newest message is on screen in the focused window): `{"token": <string or null>}`. At most one per channel per 3 s: the first goes out at once, later ones wait and the newest message seen goes when the 3 s end; leaving the channel sends the waiting one once, or drops it when a newer ack already went out. Discord's answer carries a `token`; it is kept per channel in memory (cleared on READY, at most 128 channels, at most 1 KiB each) and sent in the next automatic ack instead of `null`. The manual body carries no token (unverified whether Discord wants one). Unverified against the live service: the token semantics come from community documentation.
- **Mute / unmute a conversation:** `PATCH /users/@me/guilds/{guild_id|@me}/settings` with `{"channel_overrides":{"{channel_id}":{"muted":true|false}}}` (`UserWrite`, once; `@me` for DMs and group DMs). The listed state changes only when `USER_GUILD_SETTINGS_UPDATE` arrives. The inbox mute sends no duration (it is the "until I turn it back on" mute below).
- Jump: opening a row selects the conversation and then uses the existing first-unread jump; a mention uses the existing `JumpTo`. A conversation that never opens ends the wait after 10 s with the usual "cannot open" notice.
- Excluded: Nitro message bookmarks and reminders.

## Free profile editing (#79)

Each request is sent once, on one explicit click, at `UserWrite` priority, with at most one in flight from the panel; none is retried, a 401 stops the account, and the display changes only from Gateway events. Wire shapes are from community documentation of the official client and are unverified live.

- **Display name:** `PATCH /users/@me` `{"global_name":"..."}` (trimmed, at most 32 characters); empty sends `null`. The answer is parsed as the user object but the display follows `USER_UPDATE`.
- **Avatar:** `PATCH /users/@me` `{"avatar":"data:image/<png|jpeg>;base64,..."}` or `{"avatar":null}`. The same bounded helper as group icons (`image_data`: signature check, 512 KiB cap, base64 inside the 1 MiB request budget) but GIF is refused, since an animated avatar needs Nitro. Server-reported eligibility stays authoritative.
- **Bio and pronouns:** `PATCH /users/@me/profile` with only the changed fields (`bio` at most 190, `pronouns` at most 40 characters). Current values come from one `GET /users/{me}/profile` when the panel opens; without it the fields are read-only.
- **Own nickname:** `PATCH /guilds/{guild}/members/@me` `{"nick":"..."|null}` (at most 32, for the selected server); the nickname shown is from `GUILD_MEMBER_UPDATE`, which also drives voice participant names.
- **Connections:** `GET /users/@me/connections` when the user clicks Load (at most 32 kept, names capped); `PATCH /users/@me/connections/{type}/{id}` `{"visibility":true|false}`. `type` and `id` must be `[A-Za-z0-9_.-]` or the row is read-only. The new state is shown from the success answer (no event exists for it).
- **`USER_UPDATE`:** applied only when it carries the account's own ID, as a whole-object replace (a replay is silent). It sets `Changes::account` and the snapshot's `current_user`.
- **Contextual identity:** no new request. `NavigationSnapshot` carries `members` (held members of the selected guild, at most 1024, nickname clipped to 128 bytes, role IDs) and `guild_roles` (at most 250, highest position first, `@everyone` omitted), rebuilt only with the snapshot. Message authors show `members[author].nick`, else `global_name`, else `username` (empty in DMs); the profile card shows the nickname, the roles of a held member and the presence table's custom status. A member that is not held is not described. Role colours are not in the model and are not drawn. The message `member` field is still not ingested.
- **Not done by design:** username change (needs the password and possibly 2FA/CAPTCHA, shown as a pointer to the official client), banner, animated avatar, theme colors, effects, per-server profile cosmetics. A 400 is explained as a limit or verification only the official client can complete; the typed values are kept.

## Push-to-talk and communication shortcuts (#82)

No new wire message. Push-to-talk, push-to-mute and the voice-activity threshold decide only which 20 ms Opus frames reach the voice connection, so the existing rules apply unchanged: a Speaking (op 5, `speaking: 1`) before the first frame after silence, and `end_speech` (five `F8 FF FE` frames, then `speaking: 0`) when frames stop. The call worker ends the burst when the gate closes, and 100 ms after the last sent frame when a level gate stops them. Opcode 4 `self_mute`/`self_deaf` still mean only the toggled mute and deafen; push-to-talk and push-to-mute are local and never change the voice state Discord shows.

- **Gate:** the microphone is open when there is no server mute, self mute, deafen or held push-to-mute, and, in push-to-talk mode, the key is held or inside its release delay. A guild voice channel whose permissions lack `USE_VAD` forces push-to-talk, as the official client does; DMs and group calls have no such restriction. A server mute or deafen (VOICE_STATE_UPDATE `mute`/`deaf`) can never be overridden locally.
- **Level gate (voice activity only):** the frame RMS after noise suppression is compared with `-n` dBFS (1-100); it opens at the threshold, stays open 10 frames (200 ms) after the last frame at or above it, and counts a frame within 3 dB below the threshold as still speech. Automatic sends every frame, as before.
- **Global listener:** Windows `WH_KEYBOARD_LL` on a dedicated thread; the hook passes every key on unchanged. Injected (software-generated) key events are treated like real ones. macOS needs an event tap with Accessibility permission, X11 an `XRecord`/grab client and Wayland the GlobalShortcuts portal; none is implemented, and each is reported with its reason. Wayland compositors do not deliver keys of other windows to an application, by design.

## Camera in calls (#84)

Implemented by `fastcord-media` (`VideoOptions::camera`, `MediaSender::set_video_sending`, `set_video_users`), `fastcord-platform::capture` (camera source), `fastcord-video::share` (`start_camera`, `PreviewSink`) and the app's `gateway::camera`. It reuses the H.264/AV1 transport of milestones 25-26 unchanged. **Nothing below was captured from a live session**; the unverified assumptions are listed here and in `docs/TESTING.md`.

- Identify (op 0) on a call connection: `video: true` and `streams: [{"type": "video", "rid": "100", "quality": 100, "max_bitrate": 1500000, "max_framerate": 30, "max_resolution": {"type": "fixed", "width": 1280, "height": 720}}]` (a screen share offers `"type": "screen"`). Select Protocol lists H.264 (encode and decode) and AV1 (decode) exactly as for a share. A platform without camera capture sends no `streams` and offers decode only.
- Session Description (op 4) `video_codec` and Session Update (op 14) choose the codec this client may send; anything but `H264` (or no layer) sends nothing and is surfaced as `VideoNegotiated { codec: None }`, which pauses the camera.
- Opcode 12 from us: right after Session Description a camera connection declares `{"audio_ssrc", "video_ssrc": 0, "rtx_ssrc": 0, "streams": []}`; the first frame after the camera is turned on announces the layer (`type: video`, `active: true`, the READY SSRCs) before its first RTP packet; turning the camera off announces `active: false`. RTP of a camera carries abs-send-time, playout-delay and the RID extension, and **no** video-content-type (a share's `1` = screenshare).
- Opcode 15 from us: `{"<ssrc>": 100, "any": 0}` for each user whose tile is on screen that has an active announced stream, re-sent when it changes and after RESUMED; `{"any": 0}` when nothing is on screen. A share viewer still wants every announced stream. From the server to us: the owner rules of the H.264 section (`{"<our ssrc>" or "any": quality}`; 0 pauses the layer, above 0 resumes it and caps the bitrate).
- Opcode 4 (main Gateway): `self_video` is true while the camera is live (capturing and H.264 accepted), false otherwise and on join.
- Limits: at most six remote camera streams are received at once (the reassembly buffer is 4 MiB each; the received-frame queue is eight frames, at most 16 MiB); a connection remembers at most 16 users' announced streams.
- **Unverified assumptions:** that the user-account voice gateway accepts a `video` layer in Identify on a call (as on a share), assigns SSRCs in READY for it and expects the opcode-12 declare/announce/stop sequence above; that an official client's `self_video` and layer state agree with ours; whether the camera RTP needs content-type or other header extensions; that the same payload types (103/104 H.264, 101/102 AV1) apply on a call; which codec the server selects when an official client has the camera on (U4); simulcast: only the single layer is sent and received.

## Camera backgrounds (#85)

No wire change. The effect is applied to the NV12 picture before it is encoded, so Discord receives an ordinary 720p30 H.264 camera layer exactly as in #84; a blurred or replaced background is not signalled to the server or other participants, and there is no request, event or stored state about it. ## Reporting messages, users and servers (#81)

A report is a submission to Discord, so it is an explicit user action with a review step and is never automatic and never retried. Exactly one `POST` is sent, from the review step's Submit button, at `UserWrite` priority; opening the panel only reads the menu (`UserRead`). A 401 stops the account; logout, account change or Close (not while sending) drops the panel and aborts a menu read. Wire shapes are from community documentation of the official client and are **unverified** against a live account (`docs/TESTING.md`).

- **Menu (server-driven):** `GET /reporting/menu/{message|user|guild}` returns `{name, version, variant, root_node_id, success_node_id?, fail_node_id?, nodes: {id: {header, subheader, children: [[label, id]...], elements, button: {type}}}}`. It is parsed into a bounded tree (`ReportMenu`, at most 512 nodes, 40 choices per node, depth 12, labels cut at 200 and texts at 400 characters; `name`/`version`/`variant` must be short `[A-Za-z0-9._-]` tokens because they are written back; the name must match the target; a child pair is read in either order; a choice to a missing node is dropped). No category is hard-coded: the panel renders whatever nodes Discord sends. A leaf with no `elements`, not a `cancel` button and not the success/fail node is `Submit`; a node with `elements` (details to fill in), a `cancel` button, or the success/fail node is `Unsupported`: shown as "(web form)" and not selectable, with the web form offered.
- **Targets:** a message (`channel_id` + `message_id`; voice messages are messages, labelled as such), a user (`user_id`; from the profile card), a server (`guild_id`; from the server header). Only another person's ordinary messages (types 0/19) offer Report, behind More; nothing is offered for the account itself.
- **Submit:** `POST /reporting/{message|user|guild}` `{version, variant, language:"en", breadcrumbs:[node ids after the root], elements:{}, name, channel_id/message_id | user_id | guild_id}`. The path is re-validated against the menu (every step a real choice, ending on a `Submit` node) immediately before sending. Only IDs and the chosen path are sent; message text, usernames and attachments are not copied (Discord resolves the IDs itself); the review says so. Any 2xx is the receipt; `report_id` (string or number, at most 40 characters) is shown as the reference when present, and an unreadable 2xx body is still a receipt without one.
- **Outcomes:** 2xx is the receipt. 403, 404, 429 and other 4xx are definite refusals ("Nothing was submitted"); 400 and 403 are worded as "rejected, or asks for a challenge or verification only the official client can complete" and offer the web form (a CAPTCHA/verification is never solved or bypassed here). A timeout, connection loss, 5xx or oversized response is ambiguous: "may have been submitted", not sent again automatically, with no resend control. A message that leaves the timeline (deleted, or no longer held) before Submit ends the report with nothing sent; a message deleted after Submit does not rewrite the outcome.
- **Handoff:** where a category needs input this client cannot collect, or a refusal says verification is needed, the panel offers "Open Discord's web form" (`https://dis.gd/report`, unverified link; opened only on click through `open_url`) and, for a message, "Copy message link". It is labelled as the website, not as a report made here.
- **After a report:** Ignore and Block (as two more buttons, once, only when the person is not already ignored or blocked) are separate requests through the existing relationship routes; they are never sent automatically.
- **Privacy:** report targets, labels, excerpts and Discord's answers are never logged; `Debug` of the target, menu, receipt and panel events prints only a kind or a count.

## Message requests, Ignore and privacy (#80)

Every request is sent once, on one explicit click, at `UserWrite` priority (reads at `UserRead`), with at most one write in flight from the panel; none is retried, a 401 stops the account, and what is shown changes only from Gateway events (so another client's change converges the same way). Wire shapes are from community documentation of the official client and are **unverified live**; the accept route in particular is the least certain.

- **Request state:** a private channel carries `is_message_request` and `is_spam` (`Option<bool>`; absent is "not said", neither accepted nor pending). A channel with `is_message_request: true` is a pending request: it is excluded from the DM list, from `select_private_channel`/`open_channel`, from the unread inbox and from incoming-call rings, and listed instead in `NavigationSnapshot::requests` (newest first, at most 100 rows, the total kept). A `CHANNEL_UPDATE` that omits the flags keeps the held values, so an unrelated update never accepts a request; acceptance is `is_message_request: false` or the channel disappearing.
- **Preview:** `GET /channels/{id}/messages?limit=5`, only for a channel that is a pending request, shown as at most 5 clipped lines; no accept, no `POST .../ack`, nothing marked read. Text of a suppressed author is withheld.
- **Accept:** `PUT /channels/{id}/recipients/@me` (route unverified). **Decline:** `DELETE /channels/{id}` (closes the conversation; asks a second click). Both are validated against the current request list again at the click, and the result is shown only when `CHANNEL_UPDATE`/`CHANNEL_DELETE` arrives; an answer that finds the request already gone is not an error shown as a failure.
- **Ignore:** `PUT /users/@me/relationships/{id}/ignore` `{}` and `DELETE` of the same path (unverified). It is a flag, `user_ignored`, on a relationship entry in READY and in `RELATIONSHIP_ADD`/`RELATIONSHIP_UPDATE`; it never changes the relationship type. An entry whose type is none of the four kept ones but carries the flag is kept as an ignore only (`Ready::ignored`, an update with `kind: None`). Rules: an update that omits the flag leaves it; an add never clears it; `RELATIONSHIP_REMOVE` of a kept relationship leaves the ignore (an unfriended user stays hidden) while the removal of an ignore-only entry ends it; a new READY replaces the set. The set holds at most 2000 IDs and is byte-accounted with the relationships.
- **Suppression:** `Store::suppression(user)` is `Blocked` (relationship type 2), else `Ignored`, else none, never for the account itself; `Store::suppressed()` is the shared view the snapshot carries. Consumers: the timeline stand-in (`timeline::hide_suppressed`, applied after the history snapshot, replaces the message with an empty one of the same ID and position and a distinct revision bit), reply quotes (author recorded in `ReplyLine`), the mention list, typing names, desktop notifications (also for requests) and incoming-call rings for one-to-one DMs. Group calls ring because the ring does not name its starter. Unread counts and read cursors are Discord's and are not altered.
- **Privacy settings:** `GET /users/@me/settings` when the user clicks Load; read leniently into `PrivacySettings`: `friend_source_flags` `{all, mutual_friends, mutual_guilds}` (all three booleans or unknown), `default_guilds_restricted`, `restricted_guilds` (at most 256 string IDs, else unknown because it is written back whole) and `explicit_content_filter` (0 to 2 offered). `PATCH /users/@me/settings` carries only the fields the user changed whose value Discord reported; the answer is the settings as Discord has them. `USER_SETTINGS_UPDATE` is decoded into the same fields and kept as a per-field stamped overlay (`PrivacyLive`, reset by READY, stamps never reused): a panel read at stamp N takes events with a higher stamp over its answer and over a local draft of that field. Group-DM add control and the other privacy toggles live in the protobuf user settings and are not implemented.
- **Budgets:** requests listed at most 100 (names capped by `capped_name`), preview 5 lines of at most 200 characters, ignored IDs at most 2000, restricted-server list at most 256, one request in flight, panel state dropped on logout.

## Group DM management (#78)

Every request is sent once, on one explicit click, at `UserWrite` priority, with at most one in flight from the panel; none is retried, a 401 stops the account, and the conversation changes only when the matching Gateway event arrives (so changes made in another client converge the same way). Wire shapes are from community documentation of the official client and are unverified live.

- **Add a member:** `PUT /channels/{channel}/recipients/{user}`, no body. Only a friend who is not already a member can be chosen (never a typed or discovered ID). The result is `CHANNEL_RECIPIENT_ADD`.
- **Remove a member (owner only in the UI):** `DELETE /channels/{channel}/recipients/{user}`; `CHANNEL_RECIPIENT_REMOVE`. Needs a second confirming click.
- **Rename:** `PATCH /channels/{channel}` `{"name":"..."}` (trimmed, at most 100 characters); an empty name sends `{"name":null}`, which restores the member-name label. `CHANNEL_UPDATE`.
- **Icon:** `PATCH /channels/{channel}` `{"icon":"data:image/<png|jpeg|gif>;base64,..."}`, or `{"icon":null}` to remove. The file is read off the UI thread with a hard 512 KiB cap (so the base64 body stays under the 1 MiB request budget), identified by signature (not extension) and never kept. Icons are not downloaded or drawn; the panel shows only whether one is set.
- **Transfer ownership (owner only):** `PATCH /channels/{channel}` `{"owner":"<user id>"}`; `CHANNEL_UPDATE` carries the new `owner_id`. Confirmed first. Whether Discord accepts this for a user account is unverified.
- **Leave a group / close a DM:** `DELETE /channels/{channel}` (the group variant is confirmed first; no `silent` flag is sent from the UI). The DM or group disappears on `CHANNEL_DELETE`; a closed DM returns when opened again (`POST /users/@me/channels`, existing).
- **State:** `Channel` gained `owner_id` and `icon`. A `CHANNEL_UPDATE` with no participants keeps the known list and one without `owner_id` keeps the known owner; `CHANNEL_RECIPIENT_ADD` is idempotent, ignores the account itself and stops at 64 participants; `CHANNEL_RECIPIENT_REMOVE` of the account removes the conversation. The selection snapshot carries the members (names capped, at most 64), owner, custom name and icon presence. Name changes (type 4), icon changes (5) and joins/leaves (1, 2) still render as the generic system lines.
- **Failures:** 403 and 404 and 400 and 429 each get their own wording; a network error or 5xx is "may have been applied, check the list" and is never repeated automatically.
- Not implemented: creating a group from a one-to-one DM (adding to a DM), group-icon rendering, a typed-ID add, `silent` leave.

## Invitations and membership (#90)

Each write is sent once, on one explicit click, at `UserWrite` priority, never retried; a 401 stops the account, and the server list changes only on `GUILD_CREATE`/`GUILD_DELETE`. Responses are read with bounded names; an invite without a `guild` (a group DM invite) is shown as invalid.

Verified offline against synthetic fixtures (`fixtures/rest/invites-synthetic.json`, `invite-list-synthetic.json`, `discovery-synthetic.json`) only; **no route has been captured from an official user client or exercised with the alt account.**

- **Resolve:** `GET /invites/{code}?with_counts=true` (`SpeculativeRead`, no body). Reads `code`, `guild.{id,name,icon}`, `channel.name`, `approximate_member_count`, `approximate_presence_count`, `expires_at`; every count may be absent. `404` with code `10006` ("Unknown Invite") means expired, revoked or unknown. Codes are 2 to 32 characters of `[A-Za-z0-9-]` and are checked before a route is built.
- **Join:** `POST /invites/{code}` body `{}`. Unverified for a user account: the official client may add fields (for example a `session_id`) and may answer with a CAPTCHA (`captcha_key`/`captcha_sitekey`) or verification (`40002`) refusal, which sets the write pause. Other refusals (`403` banned, full, `400`) keep Discord's code and short message (`with_error_detail`).
- **Leave:** `DELETE /users/@me/guilds/{guild}` body `{"lurking":false}`. Unverified; an owner is stopped before the request.
- **Create:** `POST /channels/{channel}/invites` body `{"max_age":<seconds>,"max_uses":<n>,"temporary":false}`; `max_age` is one of 1800, 3600, 21600, 43200, 86400, 604800 (default) or 0 (never), `max_uses` one of 0 (no limit), 1, 5, 10, 25, 50, 100. The response's `code` is shown as `https://discord.gg/{code}`.
- **Permission:** `CREATE_INSTANT_INVITE` (bit 0) of the channel's effective permissions gates Create link; `MANAGE_GUILD` (bit 5) or `MANAGE_CHANNELS` (bit 4), both of the channel's effective permissions, gate Manage invites. The header Invite button shows when any of the three is held.
- **List (unverified):** `GET /guilds/{guild}/invites` (MANAGE_GUILD; every invite of the server) or, with only MANAGE_CHANNELS, `GET /channels/{channel}/invites`; `UserRead`, no body. Reads an array of `code`, `channel.name`, `inviter.{username,global_name}`, `uses`, `max_uses`, `max_age`, `temporary`, `created_at`, `expires_at`. Expiry is `expires_at` if present, else `created_at + max_age`, else "never" when `max_age` is 0. At most 100 entries are kept and entries whose code is not 2 to 32 characters of `[A-Za-z0-9-]` are dropped. `403` shows the missing permission; the list is never refreshed by a loop.
- **Revoke (unverified):** `DELETE /invites/{code}`, no body, `UserWrite`, only after an explicit Confirm on that row, sent once and never retried. Success or `404` (`10006` Unknown Invite) removes the row; `403`, a network error or any other refusal keeps it with a note, and a further attempt needs a new Confirm.
- **Discovery (unverified):** `GET /discoverable-guilds?offset={n}&limit=24` (`UserRead`; Discord accepts at most 48). Reads `guilds[]` (or a bare array) with `id`, `name`, `description`, `icon`, `approximate_member_count`, `approximate_presence_count`; texts are cut (name 100, description 200 bytes), 24 servers per page, at most 4 pages kept. This is a user-client route that has not been captured from an official client; the response shape is a guess. There is no join route in the list: a server is joined with an invite link. Free-text discovery search (the official client uses an external search service) is not implemented.

## Multi-participant call video (#86)

Two small additions to the viewer side of opcode 15 and no new opcode. A call connection already wants `{"<primary ssrc>": 100, "any": 0}` for the cameras that are drawn (#84). A camera drawn small (`MediaSender::set_video_thumbnails`) now names the *lowest-quality active* stream of that user from opcode 12 instead of the best one; the value stays 100 and users with one layer are unchanged. The choice is made by SSRC, not by a quality number, because the only documented use of the value is to scale a sender's bitrate. Changing the layer asks for a keyframe on every receiver. **Not observed against Discord:** whether user clients announce more than one camera layer, and whether the server forwards the lower one on request. A stream viewer (several can run at once, one connection each) now sends `{"any": 0}` while its stream is not drawn, which was previously only a decoder-side suspension, and wants the stream again, from a keyframe, when it is.

## Scheduled community events (#92)

All routes below are user-client routes **not captured from an official client or exercised with the alt account**; the shapes follow the public guild scheduled event object and are read defensively (`fixtures/rest/scheduled-events-synthetic.json` is synthetic). Reads are `UserRead`, writes `UserWrite`; all use `with_error_detail`. Each write is sent once on one explicit click and never retried; the reducer rechecks permissions and the event's state immediately before sending; a 401 stops the account. A list body over 1 MiB is not parsed.

- **List (unverified):** `GET /guilds/{guild}/scheduled-events?with_user_count=true`. At most 100 events are kept; one that does not decode (unknown `status` outside 1 to 4 or `entity_type` outside 1 to 3, bad start time) is skipped alone. Reads `id`, `guild_id`, `channel_id`, `creator_id`, `creator.{username,global_name}`, `name` (100 characters), `description` (1000), `scheduled_start_time`, `scheduled_end_time`, `status`, `entity_type` (1 Stage, 2 voice, 3 external), `entity_metadata.location` (100), `user_count` and `recurrence_rule`. The list replaces the guild's events in the reducer; events deleted on the Gateway shortly before (the last 32 ids per guild) are not revived by a late list.
- **Gateway:** `guild_scheduled_events` on `GUILD_CREATE` (unverified for user accounts; the list covers its absence), `GUILD_SCHEDULED_EVENT_CREATE`/`UPDATE` (the event; an update that omits `user_count` keeps the known count), `GUILD_SCHEDULED_EVENT_DELETE`, and `GUILD_SCHEDULED_EVENT_USER_ADD`/`USER_REMOVE` (`guild_id`, `guild_scheduled_event_id`, `user_id`). The account's own add/remove sets "interested" and is counted once however often it is replayed; other members' adds and removes change the count by one each, so a replayed one can drift the count until the next list. An event of an unknown guild or id is ignored.
- **Interest (unverified for user accounts):** `PUT` and `DELETE /guilds/{guild}/scheduled-events/{event}/users/@me`, no body. Whether the account is interested is not in the list answer, so it is unknown until the Gateway reports it; both buttons are then offered. The UI changes only on the Gateway's user add/remove.
- **Create (unverified):** `POST /guilds/{guild}/scheduled-events` body `{name, scheduled_start_time (ISO 8601 UTC), entity_type, privacy_level: 2, description?, scheduled_end_time?, channel_id | entity_metadata: {location}}`. An external event requires a location and an end time after the start; a Stage or voice event requires a channel. Needs MANAGE_EVENTS (bit 33) or CREATE_EVENTS (bit 44); Discord's per-channel requirements (for example for Stage channels) are left to its 403.
- **Edit/status/delete (unverified):** `PATCH /guilds/{guild}/scheduled-events/{event}` with the full editable set (an edit sends `null` for what is empty, `channel_id: null` for an external event and `entity_metadata: null` otherwise) or `{"status": 2}` (start, only from scheduled), `{"status": 3}` (end, only from active), `{"status": 4}` (cancel, only from scheduled); `DELETE /guilds/{guild}/scheduled-events/{event}`. CREATE_EVENTS alone manages only events whose `creator_id` is the account; MANAGE_EVENTS manages all. Cancel and delete ask for a confirmation first.
- **Recurrence:** `recurrence_rule.{frequency (0 yearly, 1 monthly, 2 weekly, 3 daily), interval, by_weekday (0 = Monday)}` is shown read-only as "Every 2 weeks on Mon, Wed". Other rule fields (`by_n_weekday`, `by_month`, `by_month_day`, `count`) are ignored. Creating or editing a recurrence is not implemented, and editing a recurring event sends no rule.
- **Link:** `https://discord.com/events/{guild}/{event}`.
- **Joining:** the existing voice join path (`JoinVoice`), offered only for an event that is held, not completed or canceled, has a channel, and whose channel is an enabled row with CONNECT.

- Unverified assumptions: that a moderator's invite arrives as `suppress: false` on the invitee (so the audience member is moved to speakers without clicking) and not as a pending invitation that the invitee accepts; that the microphone must stay unsent while suppressed (the client enforces it regardless); that voice-state updates for a Stage carry no other field this client needs.
## Manual commands and message components (#100)

Everything here is **unverified**: none of it was captured from an official user client, and the alt account was not used. It follows community knowledge of the user-account routes (Discord documents only the bot side) and must be confirmed live before the issue's acceptance gate is met (docs/TESTING.md).

- Received: a message may carry `components`, parsed with bounds (at most 40 components in all, depth 3, labels cut at 80 characters, text displays at 2,000, `custom_id` at 100, URLs at 512, 25 options per select) and charged to the message store's byte ledger. Types kept: action row 1, button 2 (styles 1-4 send an interaction, 5 is a link, 6 or a `sku_id` is premium), string select 3, user/role/mentionable/channel select 5-8, and the Components V2 pieces text display 10, section 9, container 17 and separator 14. Anything else (thumbnail, media gallery, file, unknown) is `Unsupported(type)` and drawn as "Unsupported component". `MESSAGE_UPDATE` with a `components` list replaces the held one (an empty list alone is not a field; it still removes buttons from a message that has them). `flags & 64` marks an ephemeral message.
- Button or select: `POST /interactions` with a JSON body `{type:3, application_id, guild_id?, channel_id, message_id, message_flags, session_id, nonce, data:{component_type, custom_id, values?}}`. `application_id` is the message author's ID (a bot user ID is its application ID; not verified for webhook-style responses). `session_id` is the Gateway session ID of the last READY. `nonce` is a fresh snowflake-shaped string. The official client sends the same fields as multipart `payload_json`; JSON is assumed to be accepted. Discord answers `204` with no body. A string select sends exactly one value (selects needing several values, and user/role/mentionable/channel selects, are drawn read-only: "not available in this client").
- Slash command: the same route with `type:2` and `data:{version, id, name, type:1, options:[{type, name, value}]}`, `application_id` of the command; a subcommand is `{type:1, name, options:[...]}`. Values are typed before sending: integer, number, boolean (yes/no), string, and user/channel/role/mentionable as an ID or a mention (`<@id>`, `<#id>`, `<@&id>`). The command list is `GET /guilds/{id}/application-command-index` (server channels) or `GET /channels/{id}/application-command-index` (DMs and group DMs), read as `{application_commands:[{id, application_id, version, type, name, description, options:[{type, name, description, required, choices:[{name, value}], options}]}], applications:[{id, name}]}`: chat-input commands only, at most 200 commands within 256 KiB, 25 options and 25 choices each. Commands with a subcommand group (option type 2) or a required attachment are left out of the list; an optional attachment option is skipped. The list is cached per scope (4 scopes, 1 MiB) for 5 minutes; that lifetime is a guess.
- Modal: `INTERACTION_MODAL_CREATE` `{id, nonce, application:{id} or application_id, channel_id, title, custom_id, components:[{type:1, components:[{type:4, custom_id, label, style 1|2, min_length, max_length, required, placeholder, value}]}]}` (a V2 label wrapper, type 18, is unwrapped). It is shown only when its `nonce` is that of an interaction this client is waiting for in the open channel. Submit: `POST /interactions` `{type:5, application_id, ..., data:{id: <modal id>, custom_id, components:[{type:1, components:[{type:4, custom_id, value}]}]}}`, checked against the input limits first. A required field must not be empty.
- Outcome: `INTERACTION_SUCCESS {id, nonce}` and `INTERACTION_FAILURE {id, nonce, reason_code}` settle the request with that nonce. The control shows a pending state until one of them, the modal for it, or 15 seconds pass ("The application did not respond."). An outcome for a nonce that is not waiting (settled, timed out, another client) changes nothing. The reason code is not mapped; the text is fixed ("The application could not handle that."). The REST answer alone never settles anything, a failed request is reported once, and nothing is ever sent twice.
- Not implemented: autocomplete (`type:4` and `APPLICATION_COMMAND_AUTOCOMPLETE_RESPONSE`), attachment options, subcommand groups, context-menu commands on messages and users (`type` 2 and 3 commands are left out of the list), user/role/mentionable/channel selects and multi-value selects, thumbnails, galleries and files of Components V2, container accent colours, Markdown inside text displays.
- Ephemeral: a message with flag 64 is shown with "Only you can see this" and a Dismiss button that removes it from this client's store only (a local `MESSAGE_DELETE`); nothing is sent, the read cursor never moves to it, and it leaves with the conversation (no history is kept when a channel closes). Ephemeral messages are never edited into the read state or counted as unread by this client.

## Stream audio (milestone 35)

Implemented by `fastcord-platform::loopback`, `fastcord-audio::soundshare`, `fastcord-media` (`MediaSender::send_soundshare`) and the app's `gateway::share_audio` / `gateway::stream_speaker`.

### What is sent
- Audio is Opus on the **stream** session only (the one opened for Go Live), at the audio SSRC from that session's READY (the same SSRC announced as `audio_ssrc` in opcode 12), payload type 120, 20 ms frames, stereo, 128 kbit/s music-tuned, RTP timestamp step 960. Each frame is DAVE-sealed with the stream group's key exactly like voice (`encrypt_opus`), then rtpsize AEAD. The call connection carries only the microphone.
- Before the first frame after silence the stream session sends opcode 5 `{"speaking": 2, "delay": 0, "ssrc": <audio ssrc>}` (SOUNDSHARE, `1 << 1`, no VOICE bit). After 500 ms of digital silence (or a stalled capture) the driver's end-of-speech path runs: five Opus silence frames are not sent (the DAVE silence sentinel is never put on the wire), then `{"speaking": 0, ...}`. Sound resumes with another `speaking: 2`.
- Nothing audio-related is added to Identify, Select Protocol or opcode 12 (the audio SSRC was already announced there).

### What is received
A watch session already receives `VoiceMessage::Audio` for SSRCs it mapped (opcode 12 `audio_ssrc`, opcode 5). Those packets now go to an output-only speaker; nothing else changed on the wire.

### Verified offline
Opcode 5 `speaking: 2` followed by a DAVE-sealed packet that the peer group decrypts to the exact frame, on a resumed stream session next to a surviving parent (`gateway/tests.rs`); stereo 20 ms Opus packetization from synthetic PCM (`soundshare`).

### Assumed, not captured from Discord (verify live, docs/TESTING.md)
That the official viewer plays an SSRC announced as `audio_ssrc` of a stream session with `speaking: 2` (not `1` or `3`); that its decoder accepts 128 kbit/s stereo Opus with no in-band FEC; that no `delay`, priority bit or extra opcode is needed; the official client's own bitrate and whether it expects a lower one; and the audio/video offset a viewer perceives.

Writes are `UserWrite` with `with_error_detail`, each sent once on one explicit click and never retried; a 401 stops the account, a 403 reads as missing permission or hierarchy, a 404 as gone, a `Retryable` failure as "may have been applied". The screen changes only when the Gateway confirms.

- **Create a role (unverified):** `POST /guilds/{guild}/roles` body `{"name": "new role"}` (Discord fills the rest); it appears with `GUILD_ROLE_CREATE`.
- **Edit a role (unverified):** `PATCH /guilds/{guild}/roles/{role}` with only changed fields of `name` (1-100 characters), `color` (plain RGB integer 0-16777215; no gradient or holographic colours), `hoist`, `mentionable` and `permissions` (decimal string; bits the form does not list are kept as they are). Role icons and unicode emoji are not sent. The display follows `GUILD_ROLE_UPDATE`.
- **Delete a role (unverified):** `DELETE /guilds/{guild}/roles/{role}` after a Confirm. `GUILD_ROLE_DELETE` also removes the role from held members and from every channel overwrite.
- **Reorder roles (unverified):** `PATCH /guilds/{guild}/roles` body `[{"id": "<role>", "position": n}]`; Move up/down swaps the position values of two neighbouring roles (both below the account's highest role, neither managed or `@everyone`) and sends those two entries. - **Channel overwrite (unverified):** `PUT /channels/{channel}/permissions/{id}` body `{"type": 0|1, "allow": "<bits>", "deny": "<bits>"}` (0 role, 1 member; `allow` and `deny` never share a bit), `DELETE /channels/{channel}/permissions/{id}` after a Confirm. The channel changes with `CHANNEL_UPDATE`.

This is the documented Modify Channel field; whether the official client's "Sync now" sends this or `lock_permissions` is **not verified**, and `lock_permissions` is not sent. A member's roles can be changed only when their highest role is below the account's (the owner's and one's own excepted).
- **Gateway:** `GUILD_ROLE_CREATE/UPDATE` replace the held role by ID (replays change nothing; a late update for a deleted role is indistinguishable from a missed create and is applied), `GUILD_ROLE_DELETE` also prunes members and overwrites, `CHANNEL_UPDATE` replaces a channel's overwrites. Roles now keep `color`, `hoist`, `mentionable` and `managed`.
- **Not implemented:** role icons, gradient/holographic styles, role member counts and bulk "members of this role" lists, permission templates, Administrator-only creation prompts, per-thread overwrites, and the profile panel's own "Roles" entry (the member menu's is the entry point).

- **Server folders and order (read only).** The Identify capabilities do not include the protobuf user settings, so READY carries the legacy `user_settings` object; its `guild_folders` is `[{id, name, color, guild_ids[]}]` (`id` null for a lone server placed in order; ids as strings or numbers; `color` a 24-bit integer). The protobuf wins over the JSON when both are in READY. A blob that is malformed, over 512 KiB (base64) or lacks field 14 is "unknown": the folders stay as they are. `USER_SETTINGS_UPDATE` carrying `guild_folders` is applied the same way (one event is either a folder change or a privacy change here). - **Rail order.** Servers the settings do not place come first (new servers), then the settings' order. A folder with an `id` is a header row (folder glyph, color, name) followed by its held servers while open; a folder without `id` places its servers directly. A closed folder shows the unread and mention state of its servers. Open/closed is local (per account, settings file), like the folded categories and the per-server "hide muted channels" choice.
- **Not written back.** Moving a server or creating a folder would need `PATCH /users/@me/settings-proto/1` with a base64 `PreloadedUserSettings` (or the legacy settings PATCH) that preserves every unknown field of the account's settings. That merge behaviour is not established, so reordering is not offered; folders are read-only here.
- **Categories.** Folding a category is local; unread channels, the open channel and voice channels with people in them stay listed inside it. The `collapsed` flag of `channel_overrides` is not read.
- **Notification settings:** `PATCH /users/@me/guilds/{guild_id|@me}/settings` (`UserWrite`, once per click, `RestClient::set_notification`). The server itself: `{"muted": true, "mute_config": {"selected_time_window": <seconds>, "end_time": "<RFC 3339 UTC>"}}` for 15 minutes (900), 1 hour, 3 hours, 8 hours and 24 hours; "until I turn it back on" is `{"muted": true, "mute_config": {"selected_time_window": -1, "end_time": null}}`; unmuting is `{"muted": false, "mute_config": null}`; `{"message_notifications": 0|1|2}` (all, only mentions, nothing; 3 is "use the server's setting" for a channel override and the server's default for a server); `{"suppress_everyone": bool}`, `{"suppress_roles": bool}` (server only). A channel or DM is the same object under `channel_overrides.{channel_id}` (no suppress fields). `@me` addresses DMs and group DMs.
- **Reading them.** `user_guild_settings` (READY) and `USER_GUILD_SETTINGS_UPDATE` carry `message_notifications`, `suppress_everyone`, `suppress_roles` and each override's `message_notifications`. A channel notifies at its override, else the server's level, else the server's `default_message_notifications`, else all messages. "Only @mentions" removes the unread dot but keeps mention counts; "Nothing" hides both and silences desktop notifications; suppressed `@everyone`/`@here` and role mentions are not counted as mentions for the badge or the toast (the message still highlights). A mute is read once at READY or update (`end_time` already past is ignored); a mute that expires during a session is not re-evaluated until the next settings event.

No new route. `POST /channels/{id}/messages` already carried `"tts": false`; a draft starting with `/tts` now sends `"tts": true` with the prefix removed. The message object's `tts` boolean is read on `MESSAGE_CREATE` and in history. Discord requires SEND_TTS_MESSAGES (bit 12) for a `tts` message; the client checks it first (the reducer's channel permissions) and the server stays authoritative (a 403 is the ordinary send failure). **Unverified:** that the official client reads a message sent this way, and whether a DM needs any permission (none is checked). Speech synthesis itself is local and has no wire traffic.

## Manual moderation and audit log (#95)

Every route below is a user-client route **not captured from an official client or exercised with the alt account**; shapes follow public documentation. Each is one explicit click, sent once, never retried. `X-Audit-Log-Reason` (percent-encoded, at most 512 bytes before encoding, omitted when blank) is added to kick, ban, timeout and nickname requests only.

- **Timeout (unverified):** `PATCH /guilds/{g}/members/{u}` `{"communication_disabled_until": "<ISO 8601>"|null}`; durations 60 s, 5 min, 10 min, 1 h, 1 day, 1 week from the click; `null` removes it. Needs MODERATE_MEMBERS (bit 40); not offered for administrators or the owner.
- **Nickname (unverified):** `PATCH /guilds/{g}/members/@me` `{"nick": str|null}` (CHANGE_NICKNAME, bit 26) and `PATCH /guilds/{g}/members/{u}` `{"nick"}` (MANAGE_NICKNAMES, bit 27, hierarchy as for kick); `null` resets; at most 32 characters.
- **Ban (existing route, extended):** `PUT /guilds/{g}/bans/{u}` `{"delete_message_seconds": 0|3600|21600|43200|86400|259200|604800}`; the default is 0.
- **Ban list (unverified):** `GET /guilds/{g}/bans?limit=50[&after=<user id>]` (BAN_MEMBERS); 50 per page, at most 500 held. **Unban (unverified):** `DELETE /guilds/{g}/bans/{u}` after a Confirm.
- **Voice move (unverified):** `PATCH /guilds/{g}/members/{u}` `{"channel_id": "<voice channel>"}` (MOVE_MEMBERS; the account and the member must both see and connect to the destination, checked by the reducer).
- **Delete another user message:** the existing `DELETE /channels/{c}/messages/{m}` with MANAGE_MESSAGES. **Bulk delete (unverified):** `POST /channels/{c}/messages/bulk-delete` `{"messages": [ids]}`, 2 to 100 messages, each younger than 14 days (judged from the snowflake time, one minute inside the limit, at selection and again at send); Discord refuses the whole request if one does not qualify. `MESSAGE_DELETE_BULK` (already decoded) removes the rows.
- **Reactions (unverified):** `DELETE /channels/{c}/messages/{m}/reactions/{emoji}/{user}` removes one user reaction, `DELETE .../reactions/{emoji}` clears one emoji (MANAGE_MESSAGES, Confirm). The official client may use a typed `/0/{user}` form as it does for the own reaction.
- **Threads (unverified):** `PATCH /channels/{thread}` `{"archived"?, "locked"?}` (MANAGE_THREADS); the header follows `THREAD_UPDATE`.
- **Audit log (unverified):** `GET /guilds/{g}/audit-logs?limit=50[&before=<entry id>][&action_type=n][&user_id=u]` (VIEW_AUDIT_LOG, bit 7); parsed with at most 50 entries and 200 users; names come from the answer `users`; an unknown `action_type` shows as "Action n". A two-factor demand (code 60003) is shown, never answered.

## Authorized apps, server integrations, connections and webhooks (issue #101)

Implemented by `fastcord-discord::apps` (plus `profile_edit` for connections) and the app's `apps` panel. Every route below is a user-client route from public documentation and community knowledge, **not captured from an official client or exercised with the alt account**. Writes are `UserWrite` with `with_error_detail`, each sent once on one explicit click and never retried; 401 stops the account, 403 reads as missing permission, 404 as already gone, 429 as rate limiting, `Retryable` as "may have been applied".

- **Authorized apps (unverified):** `GET /oauth2/tokens` -> array of `{"id", "scopes", "application": {"name"}}` (the authorization id, not the application id); at most 100 rows kept. Deauthorize: `DELETE /oauth2/tokens/{id}` after a Confirm.
- **Server integrations (unverified):** `GET /guilds/{g}/integrations` (MANAGE_GUILD, checked in the reducer) shows name, type, account and bot user. Remove: `DELETE /guilds/{g}/integrations/{id}` after a Confirm.
- **Adding an app (browser only):** the panel takes a numeric client id (or a pasted authorize link) and opens `https://discord.com/oauth2/authorize?client_id=<id>&scope=bot%20applications.commands` in the default browser. There is deliberately no native authorization: the consent page, its permission list, CAPTCHA and any MFA belong to Discord's own origin, and a user-token client must neither answer them nor request an OAuth grant itself.
- **Connections (unverified):** `GET /users/@me/connections` is read-only (type, name, visibility, `show_activity`). Toggles are `PATCH /users/@me/connections/{type}/{id}` with `{"visibility": bool}` or `{"show_activity": bool}`; the list updates only after the answer. No connection is added, removed or refreshed.
- **Incoming webhooks (unverified):** the list of #98, `GET /channels/{c}/webhooks` (MANAGE_WEBHOOKS), keeps only `type: 1` here (type 2 follower rows stay in "Followed announcements"). Create `POST /channels/{c}/webhooks` `{"name"}`; rename and/or move `PATCH /webhooks/{id}` `{"name"?, "channel_id"?}`; delete `DELETE /webhooks/{id}` after a Confirm. Names are 1-80 characters.
- **Webhook token:** held in a zeroizing buffer in the open panel only, absent from `Debug`/`Display`/logs, dropped when the panel closes or the account changes. "Copy webhook URL" writes `https://discord.com/api/webhooks/{id}/{token}` to the clipboard only on its own click. A rename answer without a token keeps the one already held. Nothing is ever executed or posted through a webhook; fixtures carry fake tokens.
- **Not implemented:** live `WEBHOOKS_UPDATE`/integration events (lists are loaded when opened), adding connections, linked-role and app command settings, an app directory, bot permission editing.
- **Unverified:** every route and field name above, whether deauthorizing needs MFA or a password, the `show_activity` field, and whether Discord answers a rename with the token.

## Embedded Activities, read only (issue #102)

All **unverified** (no capture; assembled from public descriptions). `EMBEDDED_ACTIVITY_UPDATE` and `EMBEDDED_ACTIVITY_UPDATE_V2` are read leniently: `guild_id`; channel from `channel_id` or `location.channel_id`; `embedded_activity.application_id` and `embedded_activity.name` (or the same keys at the top level); the activity runs while `participants` (V2: `connections`) is non-empty, or, when neither array exists, while `embedded_activity` is present. Keyed by (channel, application): a replay changes nothing, an end of an unknown activity is ignored, at most 3 per channel and 32 per guild, names cut to 64 characters without control characters. Nothing is sent: no launch, join or SDK message. Whether the Gateway delivers these events to this client (they may need a subscription flag) is not known. Presence `activities` are not used: only friends and DM recipients receive presence here.
## AutoMod and communication safety (#96)

Every route below is a user-client route **not captured from an official client or exercised with the alt account**; shapes follow public documentation. Each write is one explicit click, sent once, never retried. Discord's refusal message and code are shown as they came (`with_error_detail`); a two-factor demand (60003) is shown, never answered.

- **List (unverified):** `GET /guilds/{g}/auto-moderation/rules` (MANAGE_GUILD), read when the panel opens; at most 50 rules, 1000 keywords, 10 patterns, 1000 allowed phrases, 8 actions and the exemption lists are kept per rule, with every string cut.
- **Create (unverified):** `POST .../rules` `{name, event_type: 1, trigger_type: 1|3|4|5, trigger_metadata?, actions, enabled, exempt_roles, exempt_channels}`. `trigger_metadata`: keyword rules `keyword_filter` (at most 1000 of 60 characters), `regex_patterns` (10 of 260), `allow_list` (100); word-list rules `presets` (1 profanity, 2 sexual content, 3 slurs) and `allow_list` (1000); mention spam `mention_total_limit` (1-50) and `mention_raid_protection_enabled`; spam has none. Actions: `{type: 1, metadata?: {custom_message}}` (at most 150 characters), `{type: 2, metadata: {channel_id}}`, `{type: 3, metadata: {duration_seconds}}` (at most 2419200, keyword and mention rules only), `{type: 4}` (member profile rules only). Per server 6 keyword rules and one each of spam, word list, mention spam; at most 20 exempt roles and 50 exempt channels. Member profile rules (trigger 6, `event_type` 2) are listed, switched and deleted but not created.
- **Edit (unverified):** `PATCH .../rules/{id}` with only the fields that differ (`name`, `enabled`, `trigger_metadata` whole, `actions` whole, `exempt_roles`, `exempt_channels`). Unknown `trigger_metadata` keys and unknown action objects are kept and sent back unchanged. **Delete (unverified):** `DELETE .../rules/{id}` after a Confirm.
- **Gateway (unverified for user accounts):** `AUTO_MODERATION_RULE_CREATE`, `_UPDATE` and `_DELETE` carry the rule object; they are kept as the last 8 changes (256 KiB) and applied to the open list by rule ID, so replays change nothing. `AUTO_MODERATION_ACTION_EXECUTION` is not decoded.
- **Refused sends:** error codes 200000 and 200001 on `POST /channels/{c}/messages` read "AutoMod blocked this message: <message> (code)"; Discord's message names the rule when it gives one. **AutoMod alert messages** are message type 24; the rule comes from an embed field named `rule_name` and the person from the embed author (both unverified names), the flagged text is the embed's own.
- **Safety settings (unverified):** `PATCH /guilds/{g}` `{"verification_level": 0-4}` and `{"safety_alerts_channel_id": id|null}` (only changed fields, so every other field is untouched); both are read from the guild's properties and `GUILD_UPDATE`. `RAID_ALERTS_DISABLED` is read from `features` and shown only. `POST /guilds/{g}/mfa` `{"level": 0|1}` (owner only) requires or stops requiring two-factor authentication of moderators; the display follows `GUILD_UPDATE` `mfa_level`.

## Write allowlist

Every non-GET request passes `RestClient::check_write` (`fastcord-discord/src/write_group.rs`). It is classified into a `WriteGroup` by method, normalized route and, for `POST /channels/{c}/messages`, the JSON body (`poll`, non-empty `sticker_ids`, `message_reference.type == 1`, `tts: true` make it **Message extras**; a non-empty `attachments` makes it **File uploads**; anything else is **Basic messages**). A route shared by features (`PATCH /channels/{c}`, `DELETE /channels/{c}`, `PATCH /guilds/{g}`, `DELETE /webhooks/{id}`) takes the group its caller names with `RestRequest::in_group`. A group that is off fails before the rate limiter and the network with `RestError::WriteNotVerified`; an account refusal (CAPTCHA or verification) still stops all writes first. A write the table does not know is `Unclassified`, which is off. Gateway op 4 (voice state) is not REST and is unaffected; opening an existing DM sends nothing. Password login and QR remote auth use their own HTTP path and are not covered; the notification-setting quarantine (`NOTIFICATION_WRITES_ENABLED`) is a separate hard block.

**On by default (seen working on the alt account):**
- Basic messages: `POST /channels/{c}/messages` (plain text, replies, silent), `PATCH` and `DELETE /channels/{c}/messages/{m}`.
- Own reactions: `PUT` and `DELETE /channels/{c}/messages/{m}/reactions/{emoji}/@me` (remove uses `/0/@me`).
- Typing: `POST /channels/{c}/typing`.
- Read acknowledgement: `POST /channels/{c}/messages/{m}/ack`.
- Attachment URL refresh: `POST /attachments/refresh-urls` (read-like, automatic).

**Off by default (turn on one at a time under Settings, Advanced, Test unverified actions; session only, fake mode turns all on):** Message extras; File uploads (`POST /channels/{c}/attachments`); Pins; Poll votes; Application interactions (`POST /interactions`); Ring a call; Soundboard play; Open a DM by typed ID (`POST /users/@me/channels`); Group DM management; Relationships, ignore and message requests; Friend request by username (`POST /users/@me/relationships`); Join or leave a server (`POST /invites/{code}`, `DELETE /users/@me/guilds/{g}`); Create and revoke invites; Profile and connections; Status and privacy settings (`PATCH /users/@me/settings`, `/users/@me/guilds/{g}/settings`); Log out sessions; Deauthorize an app; Reports; Server administration; Channels; Roles and permission overwrites; Moderation (members, bans, bulk delete, others' reactions); AutoMod; Community and onboarding setup; Accept rules and onboarding answers; Scheduled events; Announcements; Emoji, stickers and sounds; Webhooks and integrations; Stage voice states and instances; Threads and forum posts; Other, unclassified writes. The exact routes of each group are listed in the switch and in `WriteGroup::routes`.

The refusal text is "Not yet verified on a live account. Enable it under Settings → Advanced → Test unverified actions (alt account only)." (`WRITE_NOT_VERIFIED`).
