# Testing

## Automated (CI, every push)
`cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` on Windows, Linux, and macOS. Tests are deterministic and offline: protocol fixtures in `fixtures/`, injected clocks, crypto/media vectors. No live credentials in CI.

### REST transport and scheduler (milestone 4)
- `cargo test -p fastcord-discord --locked` exercises the real scheduler with an injected monotonic clock and sanitized `fixtures/rest/rate-limits.json`; no sockets, credentials, wall-clock sleeps, or server timestamps are involved.
- Coverage includes shared bucket hashes across methods/routes without conflating major IDs, fractional resets, global and per-route 429 pauses (body/header/scope), concurrent reservations and out-of-order responses, unknown-route serialization, priority ordering, cancellation, byte budgets, and account-wide stop when the transport observes a 401.
- Raw `Authorization` headers and token/request Debug redaction are checked offline. Network and 5xx failures are returned to callers for reconciliation/retry policy; only confirmed 429 rejections are rescheduled. A failed or ambiguous message POST must not be retried blindly.
- Live alt-account `GET /users/@me`, correct-account display, app restart restoration, and real-account credential deletion remain pending: the maintainer's authenticated browser was not available through the browser relay or CDP during milestone 5. The implemented token path is covered offline and can be exercised without touching a real account.

### Login and native credential storage (milestone 5)
- `cargo test -p fastcord-app --locked` uses sanitized `fixtures/rest/current-user.json` and deterministic UI-state transitions. It covers warning acknowledgement, input byte limits, invalid-token stop, explicit consent after storage failure, saved versus memory-only state, immediate authentication-worker cancellation on logout, state/secret purge, deletion failure/retry, saved-account identity mismatch, and redaction of text-input messages/session results.
- `cargo test -p fastcord-platform --locked` uses the keyring ecosystem's in-memory test store for the real platform adapter's account naming/discovery, save/load/overwrite/delete, locked-store behavior, idempotent deletion, malformed-secret handling, and categorical error redaction. CI never opens a real user's native store.
- In an interactive desktop session with an unlocked native store, run `cargo test -p fastcord-platform native_dummy_save_restart_restore_delete --locked -- --ignored`. It saves a dummy secret under the separate service `fastcord-m5-test`, opens a new store instance to discover/restore it, deletes it, and confirms both retrieval and discovery are empty. No real Discord credential is used or printed.
- Windows UI checklist: launch `target/debug/fastcord.exe`, observe the ToS/alt-account warning and masked input, acknowledge it, submit an obviously fake token, and confirm the real Discord API rejection returns to the login screen without an authenticated account. Check the explicit memory-only choice and the lack of inactive QR buttons.
- Windows milestone 5 results: the actual debug app opened and closed normally; the warning, acknowledgement, explicit memory-only choice, masked token field, and lack of inactive QR controls were observed. Submitting an obviously fake token through the real UI reached Discord and returned the rejected-token error with the field cleared and no authenticated account. The separate-service native dummy save/new-store restore/delete check also passed and confirmed no test entry remained.
- Pending live-alt checklist (Windows, Linux, macOS): obtain only the authorized alt token, paste it into the real app, confirm display name/username/ID against that account, restart and confirm only the saved token restores, then log out and verify the native entry is absent. Check locked-store explanation/explicit nonpersistent consent; restart a memory-only session and confirm it does not restore. Test a real invalid token and confirm login stops.
- macOS maintainer checklist: use the CI-built native app; perform the preceding live-alt checks with login Keychain unlocked, then locked/denied; use Keychain Access to confirm service `fastcord` and the alt's account ID disappear on logout. Linux native checks need an interactive session D-Bus and Secret Service provider.

### QR login (milestone 5a)
- `cargo test -p fastcord-discord remote_auth --locked` runs the real client state machine against an in-process gateway that uses real WebSocket framing (in-memory duplex) and performs real RSA-2048 OAEP with the public key the client sends. Fixtures: `fixtures/remote-auth/` (documented `hello` payload, a CAPTCHA-required exchange response with a placeholder site key). Coverage: full flow to token with exactly one ticket exchange; fingerprint mismatch stops before any QR; phone cancel after scan; CAPTCHA stop with no token; tokens that are not clean credentials rejected; out-of-order, binary, malformed, and undecryptable frames; unknown ops ignored; gateway close code 4003 maps to expiry; the server timeout is honored and clamped (a hostile `0` expires at the 5 s floor, not immediately); heartbeat cadence and a missing ack being fatal (paused Tokio clock); dropping the event receiver cancels; nonce-proof base64url encoding with bytes that differ from standard base64; per-attempt key uniqueness; Debug redaction of events, keys, and payloads. No sockets or credentials are used.
- `cargo test -p fastcord-app --locked` covers the QR screen state: start requires the warning acknowledgement, regenerate uses a new attempt id and ignores stragglers (including a late token), cancel returns to login and drops the attempt, expiry/phone-cancel/CAPTCHA end states and their wording, authorization entering the same validation/storage worker as token paste, and redaction of QR messages and phases.
- Live, unauthenticated (needs only network; run manually): `cargo test -p fastcord-discord live_ --locked -- --ignored --nocapture`. It performs the real `hello` → `init` → nonce proof → `pending_remote_init` handshake, requires a 43-character fingerprint, keeps the session open across two heartbeat intervals (about 95 s) to prove heartbeat acks, and posts a bogus ticket to the exchange endpoint. Windows results (2026-10-07): handshake and QR issued; session lifetime reported by the server 299–339 s; heartbeat acks worked; bogus ticket answered with HTTP 404 and no CAPTCHA.
- Windows UI results: the real debug app showed the QR screen only after the warning was acknowledged and **Show QR code** was pressed; the rendered code, screenshotted and decoded with an independent QR reader, contained `https://discord.com/ra/` plus a 43-character fingerprint; **Cancel** returned to the login screen with the acknowledgement kept; with no scan, the code expired on its own after the server timeout (about 5.5 minutes) and the screen read "This QR code expired." with **Generate new code** and **Back to login**; **Generate new code** produced a different, decodable QR code.
- Pending live-alt checklist (Windows, then macOS/Linux): scan the code with the alt account's phone app and confirm the screen names the alt account while waiting for confirmation; confirm on the phone and verify the app logs in as the alt, saves the credential (restart restores it), and logs out cleanly; cancel on the phone and confirm the cancel message; let a code expire and generate a new one; cancel in the app mid-scan and confirm the phone shows no pending login afterward; note whether Discord ever answers the real ticket exchange with a CAPTCHA (the app must stop with the CAPTCHA message). Never record the token or ticket.

### Main Gateway lifecycle (milestone 6)
- `cargo test -p fastcord-discord gateway --locked` runs the real connection driver against an in-process Gateway that speaks real WebSocket framing (in-memory duplex) and a real persistent zlib stream (the test server compresses with a persistent `flate2` compressor, each event ending in a sync flush). Tokio time is paused, so heartbeats, backoff, and timeouts are deterministic and instantaneous. Fixtures: `fixtures/gateway/` (`ready.json` in the deduplicated PRIORITIZED shape, `ready_supplemental.json`, `ready_non_deduped.json`, `passive_update_v2.json`, `identify.sanitized.json`, `app-page-excerpt.html`; all IDs fabricated).
- Coverage: fragmented compression (READY in 7-byte and events in 1-byte WebSocket messages, flush suffix split across messages, dictionary shared across events, a new connection needing a new dictionary, garbage, a decompression bomb stopped at the 16 MiB ceiling, scratch released after a large event); READY and READY_SUPPLEMENTAL normalization (user dedupe, `merged_members` alignment around an unavailable guild, DM `recipient_ids`, null arrays, partial users, the non-deduplicated shape, misaligned members rejected); Identify payload value-for-value against the recorded sanitized payload; jittered first heartbeat and exact interval, latest sequence (including from unhandled events), missed ACK to Resume to RESUMED, replay and in-connection duplicates dropped, server reconnect (op 7), Invalid Session (resumable and not) with an identical profile after re-Identify, repeated Invalid Session stop, every close-code class (4004 auth stop of REST work too, fatal codes, session-ending vs resumable), REST-originated 401 stop, discovery 401, off-Discord URLs refused, backoff schedule with refused connects, hello timeout, hostile heartbeat interval, heartbeat-request flood bounded by the 120/60 s ceiling, 16 MiB event ceiling, malformed READY, `required_action`, a consumer that stops reading for several heartbeat intervals (30 x 150 KB events through the 2 MiB queue: heartbeats continue, nothing is dropped or reordered), and a clean 1000 close on drop.
- `cargo test -p fastcord-app --locked` covers the account screen's Gateway panel: status folding from the event stream, never showing "Connected" while reconnecting, stale-session messages ignored, a rejected token returning to login without silently deleting the saved credential, logout dropping the connection, and redaction.
- Live, unauthenticated (needs only network; run manually): `cargo test -p fastcord-discord live_ --locked -- --ignored --nocapture`. `live_build_number_is_fetched_from_the_web_client` reads the real build number; `live_real_gateway_negotiates_zlib_stream_and_rejects_a_bogus_token` performs real discovery, TLS WebSocket, real compressed HELLO, the real Identify payload, and expects the real close 4004. Windows results (2026-10-07): build number 631730 fetched; states `Connecting, AwaitHello, Identifying, AuthenticationRequired` (4004, not 4002).
- **Pending live check (alt account; needs a token, which was not available):** with `FASTCORD_LIVE_TOKEN` set in the environment of that single command (never in a file), run `cargo test -p fastcord-discord live_account --locked -- --ignored --nocapture`. It Identifies with the real profile, prints READY/READY_SUPPLEMENTAL counts, severs the connection, and requires `Resuming` then `RESUMED` with no second READY. Also record whether READY arrives without a challenge or `required_action` (closes risk U1), whether `merged_members` really is parallel to `guilds` (including unavailable ones) and READY_SUPPLEMENTAL's member/user shape (the code assumes the documented ones and stops with `MalformedReady` otherwise), and that `PASSIVE_UPDATE_V2` arrives for an unsubscribed guild. In the app: log in as the alt, confirm the account screen reads "Connected to Discord: N servers, M direct messages.", disable the network for ~1 minute and confirm it shows reconnecting (never "Connected"), restore it and confirm it recovers, then log out and confirm the alt shows offline in the official client.

### Interop partner for voice and Go Live
- **fastcord** runs as the **alt account** (already logged in on discord.com in the maintainer's browser; obtain login via QR/token from that session).
- **Partner:** the maintainer's official Discord client on the same PC, in a private test server/DM with the alt.
- The agent verifies results itself: captures the official client's audio output (WASAPI process loopback) and analyzes it (presence, level, a known test tone/phrase), and screenshots the official client's window for video. No second human is required.
- The agent never sends messages, joins channels, or changes settings from the maintainer's main account beyond the agreed test server/DM.

Live Discord tests use the alt account only. Never commit tokens, voice tokens, DAVE state, or signed CDN URLs; sanitize captured fixtures.

## Per-milestone checklist
Each milestone in `docs/SPEC.md` §16 lists acceptance criteria. Before committing, exercise every criterion on the platforms it names and note the result (and any measurement) in the commit message body.

### Bounded state and lazy subscriptions (milestone 7)
- `cargo test -p fastcord-discord --locked` covers it with no network and no credentials. Fixtures: `fixtures/gateway/` (`subscriptions_navigation.json`, `member_list_update_sync.json`, `member_list_update_ops.json`, `voice_state_update.json`, `guild_member_update.json`, plus the READY-family ones; all IDs fabricated, shapes from community documentation).
- `gateway::subscription` and `gateway::tests` (real driver, in-process WebSocket/zlib Gateway, paused time): exact two-guild navigation fixture; coalescing; bounded viewport/member interests; pre-READY gating; fresh Identify replay; Resume replay and explicit release of subscriptions removed while disconnected; navigation churn below the 120/60 s ceiling while heartbeats continue (including a short HELLO interval). Only opcodes 1, 2, 6, and 37 are sent; there is no opcode-14 fallback. Oversized batch planning is an error, not a silent dropped entry.
- `state::member_list` (sparse flat-list model): SYNC, INSERT, UPDATE, DELETE, and INVALIDATE with index-correct shifting across segments and holes, joining, a short SYNC ending the list, unknown operations, `u32::MAX` positions, and the 1,000-row cap.
- `state` reducer tests: deduplicated users survive until READY_SUPPLEMENTAL references them; supplemental member/voice alignment; voice updates while browsing another guild and passive updates for cold guilds; monotonic channel markers; partial member/user field presence versus explicit clearing; zero member-list headers; selected channel list-key matching; navigation and viewport range release; guild/channel/DM lifecycle. **Byte caps:** a generated account of 120 guilds x 250 channels with 60,000 member updates remains within 12 MiB with identity intact, while voice/requested/visible-row members remain pinned. Allocated capacities and map slack are charged, the ledger is compared with a full recount, and eviction releases map backing allocations. A mandatory identity floor above the limit yields a terminal diagnostic and releases the account store instead of exceeding the ceiling or silently losing permissions.
- `cargo test -p fastcord-app --locked`: the worker applies ordered events, counts follow the reducer, and required state above the safety ceiling produces the visible terminal error and closes the Gateway.
- Windows UI result: the real debug executable was built, launched, and visually observed on the native desktop (776 x 679 window); the unauthenticated warning, QR/token login controls, masked input, and saved-login retry were displayed. It closed normally. No authenticated alt session was available, so the connected-state safety diagnostic and guild/member views were exercised offline rather than claimed as a live UI result.
- **Pending live checks (alt account; needs a token, which was not available):** with the alt logged in and a second test guild joined: (1) select a channel through a throwaway harness or the milestone 8 list and confirm the first opcode 37 is accepted (no close 4002/4001) and `GUILD_MEMBER_LIST_UPDATE` with a `SYNC` for `[0, 99]` arrives; record the real list `id` for a channel with permission overwrites and whether `typing: false` for a never-subscribed guild is harmless (**U2**); (2) switch guilds and confirm the first guild's `INVALIDATE`/silence and that its PASSIVE_UPDATE_V2 resumes; (3) join voice in guild A, browse guild B, have the official client join/leave voice in A, and confirm A's voice states stay current (via VOICE_STATE_UPDATE for the subscribed voice guild); (4) sever the connection and confirm after a Resume the resent subscription is accepted and no duplicate list state results; (5) confirm which guilds the server subscribes implicitly before any opcode 37 (do MESSAGE_CREATE events arrive for guilds never selected?). Update `docs/PROTOCOL.md` with the results.

### Guild/channel navigation and renderer (milestone 8)
- Offline reducer fixtures (`fixtures/gateway/navigation_ready.json`, `guild_role_events.json`, `subscriptions_guild_only.json`, and READY-family payloads) exercise accessible text/announcement/voice rows, category/position ordering, owner/admin and everyone/role/member overwrites, incomplete permission metadata, forbidden injected clicks, remembered selection, channel deletion, guild outage/recovery, membership updates, and role create/update/delete. Selection is validated against current reducer state, not trusted UI data.
- App tests cover fixed-height viewport/overscan ranges independent of account size, 10,000 coalesced navigation/viewport commands, and a latest-slot presentation queue with at most one outstanding notification. No histories are requested by navigation; opcode 37 selects only the browsed guild, requests the current member if permissions need it, and leaves member-list ranges empty because no member sidebar is displayed.
- Renderer configuration tests check one native wgpu API (DX12/Metal/Vulkan according to target) and no OpenGL/automatic API mask. The real compositor uses explicit settings rather than environment mutation; tiny-skia remains the no-supported-adapter fallback.
- Windows UI result (2026-10-07): the actual release app launched and rendered its login controls normally with conflicting `WGPU_BACKEND=gl` and `ICED_BACKEND=tiny-skia`; no login was attempted. A temporary, subsequently removed fixture launcher used the same native renderer, Store/Navigation, fixed-height lists, and navigation view with `navigation_ready.json`: accessible channel/category rows and a disabled outage guild were visually observed; selecting `read-only` displayed its permission summary; clicking the no-CONNECT voice row did not change selection; scrolling exposed later categories while retaining the selected ID. Both windows closed normally. This was an offline fixture check, not a claim of authenticated Discord interoperability. Working-set/private/GPU measurements are in `docs/PERFORMANCE.md`.
